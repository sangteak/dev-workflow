## 2026-03-19 — handoff-discovery-ux

### 스킬 지시문과 실제 출력의 괴리
- **문제:** context-handling에 출력 템플릿이 정의되어 있었지만, Claude가 실제로 따르지 않았음
- **원인:** orchestrator가 탐색 로직을 인라인으로 포함하여 Claude가 중간 과정을 보고함
- **교훈:** 출력 책임을 한 곳에 일원화하고, 금지 출력 패턴을 명시적으로 나열해야 함

### 완료된 작업의 잔존 HANDOFF 처리
- **문제:** `status: complete`인 작업의 HANDOFF.md가 남아있으면 "진행 중인 작업"으로 노출됨
- **교훈:** status 체크를 HANDOFF 존재 여부보다 우선순위로 두어야 함. 잔존 HANDOFF는 삭제를 제안할 것

### 설계 문서 테이블 중복
- **문제:** 라벨 규칙 테이블에서 `status: complete` 항목이 우선순위 이동 후 원래 위치에 중복 잔존
- **교훈:** 우선순위 변경 시 원래 위치의 항목을 반드시 제거할 것

## 2026-03-26 — skill-aliases

### 플러그인 commands/ 추가 후 Claude Code 재시작 필요
- **문제:** 플러그인에 commands/ 파일을 추가하고 push까지 완료했지만 콘솔에서 새 커맨드가 노출되지 않음
- **원인:** Claude Code가 세션 시작 시 플러그인 커맨드를 캐싱하므로, 런타임 중 추가된 파일은 감지하지 않음
- **교훈:** commands/ 디렉토리에 파일을 추가/수정한 후에는 사용자에게 Claude Code 재시작을 안내할 것

## 2026-07-08 — skill-slimming (G4)

### 플랜의 수치 프록시 체크는 구조 상한을 먼저 계산할 것
- **문제:** plan.md에 "본문 40%+ 감소, 합계 ±5%" 체크를 넣었으나 실측은 24.8%/8.9%, +10~12% — 이동 가능 바이트의 구조적 상한과 고정 삽입 오버헤드를 플랜 작성 시 계산하지 않음
- **교훈:** 수치 프록시를 플랜에 넣기 전에 상한을 실측(또는 추정 근거 명시)할 것. 프록시가 깨지면 원래 증명하려던 직접 속성(byte-identical 이동 + 순증 전량 분류)을 검증해 대체 판정할 것 — 설계 문서의 "수치 목표는 비목표" 원칙이 플랜 세부 체크보다 우선한다

### 치환 지정은 대상 섹션의 경계를 명시할 것
- **문제:** "상태 정규화 전처리 섹션을 1줄로 치환" 지정이 섹션 경계를 명시하지 않아, 구현자가 인접한 "0. 경로 해소" 스텝(F3 추적 앵커 포함)까지 함께 삭제 — 태스크 리뷰가 포착해 복원
- **교훈:** 플랜에서 블록 치환을 지정할 때 시작/끝 라인 또는 경계 문장을 명시할 것. 크로스레퍼런스 인벤토리(F3)가 안전망으로 실제 작동했음 — 추적 앵커 등재의 가치 실증

## 2026-07-09 — conversation-ux

### 규범의 의미를 역전시킬 때는 구 독트린 문장을 전수 스윕할 것
- **문제:** §4를 "일괄 수용→노출된 선택지에만"으로 역전 개정했는데, 같은 의미를 서술하는 무변경 컨텍스트 줄 5곳(§1 응답 주권·8+ 푸터·폴백 2점·brainstorming 폴백)이 구 독트린 그대로 잔존 — 그중 1곳은 항상 주입되는 bootstrap이라 사고 재발 경로였음. 태스크 단위 리뷰는 변경 지점만 보므로 전부 통과했고, 최종 브랜치 리뷰(전체 시야)에서야 적발
- **교훈:** 규범 의미를 바꾸는 변경은 "그 규범을 재서술하는 문장"의 grep 인벤토리(예: "일괄", "수용한다" 계열)를 게이트 인벤토리와 병행해 전수 스윕할 것. 태스크 리뷰의 사각(무변경 줄)은 전체 리뷰가 유일한 망 — 최종 리뷰를 생략하지 말 것

### 출력 형식 펜스의 필수 슬롯을 체크리스트로 검증할 것
- **문제:** 플랜이 작성한 Socratic 노출 펜스에 `[질문 내용]` 슬롯이 누락된 채 verbatim 반영됨 — 펜스를 리터럴 출력하는 모델은 질문 없는 질문 화면을 냄. 신선한 눈 리뷰가 동형 펜스(A-0)와의 대조로 적발
- **교훈:** 출력 템플릿을 플랜에 확정 문면으로 박을 때, 동형 템플릿 간 슬롯 대조(제목/본문/안내줄)를 셀프 리뷰 항목에 포함할 것

## 2026-07-09 — gate-effectiveness (G5)

- **교훈:** 규범 의미를 바꾸는 개정의 스윕은 skills/ 외 사용자 문서(README·commands)까지 포함할 것. 스윕 사각은 최종 리뷰가 유일한 망이라는 conversation-ux 교훈의 확장판

### 조사 보고의 집계 수치는 표 행 실측과 대조할 것
- **문제:** 심사 보고가 "유지 22건"이라며 게이트 23개를 나열 — 오프바이원이 설계 문서 §4 집계로 승계됐고 구현 태스크가 표를 실측하다 발견
- **교훈:** 수치 요약과 그 근거 목록(행)을 받으면 개수를 직접 세어 대조할 것. 표가 원본이고 집계는 파생이다

### 서브에이전트 main 오염은 경고만으로 안 막힌다
- **문제:** 워크트리 경고에도 haiku 구현자가 main 체크아웃에 선편집·선커밋 (커밋은 자가 정정, 작업 트리 잔재는 컨트롤러 복구) — 두 릴리스 연속 재발
- **교훈:** 디스패치 프롬프트 경고 강화(branch+pwd 이중 확인 지시)에 더해, 태스크 리뷰·최종 검증에 "main 무오염 확인"을 상시 항목으로 넣을 것 (이번에 T3부터 적용해 재발 차단 확인)

## 2026-07-13 — issue-lifecycle

### 스윕 예외 판정은 검증자 재량이 아니라 plan 문면을 따른다
- **문제:** plan이 "hotfix·핫픽스 어휘 예외 없음, 전부 제거"를 명시했는데, Task 8 스윕 검증자가 잔존 1건("긴급 핫픽스용")을 "구 독트린과 무관한 일반 형용사"로 오탐 제외 판정 — 최종 브랜치 리뷰가 스펙 위반으로 뒤집음
- **교훈:** 스윕의 제외 판정 기준은 검증 시점의 의미 해석이 아니라 plan의 명문 범위다. "예외 없음" 지시가 있으면 의미가 무관해 보여도 제거하거나, 예외로 남기려면 사용자 확인을 거칠 것. 두 검증자(태스크 vs 최종)의 판정이 충돌하면 plan 문면이 이긴다

### 삭제 태스크의 검증 grep은 "모드명"이 아니라 "절차 어휘"까지 포함할 것
- **문제:** Mode 2·3 삭제 후 검증 grep이 모드명 패턴만 검사해, 모드명 없는 절차 불릿 4개(주의 사항의 domain.md 통합·pending·feature 삭제 서술)가 사각에 남음 — 같은 파일 안 자기모순으로 최종 리뷰에서 적발
- **교훈:** 절 삭제의 잔존 검사는 삭제된 절의 고유 어휘(대상·동작 명사)로도 grep할 것 — 헤딩·모드명만으로는 본문이 재서술한 절차가 안 잡힌다

## 2026-07-13 — README 현행화

### 사용자 문서에 내부 용어를 컨텍스트 없이 노출하지 말 것
- **문제:** README 각주를 "진행 모드 3종(하나씩/한꺼번에/알아서)"으로 재작성 — 스킬 내부 모드명을 그대로 노출해, 처음 읽는 독자가 무엇의 모드인지 문맥 파악 불가. 사용자 피드백으로 적발
- **교훈:** 사용자 문서(README·가이드)는 상황(독자가 언제 겪는가) → 기본 동작 → 전환 발화와 그 결과 순으로 풀어 쓸 것. 내부 용어(모드명·규범명·게이트명)는 정의 없이 쓰지 않는다 — 내부 문서(skills/)의 어휘를 복사하면 이 함정에 빠진다

## 2026-07-14 — persona-improvement

### 페르소나 발언을 개행 없는 벽 텍스트로 출력하지 말 것
- **문제:** 라운드 결과 정리에서 페르소나 발언을 문단 구분 없이 한 덩어리로 출력 — "이런 식으로 개행 없이 글을 쓰면 사람이 읽을 수가 없어" 피드백
- **교훈:** 페르소나 발언은 논점이 바뀔 때마다 빈 줄로 문단을 나누고, 병렬 나열은 불릿으로 쓸 것. 서브에이전트 원문이 문단을 갖췄더라도 본체가 정리하며 뭉개지 말 것. 어휘 수준(일상어)만이 아니라 문단 구조가 가독성의 절반이다

### 서브에이전트 main 오염 3차 재발 — 프롬프트 경고로는 안 막힌다 (구조적 확인 필요)
- **문제:** T11 haiku 구현자가 branch+pwd 이중 확인 지시·"다르면 BLOCKED 보고" 지시에도 main 체크아웃에 선편집·선커밋(2d64b33) 후 워크트리에 재커밋 — 세 릴리스 연속 재발. 구현자 리포트는 브랜치 확인을 통과했다고 허위 보고
- **교훈:** 경량 모델 태스크는 프롬프트 경고를 신뢰하지 말 것. 컨트롤러가 각 태스크 승인 직후 `git -C [main]` log를 상시 확인하고(이번에 감지 성공), 최종 검증만이 아니라 태스크 단위로 main 무오염을 게이트할 것. 근본 대안 검토 후보: 경량 모델 디스패치에서 절대 경로 Edit만 허용하는 지시 대신 워크트리 격리 실행(isolation) 사용

## 2026-07-16 — grounded-output

### 원문 유지 규범 확정 당일, 본체가 중계 압축으로 재위반
- **문제:** 국면 3 판정 3건을 화면에 옮기며 "길다"는 이유로 가이드라인 목록을 슬래시(/) 한 줄로 압축 — 기존 TD 형식 규칙("줄바꿈 목록 필수, 슬래시 금지")과 같은 세션에서 확정한 "원문 유지·고쳐 쓰기 금지"를 동시에 위반. 사용자 정정으로 적발
- **교훈:** 길이 부담은 생산 규격(발언 상한)에서 해결하는 것이지 전달 단계의 압축으로 해결하지 않는다 — 중계가 길면 원문 그대로 두는 것이 규범이다. 줄바꿈 규칙은 산출물만이 아니라 중계·요약 문면에도 적용된다

### 주석 마커 이중화 금지
- **문제:** 본체 검증 주석에 `- ↳`로 불릿과 화살표를 겹쳐 사용 — 사용자가 어색함 지적
- **교훈:** 주석 줄 마커는 `↳` 하나만 쓴다 (불릿 없이 들여쓰기). 접두 태그(리스크 아이콘·[추측] 등)는 줄 첫머리에 모아 배치한다

### 법조문식 절 기호(§)를 사용자 대면 문면에서 쓰지 말 것
- **문제:** 대화 내내 "§7", "§8"로 절을 지칭 — 사용자가 기호의 뜻 자체를 물었고, "라벨 병기" 제안도 "일반 사람이 아는 표기라는 가정이 틀렸다"로 기각됨
- **교훈:** 사용자 대면 문면에서는 절 기호·전문 표기를 아예 쓰지 않는다 — "결정 규범 문서의 블라인드 라운드 절"처럼 문서 이름+절 이름을 말로 풀어 쓴다. 언어 규범에 조항 추가 대상 (grounded-output 개정 범위 편입)

### 규범 신설 스윕의 grep 스코프는 규범의 적용 범위 전체로 잡을 것
- **문제:** 절 기호(§) 금지 규범을 신설하면서 T0 grep 스코프를 4개 경로(brainstorming·context-handling·commands·README)로 한정 — 규범의 실제 적용 범위(사용자 대면 문면 전체)에 있던 completion-protocol.md·orchestrator SKILL.md의 사용자 대면 리터럴 2건이 사각에 남아 최종 브랜치 리뷰에서 적발
- **교훈:** 새 규범의 스윕 스코프는 "지금 고치는 파일 목록"이 아니라 "규범이 적용되는 표면 전체"(references/ 포함 skills/ 전부 + 사용자 문서)로 잡는다. 스코프를 좁힐 때는 좁힌 근거를 인벤토리에 명시한다

### 내부 용어 노출 금지는 문서만이 아니라 대화 문면에도 적용된다

### 판단할 수 있는 것을 메뉴로 만들어 사용자에게 넘기지 말 것
- **문제:** 세 번 연속 같은 지적을 받음. ① "여덟 곳 중 몇은 멀쩡할 수도 있다"고 써 놓고 안 열어 본 채 범위를 물음 ② 파일을 열어 본 뒤에는 그 분류를 "맞습니까"로 물었는데, 사용자가 대조할 수단이 없는 것을 확인 요청으로 냄 ③ 화면 설계에서도 네 갈래 메뉴를 그대로 두고 설명만 얹으려 함. 사용자 정정: "너가 파악한게 맞는지를 물어야지 애초에 사용자 의견만 들으려고하고 있잖아. 지금 중간이 없이 극단적으로 질문만 하는 상황이야"
- **교훈:** 결정을 내기 전에 **먼저 판정한다.** 그리고 판정 결과와 근거를 내밀고 "그대로 진행 / 다르게 본다"를 묻는다 — 백지 메뉴를 내밀지 않는다. 기계적 기준: **💡 추천을 쓸 수 있으면 이미 답을 아는 것이므로 판정형으로 낸다.** 추천을 못 쓰는 것만 메뉴형이다. 확인을 요청할 때는 사용자가 실제로 대조할 수 있는 것만 물어야 한다 — 내가 파일을 읽어 만든 분류는 내 산출물이지 확인 대상이 아니다

### 규범을 강등할 때는 그 규범이 보호하려던 것이 무엇인지 먼저 확인할 것
- **문제:** 계획 단계에서 REQ-006("고르면: 줄은 사용자가 겪는 차이를 말한다")을 통과 검사에서 작성 지침으로 강등. 근거는 "셀 수 있게 뒤집으면 지금 잘 도는 로컬 템플릿이 실패로 잡힌다"였는데, 배포 첫 사용에서 사용자가 불편을 겪은 화면이 정확히 그 로컬 템플릿이었다
- **교훈:** "기존 것이 걸린다"는 강등 사유가 아니라 **그 기존 것을 고쳐야 한다는 신호**일 수 있다. 강등하기 전에 걸릴 대상을 실제로 열어 보고, 걸리는 것이 결함인지 오탐인지 판정할 것. 열어 보지 않고 "파급 범위를 모른다"로 강등하면, 모르는 채로 보호한 것이 나중에 문제가 된다

## 2026-08-27 — decision-verdict

### "쉬운 말"에 독자 기준선이 없으면 어휘가 망가진다
- **문제:** 언어 규범 첫 줄이 "초보자도 읽는 일상어"였다. 그 결과 개발자 사용자에게 갈래 이름을 "새 기능 만들기"·"코드 다듬기"로 지어 냈고, 화면 문장에 "요구 사항을 캔다"·"돌던 것이 안 도는"·"처음부터 짚기" 같은 비유어를 넣었다. 사용자 정정: "지금보니까 용어와 설명 때문에 더 헷갈리네", "결국 단어 선택과 설명에 문제가 있는거같아", "그렇다고 완전 비 개발자에게 설명하듯 하니 글이 읽히지 않더라고"
- **교훈:** 어휘 규범은 **독자를 먼저 정하고 시작한다.** dev-workflow의 기준선은 **주니어와 시니어 사이의 개발자**다. 그 사람이 아는 표준 용어(리팩터링·스택 트레이스·의존성)는 그대로 쓰고, 모를 수 있는 말(이 저장소·도메인 안에서만 통하는 용어)만 푼다. "쉽게 쓴다"를 "쉬운 낱말로 바꿔 쓴다"로 읽으면 매번 새 비유어를 지어내게 되고, 그건 리터럴 스윕으로 안 잡힌다 — 사용자가 실물을 보고 짚어야만 잡힌다

### 코드에 그대로 적히는 이름은 번역하지 않는다
- **문제:** 다른 프로젝트에서 `Assignment`를 "배정", `AssignmentGroup`을 "배정 묶음", `entry_key`를 "입장 확인값", `ReleaseTickets`를 "되돌리기"로 옮겨 적어 사용자가 무엇을 가리키는지 알 수 없게 만들었다. 사용자 정정: "이거 기능을 말할때나 전문 용어를 말할때는 번역하지말고 그대로 단어를 사용해줘"
- **교훈:** 함수·타입·필드·설정 키, 외부 라이브러리와 플랫폼의 기능 이름, API 이름은 **원문 그대로** 쓴다. 처음 나오는 자리에서만 괄호로 뜻을 짧게 붙인다 — **풀이는 병기이지 대체가 아니다.** 사용자가 그 이름으로 코드를 검색해야 하므로, 번역한 순간 그 문장은 코드와 이어지지 않는다

### 화면 폭에 맞춰 문장을 끊지 않는다
- **문제:** 결정 화면을 대화에 옮길 때 문장을 78자쯤에서 손으로 접었다. 사용자 정정: "한가지 불필요한 개행이 너무 많아. 화면에 맞게 문장을 일부러 개행하지 않아도 될거 같아"
- **교훈:** 줄바꿈은 문단과 불릿의 경계에서만 한다. 줄을 어디서 접을지는 읽는 쪽 화면이 정한다. 템플릿 파일 안의 예시 문장을 손으로 접어 두면 그 모양이 그대로 학습되므로, 템플릿의 자리표시자부터 한 줄로 둔다

### 규범 이름이 규범의 적용 범위를 오해하게 만든다
- **문제:** 「초심자 구조 기본값」이 정하는 것은 구조(배경 한 줄·선택지별 결과·추천)인데, 이름의 "초심자"가 어휘 기준까지 정하는 것처럼 읽혔다. 같은 절 안에 "업종 특화 어휘는 풀이를 붙이는 대신 일상어로 **대체**한다"가 있어 번역 습관을 굳혔다
- **교훈:** 규범 이름은 그 규범이 **실제로 정하는 것**만 가리켜야 한다. 「설명 구조 기본값」으로 개명하고, 대체 조항을 병기 조항으로 바꿨다. 규범 둘이 반대말을 하면 나중 사람은 자기에게 편한 쪽을 고른다

### 결정인데 열린 질문으로 흘려보냈다 — 질문 트랙에 갈림 게이트가 없었다
- **문제:** 인터뷰에서 "카테고리 번호를 서비스 안에서만 유일하게 둘까요, 아니면 저장소 전체에서 같은 번호를 쓸까요?"를 `❓ 질문 2/4` 개방형으로 냈다. 답은 둘 중 하나로 닫혀 있고 설계 문서에 남는 규약인데도 번호 선택지·결과 줄·💡 추천이 없었다. 배경에 저장소 조사 결과까지 이미 들어 있어 결정 박스로 낼 근거가 충분했다. 사용자 정정: "질문시에 선택지를 넘버링해주지 않고 있는데 이거 의도된건가?"
- **원인:** 갈림 기준은 있었으나(`decision-flow.md`의 결정 정의, `brainstorming/SKILL.md`의 괄호 곁말) **실행할 단계가 아니었다.** 질문은 페르소나 서브에이전트가 "질문을 2~3개 생성하라"로 만들고 본체가 그대로 내보내는데, 만들어진 것이 결정인지 가리는 자리가 그 경로에 없었다. 「내보내기 전 검사」는 탐색적 질문을 통째로 적용 밖에 두어 아무것도 안 걸렸다
- **교훈:** 규범을 곁말(괄호·"~는 ~를 따른다")로 두면 실행되지 않는다. **세는 단계로 만들어 경로에 박아야 한다.** 「조립 전 갈림」 둘을 질문 규칙에 신설했다 — ① 답이 산출물에 기록되는가(→ 결정 박스) ② 답의 후보를 셀 수 있는가(→ 번호 선택지). 둘 다 기계 판정이고 주관 술어를 쓰지 않는다. 서브에이전트가 만든 산출물을 그대로 내보내는 경로에는 항상 내보내는 쪽의 가림 단계가 필요하다

### 결정의 원인을 인용 안에 묻고, 되물음에는 설명만 늘렸다
- **문제:** peach 서버 ID 상한 결정에서 「이 결정이 다루는 문제」 칸에 "받은 번호를 어느 범위까지 통과시킬지 정합니다"라고만 썼다. 실제 원인인 `int32` 상한(2147483647)은 확인된 사실 칸의 세 항목 중 하나로, 그것도 템플릿 주석 인용 안에 묻혔다. 사용자가 세 번 되물었고 그때마다 박스는 그대로 둔 채 위에 설명만 길게 붙였다. 사용자 정정: "질문에 가장 중요한 부분이 잘 보이지 않는 곳에 넣어놓고 자꾸 설명을 빙빙 돌리고 있어"
- **원인:** 문제 칸 규격이 "왜 지금 정하는지 + 앞선 결정과의 연결"만 요구했다. 시점과 순서는 있는데 **선택지가 갈리는 물리적 이유를 요구하는 칸이 없었다.** 「내보내기 전 검사」 셋도 선택지 낱말·결과 줄·선택지 대상만 보아서 원인이 묻혔는지는 아무도 안 셌다
- **교훈:** 원인은 셀 수 있다 — **"확인된 사실 칸에서 지우면 선택지 하나가 무의미해지는 항목"이 원인이다.** 지워도 선택지가 그대로 성립하면 배경이다. 이 판정에는 주관 술어가 안 들어간다. 검사 4번으로 신설했다.
  되물음에 대한 규칙도 함께 넣었다 — **설명을 덧붙여 같은 박스를 다시 내지 않는다.** 되물음은 원인이 칸 밖에 있다는 신호이므로 문제 칸을 다시 쓰고 박스를 재조립한다. 두 번째 되물음이면 원인 후보 자체를 바꾼다. 박스 위에 문단을 쌓는 것은 재조립이 아니다

### 우리가 지어낸 이름을 사용자 화면에 그대로 썼다 — "갈래"
- **문제:** `new-feature`·`spec-change`·`refactor`·`defect`를 묶어 부르는 말로 "갈래"를 쓰고 12개 파일 83곳에 박았다. 사용자 정정: "갈래 라는 말 자체가 힘들어. 갈래는 도대체 뭘 말하는지 모르잖아. 목적이 없어." 화면에는 이름 하나(`요구 사항 변경`)만 나가서 오래 안 들켰는데, 새 화면 문장을 쓰는 순간 샜다
- **교훈:** **내부에서 부르는 이름이 화면으로 새는 통로다.** 사용자 문면만 고치면 다음에 또 샌다 — 내부 이름 자체를 사용자가 아는 말로 짓는다. `action:` 앞머리 키와 `actions.md` 파일 이름은 코드에 적히는 이름이라 그대로 두고, 한국어 용어만 「작업 방향」으로 바꿨다.
  치환할 때 조사가 깨진다 — "갈래"는 모음, "방향"은 자음으로 끝나 는/은·를/을·가/이·와/과·로/으로가 전부 뒤집힌다. 기계 치환 뒤 조사 교정을 반드시 한 번 더 돌린다

### 분류를 확인받으려면 분류표를 함께 보여야 한다
- **문제:** 작업 방향 확인 화면이 짚은 이름 하나와 근거만 냈다. 그 이름이 넷 중 하나라는 사실도, 나머지 셋이 뭔지도 화면에 없어서 처음 쓰는 사람은 대조할 수단이 없었다. 근거 세 줄은 전부 "이미 있다 + 달라진다"로 같은 말이었고, 정작 리팩터링을 지우는 근거는 둘째 줄 중간을 스쳤다
- **교훈:** 앞선 릴리스에서 넷을 **선택지로** 늘어놓아 실패했다고 해서 넷을 **안 보이는 것**이 답은 아니었다. 두 실패는 다르다 — 그때는 사용자가 분류표를 채워야 했고, 이번에는 대조할 표가 없었다. 답은 **지도형**이다: 후보를 모두 보이되 고르게 하지 않고 짚은 자리를 `▶`로 표시한다.
  근거 줄은 **가장 가까운 다른 후보를 지운다.** 짚은 것이 맞다고만 말하는 줄은 근거가 아니다. 「내보내기 전 검사」 4번의 지우기 판정을 판정형 근거 줄에도 걸었다 — 근거가 맨 앞에 있다는 것과 판정을 가른다는 것은 다르다

### 목표·비목표가 낡아도 아무도 안 봤다 — 판별문이 크리티컬에만 걸려 있었다
- **문제:** 개발 중 이슈 대응은 §10 변경 이력에 쌓이는데, 그것이 §2(목표와 비목표)를 뒤집어도 §2를 고치라고 요구하는 자리가 없었다. 목표·비목표를 정면으로 묻는 판별문은 orchestrator 「크리티컬 경로」에만 있고, 경량 사이클의 갱신 지시는 `§4/§6 등`이라 §2를 안 짚으며, document-consolidation의 섹션별 매핑 표에는 §2가 소스로도 대상으로도 없었다
- **증거:** 이 저장소에서 실제로 일어났다 — `decision-verdict.md` 9장 남은 위험에 "비목표의 근거 문장 자체는 다음 사이클에서 다시 써야 한다"가 남아 있다. 낡은 걸 알면서 미룰 수 있었던 이유는 고치라고 요구하는 자리가 없었기 때문이다
- **교훈:** **어떤 절이 낡는지는 "누가 그 절을 읽고 대조하는가"로 정해진다.** 매핑 표에 없는 절은 통합이 손대지 않고, 판별문이 특정 심각도에만 걸리면 그 아래는 통과한다. document-consolidation 실행 절차에 「§2 대조」를 3단계로 신설했다 — §10 이력 전체를 훑어 §2 문장이 지금 읽어서 거짓인지 세고, 어긋나면 갱신안을 내 확인을 받는다.
  **판정 시점은 이슈마다가 아니라 마무리다.** 한 이슈가 §2를 뒤집는 일은 드물고 여러 이슈가 쌓여서 밀어내는 것이라, 쌓인 것을 한 번에 보는 자리가 판정이 가장 정확하다 — 작업 방향 확인을 국면 0이 아니라 시드 직후에 둔 것과 같은 이유다.
  §2만 확인을 받는다 — 다른 절은 조용히 갱신해도 되지만 목표·비목표는 이 기능이 무엇인지를 정하는 절이라, 승인 없이 바꾸면 사용자가 동의한 적 없는 기능이 된다

### 없던 개념에 비유로 이름을 붙였다 — "좌표계"
- **문제:** 팀 번호를 `team_info`와 `TeamVacancies` 양쪽에서 같은 기준으로 매겨야 한다는 것을 "좌표계"라고 불렀다. 시드의 Goal·Constraints·Open Questions에 그 말이 들어갔고, 사용자가 "여기서 말하는 좌표계가 뭐야?"로 적발. 뜻을 다시 설명해야 했고 결국 시드를 다시 썼다
- **원인:** 언어 규범의 조항이 `그 개발자가 이미 아는 표준 용어는 그대로 쓴다 — ... 비유어를 지어내지 않는다`라서 **대체할 원래 용어가 있어야 발동한다.** "좌표계"는 바꿔치기가 아니라 이름이 없던 개념에 새 이름을 붙인 것이라 이 조항에도, 「저장소 고유 용어 풀이」에도, 「코드 이름 번역 금지」에도 안 걸렸다
- **교훈:** 이름을 짓는 것과 용어를 바꾸는 것은 다른 실수이고, 규범은 둘 다 막아야 한다. 판정은 셀 수 있다 — **반복해서 무언가를 가리키는 명사가 저장소에서 0건이고 개발 표준 용어도 아니면 지어낸 이름이다.**
  **풀이를 붙여도 쓰지 않는다** — 풀이가 필요하다는 것이 그 이름이 일을 안 한다는 증거다. 코드에 있는 이름으로 부르거나(여기서는 "`TeamVacancies` 키의 시작 번호") 설명 문장으로 편다. 새 이름이 정말 필요하면 이름 짓는 것 자체를 결정으로 내 승인을 받는다.
  시드에 특히 강하게 건다 — 승인되면 이후 모든 문서가 그 말을 물려받는 자리다

### 「관측한다」를 선택지로 내지 않는다 — 그건 「안 고친다」다
- **문제:** 재현이 안 되는 렌더링 결함에 대해 "그대로 두고 관측한다"를 1번 선택지로 냈다. 사용자 정정: "관측하게 뭐야? 뭘 관측해야하는거야?" 실제로 관측할 장치가 없었다 — 다시 깨지는 것을 알아채는 유일한 경로가 사용자가 화면을 보고 말해 주는 것이었다
- **전례:** [✔ `intake-routing.md` 비목표] "이 저장소의 기존 관측 루프 3건이 전부 미실행 상태로 방치돼 있다". 셋이 죽어 있는 것을 알면서 네 번째를 냈다
- **교훈:** 선택지 이름은 **그것을 고르면 실제로 무슨 일이 벌어지는가**로 짓는다. **누가·무엇을·언제 보는지가 없으면 「관측」이 아니라 「안 함」이고, 그렇게 써야 사용자가 제대로 고를 수 있다.** 이름이 실질을 숨기면 「내보내기 전 검사」 어느 항목에도 안 걸린다 — 결과 줄은 그럴듯하게 쓸 수 있기 때문이다.
  관측을 정말 하려면 무엇을 세고 어디에 적는지를 선택지 안에 적는다. 못 적으면 그 선택지는 「안 고친다」다
