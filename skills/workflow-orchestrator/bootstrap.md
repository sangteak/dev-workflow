## 발동 규칙 (필수)

워크플로우 의도 신호가 있는 요청을 처리하기 **전에** 반드시 `dev-workflow:workflow-orchestrator` 스킬을 invoke하라:

- 단계 키워드: 브레인스토밍·아이디어·기획 / 계획·설계 / 구현·개발 / 리뷰·검토 / 마무리·wrap up
- 착수 신호: 결함·문제 제기(버그·에러·안 나와·재현·고쳐줘) / 사양 변경 / 리팩터링·리팩토링 — **답이 이미 정해진 요청이 아니면 발동한다**
- `docs/design/` 하위 설계 산출물을 만들거나 이어가는 작업
- 진행 중 작업 재개 발화 ("이어서 하자", "계속하자", "복구해줘")

답이 이미 정해진 요청(사실 조회, 지시가 구체적인 단순 수정, 조사)은 워크플로우를 발동하지 않고 일반 응답한다. **무엇을 고칠지 아직 정해지지 않은 문제 제기는 답이 정해진 요청이 아니다** — 발동한다.
이후 대화에서 신호가 등장하면 **그 시점에** invoke한다. 판단이 애매하면 invoke하는 쪽을 택한다.
이미 이 세션에서 orchestrator가 활성이면(워크플로우 단계 진행 중, /compact 복원 포함) 재invoke하지 않고 진행 중 흐름을 계속한다.

## 단계 감지 요약 (상세는 orchestrator 스킬)

| 단계 | 신호 | 위임 |
|---|---|---|
| BRAINSTORM | 브레인스토밍·아이디어·방향 탐색 | brainstorming 스킬 (페르소나 사용) |
| PLAN | 계획·설계, `[기능명].md` 존재 + plan.md 없음 | plan-stage 스킬 (페르소나 사용) |
| DEVELOP | 구현·개발, plan.md 존재 | `actions.md` 작업 방향 블록의 「넘길 곳」 (폴백: Superpowers subagent-driven-development) |
| REVIEW | 리뷰·검토·QA | Superpowers requesting-code-review + Evaluator QA |
| COMPLETION | 마무리·완료·wrap up, /dev-workflow:finish | Completion Protocol (문서 취합 → 커밋 제안) |

> 작업 방향(`action:`)에 따라 각 단계의 깊이와 위임 목적지가 다르다. 어느 칸을 채워야 하는지는 `[플러그인 루트]/skills/workflow-orchestrator/references/actions.md`의 작업 방향 블록이 정한다.

## 세션 불변식 (워크플로우 단계 진행 중 항상 적용)

- 사용자 입력 요청에 AskUserQuestion 도구를 사용하지 않는다 (BRAINSTORM/PLAN/COMPLETION 한정) — 텍스트 번호 목록으로 질문한다. **질문을 내보내기 전에 답의 후보를 적어 본다 — 두 줄 이상 적히면 그 줄들이 번호 선택지가 되고, 한 줄 이하일 때만 개방형으로 둔다. 번호 선택지가 붙은 질문에는 0번 탈출구를 늘 붙인다**
- 페르소나 발언에는 항상 이모지 접두사를 붙이고, 사용자 대면 문면의 독자는 주니어와 시니어 사이의 개발자다 — 표준 용어는 그대로 · 저장소에 없는 낱말로 개념에 이름 붙이지 않기 · 코드에 적히는 이름 번역 금지 · 저장소 고유 용어와 식별자는 즉석 풀이(병기) — 번호만 쓰지 않고 무엇인지 한 조각을 함께 적는다 — 내보내기 전에 풀이 없는 것을 센다 — 도메인 명사는 세션 목록 또는 코드 자리에서 1건 이상 · 줄임말 금지 · 문단 개행 · 화면 폭에 맞춘 임의 줄바꿈 금지 (원본: decision-flow 3부 「언어 규범」)
- 커밋·푸시는 Completion Protocol에서만 — 각각 별도 확인 (푸시는 원격 공개라 분리 승인)
- 결정 요청은 한 번에 하나씩 — 노출된 선택지에만 답할 수 있고, 모드 전환("다 보여줘"/"알아서")은 명시적 요청으로만 (위임·번복 의도는 수용 — 응답 주권)
- 선택 대신 되물음이 오면 설명을 덧붙이지 않고 박스를 다시 조립한다 — 빠진 것의 갈래(풀이·실물·근거·결과 줄·흐름)가 다시 쓸 자리를 정하고, 제목에 `(다시 씀: 왜 문제인지)`처럼 다시 쓴 것을 붙인다. 둘째 되물음은 다른 갈래로, 셋째는 자유 응답을 받아 그 말로 다시 조립한다. 위임 단계라도 번호 선택지를 낸 화면이면 같다 (상세: decision-flow 3부 「되물음 재조립」 — 신호·자리·접미 문구는 그 표가 정본이다)
- 결정 요청 형식 상세는 `[플러그인 루트]/skills/workflow-orchestrator/decision-flow.md`를 Read하여 따른다 (폴백: `📌 결정 요청 : [제목]` + '이 결정이 다루는 문제'(이 이름표는 제 줄에 쓰고 본문은 다음 줄부터 · 선택지가 갈리는 원인 먼저) 1-2문장(라운드·조사 선행 시 확인된 사실/확인 못 한 것/토론 요지 칸 — 빈 칸은 "없음") + 번호 선택지(결과 1줄 병기) + `💡 추천` 줄 · 헤더 `📋 확정 N/M` · 자가 응답 금지 · 라운드·조사 선행 시 박스 앞에 짧은 설명 문단(이름표 없이 — 왜·무엇을·어떻게·언제는 담을 내용의 점검표) · 내보내기 전 검사 다섯 — ① 선택지 이름의 낱말과 박스 본문의 식별자 중, 이 박스와 앞 블록에서 풀이 없는 것이나 코드 자리에서 1건 이상 안 나오는 번역어가 있으면 고쳐 쓰기(모든 박스) ② 결과 줄에 문제 칸이나 확인된 사실 칸의 명사를 하나 이상 넣기(메뉴형 자리 전부) ③ 선택지 이름에도 그 명사를 하나 이상 넣기(작업 방향 확인과 단계 감지 둘만) ④ 지우면 선택지 하나가 무의미해지는 항목(=원인)을 「이 결정이 다루는 문제」 칸에 담기 — 판정형에서는 지워도 판정이 서는 근거 줄을 빼기(전 자리) ⑤ 박스와 같은 메시지에 선택지로 답할 수 없는 물음·통보가 있으면 빼고 다음 차례에 별도 결정으로 내기(선택지를 내는 모든 박스) · 판정형으로 지정된 자리(작업 방향 확인·재협의)는 판정 한 줄 + 확인 태그 근거 + 「진행」·「의견 있음」 · 작업 방향 확인은 지도형이라 후보 넷을 모두 내고 짚은 자리에 `▶`를 붙이며 근거 줄이 가장 가까운 다른 방향을 지운다)
- DEVELOP 중 계획 밖 결함 수정은 이슈 카드 선행 — 이슈는 한 번에 하나 (상세: orchestrator 「Issue Lifecycle」)
- 마무리 신호(위 COMPLETION 어휘 또는 `<completion-signal>` 주입)를 받으면 자체 판단으로 작업을 정리하지 않는다 — orchestrator를 invoke해 Completion Protocol로 라우팅한다
