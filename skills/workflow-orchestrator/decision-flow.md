# 결정 요청의 단계적 흐름 (Decision Flow SSOT)

> dev-workflow 플러그인에서 사용자 결정을 요청할 때 따르는 단일 SSOT.
> 적용 스킬: workflow-orchestrator, brainstorming, plan-stage, document-consolidation(§8 적용 예외 조항의 규율을 받음), merge-to-domain(결정 박스와 설명 블록만 적용 — dry-run 목록이 브리핑 대체 로컬 템플릿, 헤더·대기열은 적용 예외) — 본 파일을 참조로 명시한 스킬.
> 그 외 스킬의 확인·질문은 orchestrator의 Input Format Rules를 따른다.

**적용 범위:** 본 규칙은 dev-workflow가 직접 진행하는 구간(BRAINSTORM/PLAN/COMPLETION, 세션 시작, 컨텍스트 관리)의 사용자 대면 출력에 적용된다. Superpowers 위임 단계(DEVELOP/REVIEW)와 merge-to-domain·design-summary의 기존 출력 형식은 별개다. 단 3부 「언어 규범」 펜스는 이 범위와 별개로 모든 사용자 대면 문면·페르소나 발언에 적용된다.
**게이트 실효성 정비와의 관계:** 게이트 정비는 확인의 존폐·등급(이 확인이 필요한가)을 다루고, 본 규칙은 묶음 내부의 제시 방식(남은 확인을 어떻게 보여주나)을 다룬다 — 확인 횟수를 줄이는 변경과 충돌하지 않는다.
**문서 구성:** 1부(결정 규칙)·2부(질문 규칙)는 3부(공통 형식·언어)의 스켈레톤과 언어 규범을 결정·질문에 각각 적용한 것이다 — 형식·언어의 원본은 3부가 유일하다. 3부는 「언어 규범」(원본 펜스)과 「결정·질문 구조 규범」으로 구성된다.

**재서술 지점 목록 (검증 기준 — 누락 0):** 이 문서의 규범을 **다시 적어 놓은** 자리는 아래 열이다. 규범의 뜻을 바꾸는 작업은 같은 차례에 이 열을 함께 고친다. 원본을 가리키기만 하는 줄(예: brainstorming SKILL.md의 "형식은 decision-flow.md가 정의한다")은 재서술이 아니므로 목록에 넣지 않는다.

1. `skills/workflow-orchestrator/bootstrap.md` — 세션 시작 상시 주입본의 결정 요청 형식 폴백과 언어 요약
2. `skills/workflow-orchestrator/SKILL.md` — 「결정 요청 폴백 형식」의 스켈레톤 전문·결정 정의·설명 블록·등급·언어 최소 요건·질문 규칙 요약, 그리고 이슈 경량 사이클의 언어 줄
3. `skills/workflow-orchestrator/references/grounding.md` — 등급 경계 사례와 로컬 템플릿 면제
4. `skills/workflow-orchestrator/references/actions.md` — 소비 계약의 적용 경로 목록
5. `skills/brainstorming/SKILL.md` — 성격 승인 화면의 읽기 실패 폴백, 페르소나 발언 공통 규칙의 언어 요약, 국면 1·2의 질문 규칙 요약
6. `skills/brainstorming/references/templates.md` — 「성격 승인 화면」 실물, 공통 조립 규칙의 언어 최소 요건, 「핵심 질문」 출력 형식
7. `skills/plan-stage/SKILL.md` — 「재협의 선택지」 실물
8. `skills/merge-to-domain/SKILL.md` — 결정 박스와 설명 블록의 적용 범위 조항
9. `skills/context-handling/SKILL.md` — HANDOFF 「결정 흐름 상태」 섹션의 보존 항목 목록
10. `README.md` — 사용자 문서의 결정 화면 설명
11. `skills/design-summary/SKILL.md` — 「서술 규칙」의 용어 조항

이 목록은 **바닥이지 천장이 아니다.** 규범 변경 스윕은 매번 새로 돌리고, 목록에 없는 자리를 찾으면 그 릴리스에서 이 목록에 더한다. 절차 원본은 development-principles의 「규범 변경 스윕」이다.

## 1. 메타 원칙

**결정의 정의:** 결정 = 산출물(phase 파일·설계 문서·plan.md)에 기록될, 선택지 2개 이상 중의 선택.
- 단순 진행/승인 게이트("계속할까요?", Yes/No 확인)는 결정이 아니다 — orchestrator Input Format Rules의 무박스 형식을 따르고 카운터(M)에 포함하지 않는다
- 답이 설계 결정으로 기록되지 않는 탐색적 질문은 본 SSOT의 「질문 규칙」(2부)을 따르고, 답이 결정으로 기록되는 질문만 본 절의 "하나씩" 규칙을 따른다

**질문 기본값 — 하나씩:** 모델이 결정을 요청할 때는 의존성 루트부터 한 번에 하나씩 묻는다.
- 유일한 예외: 두 결정이 상호 순환 의존이어서(한쪽 답이 다른 쪽 답 없이 성립 불가) 분리 결정이 불가능한 경우에만 하나의 종합 질문으로 묶는다
- 주제 유사성만으로 묶는 클러스터 그룹핑은 금지한다 (사후 합리화 위험). 위 순환 의존 예외와는 다른 개념이다

**응답 주권 — 사용자 응답이 형식을 이긴다:** 위임·즉시 번복·모드 전환 등 명시적 의도를 수용한다 (응답 가능 범위와 다중 값 처리는 §4를 따른다 — 노출된 선택지에만 답할 수 있으며, 모드 전환은 명시적 요청으로만). 이미 답한 항목을 재질문하지 않는다.

**충돌 처리:** 모델/페르소나가 자체 감지한 충돌은 재논의 대기열(§5)에 추가하고 현재 결정을 마무리한다. 사용자가 명시적으로 번복/재논의를 요청하면 대기열을 거치지 않고 현재 결정을 일시 중단 후 즉시 처리하며, 처리 후 "진행 중이던 [결정명]으로 돌아갑니다"로 복귀한다.

**자가 응답 금지 — 번호 선택지를 출력한 메시지는 그 선택을 기다리며 끝나야 한다.** 모델이 대신 선택하고 진행하지 않는다. 선택지를 출력한 뒤 같은 메시지에서 다른 게이트로 잇지 않는다.
**선택지 생략 화이트리스트:** 사용자 메시지에 아래 표현(또는 그 명백한 변형)이 있을 때만, 해당 지점의 선택지 출력을 생략하고 그 지시대로 진행할 수 있다: "그냥 기본값으로" / "알아서 해줘" / "당연히 [X]로" / "네가 정해줘" / "아무거나". 목록에 없는 표현은 생략 근거가 아니다 — 의도가 명확해 보여도 선택지를 출력한다. 생략 후 사용자가 이의를 제기하면 재논의 대기열을 거치지 않고 즉시 해당 선택지를 소급 제시한다.

## 2. 출력 형식

### 한 줄 헤더 (B) — 이벤트 기반 표시

```
📋 확정 N/M · 진행 중: [현재 결정명] · 재논의 K건
```

- 기호 고정 (1의미 1기호): N=확정 결정 수, M=현재 국면 전체 결정 수(확정+미확정), K=재논의 대기열 건수. K=0이면 '재논의' 필드를 생략한다
- 표시 시점: (a) 결정을 요청하는 응답 (b) 결정이 확정/추가/제외되어 카운터가 변한 응답 (c) 조사·무관 주제로 흐름을 벗어났다가 복귀하는 첫 응답 — 이 세 경우에만 표시하고 그 외 응답에는 생략한다
- 헤더는 이 한 가지 형식만 사용한다 (압축형 없음)
- 재산출: N/M/K는 대화 기억이 아니라 사전 브리핑(F) 목록 + 이후 편입/제외 이력의 재집계로 산출한다. 값이 불확실해지면 브리핑 목록·확정 이력과 대조해 재산출한다
- 국면의 마지막 결정 확정 + 재논의 대기열 처리 완료 후에는 헤더를 붙이지 않는다

### 사전 브리핑 (F) — 미결 결정 2개 이상 식별 시

발동은 시점이 아니라 이벤트다. 국면 시작 시든 토론 라운드 종료 후든, 미결 결정이 2개 이상 식별되면 그 시점에 출력한다.

**사전 브리핑(F)은 첫 결정 박스와 같은 메시지에서, 설명 블록과 결정 박스 묶음의 바로 앞에 출력한다.** 페르소나 토론·서브에이전트 라운드가 선행되는 경우 브리핑도 라운드 종료 후로 미룬다. 라운드 진행 중에는 응답을 기다린다는 문면을 출력하지 않는다 — 입력을 여는 문면은 실제로 응답을 기다리는 시점에만 쓴다.

브리핑 문면:
```
📋 결정 항목 [M]개 — 의존성 루트부터 정렬:
1. [결정명] — [정렬 근거 1줄] ← 루트
2. [결정명] — [정렬 근거 1줄]

첫 번째 항목부터 하나씩 여쭙습니다. (정렬 이의는 알려주세요 · 한 번에 보시려면 "다 보여줘" · 위임은 "알아서")
```

- 결정이 1개면 브리핑을 생략하고 즉시 결정 박스(D)로 요청한다
- 결정이 0개(페르소나 간 합의 도출)면 결정 박스 자체를 생략한다
- 미결 항목이 8개 이상이면 푸터에 한 줄을 추가한다: "항목이 많습니다 — "다 보여줘"(전체 보기) 또는 "알아서" 위임을 권합니다." 별도의 분할 메타 질문은 하지 않는다

### 결정 박스 (D)

3부 §「공통 형식·언어」의 출력 스켈레톤을 그대로 따른다.

- 박스 안 선택지 표기(번호만·문자 금지·0번 조건)는 orchestrator Input Format Rules를 그대로 따른다 — 스켈레톤·헤더·브리핑은 본 SSOT 담당, 선택지 표기는 Input Format Rules 담당
- `0. 기타`는 자유 입력 탈출구가 필요한 경우에만 포함한다 (Yes/No 성격의 결정에는 붙이지 않는다)
- 페르소나 합의 기반 추천이 있으면 `💡 추천: [번호]` 줄 + 사유 줄로 표기한다 (3부 실물 예시 참조)
- 스켈레톤에는 항상 현재 결정 1건만 담는다 — 여러 결정을 하나에 넣지 않는다

## 3. 진행 모드 (3종)

| 모드 | 발동 | 동작 |
|---|---|---|
| **하나씩** (기본) | 별도 발화 없음 | 의존성 루트부터 결정 박스(D)로 한 항목씩 |
| **한꺼번에** | 사용자 발화 또는 브리핑에 일괄 응답 (정확 문구 예: "다 보여줘", "한꺼번에") | 미확정 전 항목을 번호 목록으로 제시 (항목당 선택지 + 페르소나 추천·근거 1줄). 명확한 답은 전부 잠정 확정 후 헤더 반영, 페르소나 검증이 필요한 항목만 '답변을 전제로 한 검증 토론'으로 축약 실행 |
| **알아서** | 위임 발화 ("알아서 해", "추천대로") | 남은 항목을 페르소나 합의 추천값으로 일괄 확정하고 확정 요약표(항목·선택·근거 1줄)를 1회 출력 후 "수정할 항목 번호를 알려주세요. 없으면 진행합니다"로 역확인. 사용자가 일부 항목을 수정하면 해당 항목만 확정 변경을 한 줄 고지하고 진행한다 (요약표 재출력 없음) |

- 모드는 현재 국면에서만 유효하다. 국면 전환·세션 복구(/compact, resume) 시 기본값(하나씩)으로 리셋된다. 모드는 HANDOFF에 저장하지 않는다
- 어떤 모드든 확정 결과와 근거는 동일하게 phase 파일/설계 문서에 기록한다
- '한꺼번에' 모드의 검증 토론은 피드백 루프 규칙(최대 3라운드)을 따르되, 사용자 답변에 반박이 있는 항목만 다룬다

## 4. 사용자 응답 처리 (응답 주권의 구체 규칙)

**응답 가능 범위 — 선택지까지 노출된 항목에만 답할 수 있다.** 제목만 나열된 브리핑·목차는 응답 대상이 아니다.
- **하나씩 모드:** 쉼표·줄바꿈으로 구분된 다중 값 응답이 오면 첫 값만 현재 항목에 반영하고 나머지는 버린 뒤 한 줄로 안내한다: `첫 답만 반영했습니다. 나머지는 다음 항목에서 다시 여쭙겠습니다. (한 번에 보시려면 "다 보여줘")`
- **한꺼번에 모드:** 모든 항목의 선택지가 노출되어 있으므로 일괄 응답을 항목별로 매핑해 수용한다 (기존 규칙 유지).
- 선답·일괄 응답을 모드 전환으로 자동 해석하지 않는다 — 모드 전환은 명시적 요청("다 보여줘"/"한꺼번에"/"알아서")으로만 일어난다.

- **역질문** ("1번과 2번 차이가 뭐야?"): 답변 후 현재 결정을 요약형(결정명 + 남은 선택지 번호)으로 재제시한다. 박스 전체를 재출력하지 않는다
- **위임 발화**: '알아서' 모드로 전환한다 (§3)
- **무관한 새 주제**: 헤더 없이 응답하고(카운터·대기열 불변) 말미에 "진행 중이던 [결정명]으로 돌아갑니다"를 붙인다. 결정 재제시는 같은 응답에서 하지 않고, 다음 응답에서 §2 표시 시점 (c)에 따라 헤더와 함께 재제시한다. 새 발화에서 신규 결정이 파생되면 M에 합산하지 않고 "지금 다룰까요, 현재 결정 흐름 후에 다룰까요?"를 먼저 묻는다 (이 질문을 담은 응답에는 복귀 고지를 붙이지 않는다) — "지금"이면 현재 결정을 일시 중단하고 즉시 처리한 뒤 복귀하며(§1 충돌 처리의 사용자 명시 요청과 동일 경로), "후에"면 브리핑 목록 말미에 추가하고 M에 합산한다 (말미 고정 — 이후 배치 재조정은 '진행 중 목록 변경' 규칙을 따른다)

### 진행 중 목록 변경

- **신규 결정 발견**: 신규 항목과 기존 항목 간 의존성을 한 줄로 기술하고, 갱신된 잔여 순서를 한 줄로 통보한다 ("신규 [D]를 [B] 앞에 배치 — 이의 있으면 알려주세요"). 별도 응답을 기다리지 않고 다음 결정 요청을 이어간다 (경량 이의 게이트). 의존성이 불명확하거나 동률이면 브리핑 목록 말미에 발견 순서로 추가한다
- **목록 재조정**: 결정 확정 직후 남은 항목의 유효성을 재평가한다. 앞선 결정으로 무의미해진 항목은 "[X] 결정으로 [항목명]은 불필요해져 목록에서 제외합니다" 한 줄 고지와 함께 제거하고 M을 갱신한다. 고지 없는 조용한 제거를 금지한다

## 5. 재논의 대기열

- **추가**: 충돌 감지 시 즉시 처리하지 않고 대기열에 추가하며, 추가 시점에 "🔄 대기열 추가: [항목명] — [충돌 요지 한 줄]"로 1회 고지한다. 이후에는 헤더의 K 카운터로만 유지한다
- **등재 대상**: 대기열에는 재검토가 필요한 기확정(또는 합의 통과) 항목을 등재한다. 현재 진행 중인 결정은 그대로 확정 절차를 밟는다 — 진행 중 결정 자체를 대기열에 넣지 않는다
- **항목 이름**: 결정 박스 없이 통과된 페르소나 합의 사항도 대기열·phase 파일 기록 시 식별 가능한 이름을 부여한다 (번복 시 참조용)
- **자연 해소**: 후속 결정으로 충돌의 전제가 소멸하면 항목을 제거하고, 추가 고지와 동일한 패턴으로 본문에 1회 고지한다: "🔄 대기열 해소: [항목명] — [사유 한 줄]" (헤더는 §2 단일 형식을 유지하며 K만 감소)
- **노출 시점 (단일)**: 현재 국면의 모든 결정 완료 시 일괄 노출한다. 미노출 상태로 국면 전환이 시도되는 경우에 한해 phase 파일(또는 해당 국면 산출물) 작성 직전이 최종 안전망이다. 이미 노출·처리된 대기열을 다시 노출하지 않는다

노출 형식:

```
📌 결정 요청 : 재논의 대기열 처리 ([K]건)

**이 결정이 다루는 문제:** 확정된 결정과 충돌해 보류해 둔 항목입니다. 기각해도 사라지지 않고 phase 파일에 기록이 남습니다.

- [항목명] — 충돌 상대: [결정명] · 사유: [1줄]

1. 모두 재논의 — 고르면: 항목별로 페르소나 토론을 다시 엽니다
2. 일부만 (번호 지정) — 고르면: 지정한 것만 재논의, 나머지는 기각 기록
3. 모두 기각 — 고르면: 전부 기각으로 기록하고 진행
```

- 위 노출 형식은 고정 템플릿이며, 대기열 처리는 국면의 모든 결정이 끝난 뒤에 나와 직전에 라운드나 조사가 없다 — 「결정·질문 구조 규범」의 등급 판정에서 "없었다"에 해당하므로 설명 블록 대상이 아니다
- **재편입**: '모두 재논의' 또는 '일부만' 선택 시 해당 항목을 미확정 결정으로 카운터(M)에 재편입하고, 재편입 항목이 2개 이상이면 사전 브리핑(F)부터 재실행한다. '일부만'에서 지정되지 않은 잔여 항목은 기각으로 처리한다 — 조용히 소멸시키지 않는다
- **기각**: '모두 기각' 선택 시(또는 '일부만'의 미지정 잔여 항목) 대기열을 비운다. 기각 사실은 phase 파일에 한 줄로 기록한다

## 6. 상태 보존 (세션 이관·컨텍스트 압축)

결정 흐름 상태(카운터·정렬 순서·대기열 전문·진행 중 결정명)는 대화 컨텍스트에만 존재하므로 압축/이관 시 유실될 수 있다. 아래 시점에 파일로 보존한다:

- **HANDOFF 저장(save) 시**: 결정 흐름이 활성이면 context-handling의 "결정 흐름 상태" 섹션에 기록한다. 재논의 대기열은 항목 전문(항목명 + 충돌 요지)을 기록한다 — 건수만 쓰지 않는다. 블라인드 첫 루프 완료 여부(국면 단위)도 함께 기록한다. 결정 박스 등급 판정 근거(직전 라운드·조사 유무)·발언 재실행 이력(라운드별 상한 소진)·[✔] 최초 고지 완료 여부·**판정형 자리의 판정 오답 횟수**와 **메뉴형 자리의 되물음 횟수**도 함께 기록한다 — 유실 시 보수적으로 재판정한다 (등급은 4칸 쪽, 고지는 재고지 쪽, 오답 횟수는 0 쪽 — 두 번 틀림 판정을 넘겨짚어 메뉴형으로 떨어뜨리지 않는다).
- **/compact 직전**: 재논의 대기열이 비어있지 않으면, 먼저 일괄 노출 처리하거나 HANDOFF에 저장한 후 압축한다
- **복구(resume) 시**: HANDOFF에 "결정 흐름 상태" 섹션이 있으면 헤더(N/M/K)·미확정 잔여 순서·재논의 대기열을 복원한 후 진행 중이던 결정부터 이어간다. 내용을 기억으로 재구성하지 않는다
- 결정마다 파일에 기록하지 않는다 — 기록 시점은 save·/compact 직전·국면 완료(phase 파일 반영) 세 경우로 한정한다 (resume은 기록이 아니라 복원이다)

## 7. 페르소나 피드백 출력 형식 (brainstorming 통합)

### 에이전트 태그 (서브에이전트 실행 시)

서브에이전트로 실행된 페르소나에 에이전트명을 표시한다:
- `[Socratic]` — Socratic Interviewer 사고 제약으로 생성된 발언
- `[Contrarian]` — Contrarian 사고 제약으로 생성된 발언 (비판 담당)
- 서브에이전트가 아닌 발언에는 태그를 붙이지 않는다
- 라운드 헤더에도 현재 사용 중인 에이전트를 표시한다

### 결정 요청 분리 규칙

- 합의 시: `**합의:**` + 결론 요약
- 미합의 시: `**미합의:**` + 쟁점 요약
- 결정 항목이 없으면 (페르소나 간 합의 도출된 경우) 결정 요청 블록을 생략한다
- "이 두 가지에 대해" 같은 대명사 참조를 사용하지 않는다 — 각 결정 항목은 명시적 이름으로 가리킨다

### 원문 전달 원칙 (전 라운드 공통)

서브에이전트 발언은 본체가 고쳐 쓰지 않고 원문 그대로 나열한다 — 압축·재요약·문장 재구성 금지. 길이 통제는 발언 생산 규격(3부 「검증 규범」의 펜스)이 담당하며, 전달 단계의 압축으로 해결하지 않는다. 블라인드/대화형 라운드 구분 없이 적용된다 (구 "재구성 책임 + 블라인드 예외" 구도는 본 원칙으로 대체).

본체의 책임은 두 가지다: ① 에이전트 태그 부착과 검증 주석(↳ — 3부 「검증 규범」) ② 결정 요청 재구성 — 발언 원문에 포함된 결정 요청 문구는 그대로 노출하지 않고, 결정 요청은 본체가 결정 박스로 별도 조립한다 (발언 문면 자체는 무수정).

**규격 위반 처리:** 발언이 생산 규격을 어기면 (판정은 셀 수 있는 조건만 — 전치 태그 유무·불릿 개수·결론 줄 유무) 고쳐 쓰지 않고 재실행한다 — 1회 한정, 진행 표시·재위반 제외 고지 문구는 references/grounding.md 실물을 쓴다.

### 블라인드 라운드 공통 절차 (원본)

블라인드 절차의 원본은 본 절이 유일하다 — 각 스킬은 파라미터(대상 라운드·페르소나 목록·발췌 내용·판정 기준)만 서술한다.

- **실행:** 대상 라운드의 전원 페르소나를 병렬 서브에이전트로 동시 투입한다 — 상호 발언 미노출. 별도 비판 담당은 두지 않는다 (비판 로빈은 2라운드부터)
- **프롬프트 구성:** [사고 제약 원문 (스킬이 지정한 경우만)] + [도메인 페르소나 정의] + [발췌] + [언어 규범 펜스 전문 — "--- 언어 규범 ---" 구획] + [생산 규격 펜스 전문 — "--- 생산 규격 ---" 구획 (3부 「검증 규범」 원본 복제 — 정형 형식·출처 의무 포함)] + [전제 반박 의무: "이 전제가 틀렸다면 네 도메인에서 무엇이 무너지는지 1개 이상"] + [출력 제약: 결정 요청 문구 금지]
- **발췌 규격 (조립 재량 금지):** 사용자 발화는 원문 인용 + 시드는 해당 절 원문 + 기확정 결정 목록("재론 금지" 제약 명시). 이전 라운드 발언 전문은 넣지 않는다
- **생략 센티널:** 보탤 것이 프롬프트에 이미 적힌 내용의 재진술뿐이면 정확히 `[의견 없음 — 사유 1줄]`만 반환한다 — 취합 시 나열에서 제외한다
- **취합:** 발언 원문을 그대로 나열한다 — 본체 재요약 금지. 나열 순서는 라운드·주제마다 회전하며, 회전 상태를 잃으면 임의 순서로 재시작한다 (유실은 실패가 아니다)
- **해석:** 블라인드 일치도 독립 검증이 아니라 약한 신호다 — 같은 모델이 같은 발췌를 읽으므로 오류가 함께 나는 경향은 남는다. 언어 규범이 안 지켜진 발언을 발견하면 tasks/lessons.md에 기록한다 (자기개선 루프).
- **상태:** "국면당 첫 루프 완료 여부"는 HANDOFF 「결정 흐름 상태」에 기록한다. 불확실해지면 블라인드로 간주해 재실행한다 (오판 비용 상한: 병렬 1라운드분)
- **끄기:** 사용자가 블라인드 생략을 요청하면 해당 라운드를 기존 대화형 경로로 라우팅한다. 세션 최초 블라인드 실행 시 1회 고지: "⏳ 블라인드 라운드 — 전원 독립 의견을 병렬 수집합니다 (대기 약 1~2분 · 원치 않으면 말씀하세요)"

## 8. 적용 범위와 우선순위

- 결정이 0개면 결정 박스를 생략한다 (합의 도출됨)
- 결정이 1개면 결정 박스(D)로 즉시 요청한다 (사전 브리핑은 생략한다)
- 결정이 2개 이상이면 사전 브리핑(F) + 의존성 루트부터 하나씩 요청한다 (사용자가 모드를 바꾸면 §3 진행 모드를 따른다)
- 미결 결정 8개 이상이면 브리핑 푸터에 모드 권장 문구를 추가한다 (§2)

**로컬 템플릿 우선:** 스킬 본문 또는 본문이 지시하는 references/ 템플릿에 구체 출력 템플릿이 있는 결정 지점(예: brainstorming 시드 확인·Simplifier 스코프 정리·국면 0 카테고리 선택, plan-stage 재협의 선택지, document-consolidation 단계 확인)은 해당 템플릿을 문서 그대로 출력한다 — 임의로 D 박스로 재조립하지 않는다. D 박스는 템플릿이 지정되지 않은 결정 요청에 적용한다. **다만 「내보내기 전 검사」는 각 항목의 「적용 자리」를 따른다** — 로컬 템플릿이라는 이유로 통째로 면제되지 않는다. 선택지 낱말 검사는 모든 박스에, 결과 줄 검사는 메뉴형 자리 전부에 걸린다. 템플릿을 그대로 출력한다는 것은 모양을 재조립하지 않는다는 뜻이지, 그 안의 결과 줄을 이번 요청에 맞게 쓰지 않아도 된다는 뜻이 아니다. 면제되는 것은 설명 블록 요구뿐이다.

**적용 예외:**
- 확인 지점이 이미 순차 구조(한 시점에 질문 1건)로 고정된 스킬(예: document-consolidation)은 브리핑(F)·헤더(B)·대기열을 생략한다
- 결정 흐름이 활성이지 않은 순수 정보 제공/조사 출력에는 적용하지 않는다. 결정 흐름 활성 중의 조사·토론 응답에는 §2 표시 시점 규칙을 따른다
- 프로젝트 규칙(`.claude/rules/`)이 출력 형식과 충돌하면: 출력 형식(박스·장식 문자)은 프로젝트 규칙을 우선하되, 순차 결정 원칙(한 번에 하나)과 헤더가 담는 정보(확정/미확정/재논의 카운트)는 텍스트 형태로 유지한다

## 9. 국면(Phase) 대응표

| 스킬 | 국면 단위 | 대기열 안전망 노출 시점 |
|---|---|---|
| brainstorming | 국면 0~4 각각 | 해당 phase 파일 작성 직전 |
| plan-stage | Step 1~4 전체가 하나의 국면 | Superpowers writing-plans 핸드오프 직전 |
| plan-stage 재계획 진입 | 진입 1회가 하나의 국면 (Step 1~4 국면 규칙 재사용) | writing-plans 핸드오프 직전 |
| 기타 적용 스킬 | 해당 스킬 실행 1회 | 스킬 종료 직전 |

> §8 적용 예외에 해당하는 스킬(예: document-consolidation)은 결정 흐름이 활성화되지 않으므로 본 표의 대상이 아니다.

## 질문 규칙 (탐색적 질문 트랙)

질문은 답이 산출물에 결정으로 기록되지 않는 탐색적 입력 요청이다 (결정과의 층위 차이: 질문의 답은 대화로 가볍게 무를 수 있고, 결정은 §5 재논의 절차를 거친다).

- **기본 하나씩:** 질문은 한 번에 하나만 노출한다. 이 규칙은 종전의 "한 번에 최대 2개 질문" 규칙을 대체한다
- **진행 표시:** `❓ 질문 [N]/[M] : [제목]` — M(전체 수)은 질문 수집(페르소나 전원 소집·병합)이 끝난 뒤 확정한다. 질문 카운터와 결정 카운터(📋 확정 N/M)는 별개로 센다 — 합산하지 않는다
- **조립 전 갈림 (기계 판정 — 주관 술어 금지):** 질문을 내보내기 전에 둘을 센다. "중요한 질문인가"로 판정하지 않는다
  1. **답이 산출물(phase 파일·설계 문서·plan.md)에 기록되는가.** 기록되면 탐색적 질문이 아니라 결정이다 (1부 「메타 원칙」의 결정 정의). `❓ 질문` 대신 결정 박스(D)로 조립하고, 질문 카운터 M에서 빼 결정 카운터로 옮긴다 — 조용히 빼지 않고 한 줄로 고지한다 ("[제목]은 답이 설계 문서에 남는 항목이라 결정으로 올립니다"). 1부 「진행 중 목록 변경」의 조용한 제거 금지가 그대로 걸린다
  2. **답의 후보를 셀 수 있는가.** 두세 개로 셀 수 있으면 닫힌 집합이므로 번호 선택지를 붙인다 (3부 「출력 스켈레톤」의 질문형). 못 세면 개방형 그대로 둔다
  - 이 판정은 조립 **전에** 한다 — 어느 쪽이냐가 화면 모양 자체를 바꾸므로, 조립을 끝낸 뒤 발견하면 검사가 아니라 재작성이 된다 (판정형 「조립 전 조건」과 같은 이유)
  - 페르소나 서브에이전트가 생성한 질문에도 그대로 건다. 생성 프롬프트는 "질문을 만들라"고만 지시하므로, 만들어진 것이 결정인지 가리는 일은 내보내는 쪽 몫이다
- **형식:** 3부 스켈레톤의 질문형을 따른다. 첫 질문에만 진행 안내 1줄을 붙인다: `(답하기 어려우면 "모름"/"넘어가" — 조사로 넘깁니다 · 전체 보기: "다 보여줘" · 위임: "알아서")`
- **라우팅:** "모름"/"넘어가" 응답은 해당 질문을 조사 대기열에 적재하고 다음 질문으로 진행한다. 질문 순회가 끝나면 적재분을 일괄 조사한다 (미답변 조사 절차)
- **잠정성:** 질문의 답은 잠정이며 국면 전환 시점에 확정된다. 답의 전제가 이후 토론으로 무효화되면 해당 답을 재확인한다
- **응답 범위·모드 전환:** §4와 동일 — 노출된 질문에만 답할 수 있고, 다중 값 응답은 첫 값만 반영하며, 모드 전환은 명시적 요청으로만
- **세션 이관:** HANDOFF 저장 시 질문 진행 상태를 별도 줄로 기록한다: `❓ 질문 진행: [N]/[M] · 국면: [국면명]` + 미답변 질문 목록 (결정 마커와 혼용하지 않는다)

## 공통 형식·언어 (결정·질문 공통 — 형식·언어의 원본)

### 언어 규범 (원본)

아래 펜스가 언어 규범의 유일한 원본이다. 페르소나 서브에이전트 프롬프트에는 이 펜스를 "--- 언어 규범 ---" 구획으로 전문 복제한다 (복제는 실행 시점 행위 — 문서 사본을 만들지 않는다).

```
📣 언어 규범 — 모든 사용자 대면 문면과 페르소나 발언에 적용 (본 파일의 결정 흐름 적용 범위와 별개):
- **읽는 사람은 주니어와 시니어 사이의 개발자다** — 이것이 모든 어휘 판단의 기준선이다. 비개발자에게 설명하듯 쓰면 글이 늘어져 읽히지 않고, 시니어끼리 말하듯 쓰면 무슨 말인지 알 수 없다
- 그 개발자가 이미 아는 표준 용어는 그대로 쓴다 — 리팩터링·스택 트레이스·의존성 같은 말을 쉽게 바꾸려고 비유어를 지어내지 않는다 (예: "요구 사항을 캔다"가 아니라 "요구 사항을 정리한다")
- 그 개발자가 모를 수 있는 말, 곧 이 저장소·이 도메인·이 플러그인 안에서만 통하는 용어만 나온 자리에서 짧게 풀이한다 — 풀이는 병기이지 대체가 아니다. 줄임말은 쓰지 않되, 아래 줄의 코드 이름은 줄임말이라도 그대로 쓴다
- 코드에 그대로 적히는 이름은 번역하지 않는다 — 함수·타입·필드·설정 키, 외부 라이브러리와 플랫폼의 기능 이름, API 이름은 원문 그대로 쓰고, 처음 나오는 자리에서만 괄호로 뜻을 짧게 붙인다 (예: `Assignment`(OpenMatch가 티켓에 붙이는 접속 정보) — 이것을 "배정"으로 바꿔 쓰지 않는다)
- 한국어로 쓰되 현학적인 한자어는 피한다 — 어휘 수준을 낮추는 것이 아니라 문장을 곧게 쓰는 쪽이다
- 논점이 바뀔 때마다 빈 줄로 문단을 나누고, 병렬 나열은 불릿으로 쓴다
- 한 문장을 화면 폭에 맞춰 중간에서 끊지 않는다 — 줄바꿈은 문단과 불릿의 경계에서만 한다. 줄을 어디서 접을지는 읽는 쪽 화면이 정한다
- 절 기호(§) 같은 법조문식 표기를 쓰지 않는다 — 문서 이름과 절 이름을 말로 풀어 쓴다 (예: "결정 규범 문서의 블라인드 라운드 절")
- 목록·가이드라인을 슬래시(/)로 한 줄에 잇지 않는다 — 산출물만이 아니라 중계·요약 문면에도 적용된다 (길이 부담은 생산 규격이 해결한다 — 전달 압축 금지)
```

### 결정·질문 구조 규범

**판정형과 메뉴형 (갈림 — 설계 시점에 박는다):**

결정 요청에는 두 모양이 있다.

- **메뉴형** — 선택지를 늘어놓고 고르게 한다. 기본값이다
- **판정형** — 모델이 내린 판정과 그 근거를 먼저 보이고, 「그대로 진행」과 「고칠 게 있다」 둘로 받는다. 답을 이미 아는 자리에서 쓴다

갈림 기준은 **「근거를 댈 수 있나」**다 — 저장소나 대화에서 확인 태그(`[✔ 출처]`)를 붙일 수 있는 근거를 만들 수 있으면 판정형, 못 만들면 메뉴형이다.

**이 기준을 실행할 때마다 매기지 않는다.** 아래 다섯 자리에 값이 박혀 있고, 그 값을 그대로 쓴다.

| 자리 | 모양 |
|---|---|
| 「성격 승인 화면」 (`brainstorming/references/templates.md`) | 판정형 |
| 「재협의 선택지」 (`plan-stage/SKILL.md`) | 판정형 |
| 「Ambiguous 단계 감지」 (`workflow-orchestrator/SKILL.md`) | 메뉴형 |
| 재논의 대기열 노출 (본 문서 5부) | 메뉴형 |
| 일반 결정 박스 (아래 「출력 스켈레톤」) | 메뉴형 |

새 결정 지점을 만들 때는 이 표에 행을 더한다. 표에 없는 자리는 메뉴형으로 읽는다.

**판정형 출력 스켈레톤 (고정 — 이 모양 그대로):**

```
📌 확인 : [대상]을 [판정]으로 판단했습니다

- [✔ 출처] [그렇게 본 근거 1줄]
- [✔ 출처] [근거 1줄]

[그대로 진행하면 무엇이 달라지는가 — 다음에 무엇을 더 묻게 되는지, 또는 그 대상이 어떤 상태로 남는지를 쓴다. 만들어지는 파일 이름을 적지 않는다. 화면 폭에 맞춰 중간에서 끊지 않는다]

1. 그대로 진행
2. 고칠 게 있다
```

**조립 전 조건 (실행 시점 안전망):** 판정형으로 박힌 자리인데 「확인된 사실」에 해당하는 근거 줄에 확인 태그(`[✔ 출처]`)가 **한 줄도 없으면 메뉴형으로 조립한다.** 이 판정은 박스를 조립하기 **전에** 한다 — 판정형이냐 메뉴형이냐가 박스 모양 자체를 바꾸므로, 조립을 끝낸 뒤 아래 「내보내기 전 검사」에서 발견하면 되돌아가 처음부터 다시 조립하는 일이 되고 그것은 검사가 아니라 재작성이다.

**되묻기:** 「고칠 게 있다」를 받으면 근거를 다시 보이고 **자유 응답만 받는다** — 선택지 이름 목록을 붙이지 않는다. 받은 말을 값으로 옮기는 것은 모델 몫이고, 옮긴 결과를 다시 판정형으로 확인받는다. **판정이 두 번 틀리면 그 자리에서 메뉴형으로 넘어간다** — 두 번 틀렸다는 것은 근거가 틀렸다는 뜻이므로 횟수 상한이 아니라 이 조건이 멈춤을 만든다.

**메뉴형 되묻기:** 사용자가 선택 대신 되물으면("왜?"·"이해가 안 된다"·같은 취지) 설명을 덧붙여 같은 박스를 다시 내지 않는다. **박스를 다시 조립한다** — 「이 결정이 다루는 문제」 칸을 다시 쓰고 「내보내기 전 검사」 4번(원인)을 다시 센다. 되물음은 대개 원인이 그 칸 밖에 있다는 신호다. 박스 위에 문단을 쌓는 것은 재조립이 아니다.

**같은 결정에서 두 번째 되물음을 받으면 원인 후보를 바꾼다** — 첫 재조립에서 올린 항목이 원인이 아니었다는 뜻이므로, 다른 항목을 지워 보며 다시 센다. 위 판정형 「되묻기」와 짝을 이룬다 (그쪽은 판정이 두 번 틀리면 메뉴형으로 넘어간다).

이 되묻기는 1부 「응답 주권」의 "이미 답한 항목을 재질문하지 않는다"가 금지한 재질문이 **아니다.** 같은 결정의 판정을 갱신하는 것이라 새 결정 번호를 매기지 않고, 헤더의 확정 개수(N/M)도 움직이지 않는다.

**설명 블록 (결정 전용 — 박스 바로 앞):**

결정 박스 앞에 **짧은 문단**으로 설명을 쓴다. 사전 브리핑(F)이 있으면 브리핑 → 설명 블록 → 박스 순이다.

```
🧭 **설명**

[짧은 문단. 이름표를 붙이지 않는다.]
```

- **담을 내용의 점검표:** 왜 · 무엇을 · 어떻게 · 언제. **넷을 다 채우려 하지 않는다** — 그 결정에 필요한 것만 쓴다. 이 넷은 쓸 내용을 고르는 점검표이지 화면 모양이 아니다. 이름표를 붙여 항목으로 나누지 않는다
- **요구 시점:** 아래 「적용 등급」의 판정 질문을 그대로 쓴다 — "이 결정 직전에 페르소나 라운드 또는 조사가 있었는가?"가 "있었다"면 블록 필수, "없었다"면 생략. 등급과 별개로, 사용자가 더 풀어 달라고 하면 등급과 무관하게 낸다 (3부 「설명 구조 기본값」의 재설명 경로에 잇는다 — 새 어휘 목록을 만들지 않는다)
- **연결 한 줄을 두지 않는다** — 앞선 결정과의 연결은 박스 첫 칸이 담당한다. 블록은 문단이고 박스 첫 칸은 그 한 줄 요약이라 층이 다르다
- 고르는 데 영향을 주지 않는 내용은 쓰지 않는다 — 3부 「검증 규범」의 선별 침묵을 블록 전체로 넓힌 것이다 (그 규칙은 원래 확인 불가 항목에만 걸린다 — **범위 확대이지 재적용이 아니다**)
- **분량 상한을 두지 않는다.** 이름표를 뗀 자리에 새 상한을 만들지 않는다 — 분량을 세는 어떤 문장도 뜻 판정이 되어 「내보내기 전 검사」의 "주관 술어를 쓰지 않는다"와 부딪힌다. 상한 없이 가는 것의 부작용은 관측 항목이다

**출력 스켈레톤 (고정 — 이 모양 그대로):**

```
📌 결정 요청 : [결정명]

**이 결정이 다루는 문제:** [**선택지가 갈리는 원인 먼저** (아래 「내보내기 전 검사」 4번의 정의) + 왜 지금 정하는지 + 앞선 결정과의 연결]

**확인된 사실:**
- [✔ 출처] [사실 1줄]   (없으면 이 칸에 "없음"이라고 쓴다)

**확인 못 한 것:**
- [⚠️ 확인 불가] [결정에 영향을 주는 불확실 1줄]   (없으면 "없음")

**토론 요지:** [수렴/충돌 1~3줄]

1. [선택지] — 고르면: [결과 1줄]
2. [선택지] — 고르면: [결과 1줄]
0. [탈출 레이블] (자유 입력 탈출구 필요 시에만)

💡 추천: [번호]
[추천 사유 1줄]
```

**적용 등급 (기계 판정 — 주관 술어 금지):** 판정 질문은 하나다 — "이 결정 직전에 페르소나 라운드 또는 조사가 있었는가?"
- 있었다 → 4칸(문제·확인된 사실·확인 못 한 것·토론 요지) 상시. 내용 없는 칸은 생략하지 않고 "없음"이라고 쓴다 (칸의 부재와 확인의 부재를 구분하기 위해). 각 칸의 항목은 1줄 상한
- 없었다(표준 결정) → "이 결정이 다루는 문제" 칸만 필수, 나머지는 해당 이력(조사·앞선 토론)이 있는 칸만 추가
- 로컬 템플릿 결정·단순 승인 게이트 → 칸 구성은 기존 형식 그대로이고 **설명 블록은 면제**다 (본 문서 「로컬 템플릿 우선」·orchestrator Input Format Rules 관할). 「내보내기 전 검사」는 각 항목의 「적용 자리」를 따른다
경계 예시: ① 페르소나 라운드 종료 직후의 결정 → 4칸 ② 조사 없이 저장소 구조 대조만으로 묻는 결정 → 문제 칸+확인된 사실 칸 ③ 국면 0 카테고리 확정 → 로컬 템플릿 유지

**내보내기 전 검사 (본체 담당 — 박스를 조립한 뒤 화면에 올리기 전):**

아래 넷을 센다. 주관 술어를 쓰지 않는다. 근거 태그 유무는 여기서 세지 않는다 — 그것은 위 「조립 전 조건」이 조립 **전에** 본다.

**검사마다 적용 자리가 다르다.** 면제를 따로 모으지 않고 각 검사 옆에 적는다.

**칸이 없는 화면의 대조 상대:** 로컬 템플릿처럼 「이 결정이 다루는 문제」·「확인된 사실」이라는 이름표가 없는 화면에서는 **화면 첫 줄과 그 아래 상황을 적은 문단**이 그 두 칸을 대신한다. 아래 2번과 3번의 "칸에 나온 명사"는 그 자리에서 뽑는다. 대용할 자리조차 없으면 **사용자 발화에서 이번 일의 이름을 뽑아 화면 첫 줄에 넣고** 그것을 대조 상대로 삼는다 — 대조할 것이 없다는 이유로 검사를 건너뛰지 않는다.

1. **선택지 낱말** — 선택지 이름에 쓰인 낱말 중, 이 박스와 바로 앞 블록 본문에 한 번도 안 나오고 풀이도 안 붙은 말이 하나라도 있으면 실패
   - 풀이란 그 낱말의 뜻을 그 자리에서 푸는 문장을 말한다. 선택지의 "고르면:" 줄은 결과를 적는 자리이므로 풀이로 치지 않는다
   - "나온다"는 어간이 같으면 나온 것으로 센다 — 예를 들어 블록에 "받은 값"이 있으면 선택지의 "받아준다"는 나온 것이다
   - **판정형 자리는 이 검사의 대상이 아니다** — 선택지 이름이 「그대로 진행」·「고칠 게 있다」로 고정이라 박스 본문과 대조할 것이 없다. 판정 문장과 근거 줄이 그 자리를 대신한다 (3번의 같은 예외와 짝을 이룬다)

2. **결과 줄** — 선택지의 "고르면:" 줄에 「이 결정이 다루는 문제」 칸이나 「확인된 사실」 칸에 나온 명사가 하나도 안 들어 있으면 실패
   - **대조 상대는 이 두 칸이다.** "사용자가 겪는 차이인가"를 뜻으로 판정하지 않는다 — 그러면 주관 술어가 된다
   - 걸러내는 것은 워크플로우 절차만 적은 줄과 파일 이름·자료 구조 이름만 적은 줄이다. "고르면: 묻는 것이 기본 그대로입니다"는 걸리고 "고르면: 항목별로 페르소나 토론을 다시 엽니다"는 통과한다(문제 칸에 "항목"이 있다)
   - 명사 대조도 어간이 같으면 나온 것으로 센다 (1번과 같은 규칙)
   - **적용 자리:** 위 「판정형과 메뉴형」 표에서 **메뉴형**으로 박힌 자리 전부. 로컬 템플릿도 포함한다 — 결과 줄은 문장을 고쳐 쓰는 것뿐이라 화면 무게가 안 는다

3. **선택지 대상** — 선택지 **이름**에 「이 결정이 다루는 문제」 칸이나 「확인된 사실」 칸에 나온 명사가 하나도 안 들어 있으면 실패
   - 걸러내는 것은 어떤 요청에도 똑같이 쓸 수 있는 이름이다. "기능 추가"·"계획"은 걸리고 "매칭 진입 경로 새로 만들기"·"매칭 진입 계획 세우기"는 통과한다
   - **적용 자리:** 「성격 승인 화면」과 「Ambiguous 단계 감지」 **둘.** 나머지 메뉴형 자리는 이번 릴리스의 대상이 아니다 — 문제가 보고된 적이 없고, 범위를 다 열고 세다가 놓치는 실패를 이 저장소가 두 번 겪었다
   - 판정형 자리(성격 승인)는 선택지 이름이 「그대로 진행」·「고칠 게 있다」로 고정이므로, 대상은 선택지가 아니라 **판정 문장**에 들어간다. 근거를 못 만들어 메뉴형으로 떨어진 경우에만 선택지 이름을 센다

실패하면 채운다. 채울 재료가 없으면 조사한다. 조사하고도 못 채우면 「확인 못 한 것」 칸에 그 사실을 적고 진행한다 — **1회 한정** (본 문서 「원문 전달 원칙」의 재실행 1회 한정과 같은 모양). **설명을 못 한다는 이유로 묻기를 건너뛰지 않는다.**

**적용 밖 (검증 기준 — 누락 0):** ① 로컬 템플릿 결정 — **설명 블록 요구만 면제.** 검사는 각 항목의 「적용 자리」를 따른다 (본 문서 「로컬 템플릿 우선」) ② **선택지 없는** 탐색적 질문 (2부 「질문 규칙」 — 대조할 선택지가 없다). 번호 선택지가 붙은 질문은 1번(선택지 낱말)과 2번(결과 줄)의 대상이며, 대조 상대는 질문 제목과 「배경/힌트」다 (아래 「칸이 없는 화면의 대조 상대」) ③ 진행 모드 '한꺼번에'와 '알아서' (항목별로 박스를 내지 않는다) ④ 선택지 생략 화이트리스트가 발동한 지점 (박스 자체가 없다)

질문형 (첫 줄이 다르고, 💡 추천·0번 줄은 해당할 때만):

```
❓ 질문 [N]/[M] : [제목]

**배경:** [1-2문장]

1. [선택지] — 고르면: [결과 1줄]
2. [선택지] — 고르면: [결과 1줄]
```

탐색적 질문은 대개 개방형이다 — 번호 선택지 없이 `**배경/힌트:**` 뒤에 질문 본문으로 끝나도 스켈레톤 충족으로 본다. 번호 선택지는 답이 닫힌 집합일 때만 붙인다.

4. **원인** — 「확인된 사실」 칸의 항목 중 **지우면 선택지 하나가 무의미해지는 항목**이 「이 결정이 다루는 문제」 칸에 안 들어 있으면 실패
   - **지워 보는 것으로 센다** — "중요한가"로 판정하지 않는다. 지워도 선택지가 그대로 성립하면 그 항목은 배경이지 원인이 아니다
   - 실패하면 그 항목을 문제 칸으로 올린다. 「확인된 사실」 칸의 출처 줄은 그대로 두고, 문제 칸이 그 내용을 말로 풀어 담는다
   - 원인이 둘이면 둘 다 올린다. 문제 칸의 1~2문장 규격보다 이 검사가 우선한다 — 원인을 줄여 문장 수를 맞추지 않는다
   - 「확인된 사실」 칸이 없는 화면은 지울 항목이 없으므로 통과한다 — 없는 칸을 만들어 내지 않는다
   - **적용 자리:** 메뉴형 자리 전부. 판정형은 판정 문장과 근거 줄이 이미 박스 맨 앞이라 대상이 아니다

**금지:** 정렬이 필요한 괘선(┌ │ └)과 대화 UI의 마크다운 표. 허용: `──` 대시 구분선, 디렉토리 트리, 산출물(설계 문서·phase 파일) 내부의 표.

**설명 구조 기본값:** 사용자에게 묻거나 결과를 공유하는 모든 문면의 기본 — ① 짧은 배경(왜 묻는지/무엇이 문제인지) ② 선택지마다 "고르면: [결과 1줄]" ③ 💡 추천과 사유는 별도 줄 ④ 비유는 도움이 될 때 (의무 아님). 어휘·문단은 「언어 규범」 펜스가 원본이다. 사용자가 더 풀어달라고 하면 배경→비유→선택지별 의미→추천 순으로 다시 설명한다. 코드에 적히는 이름과 개발 표준 용어는 이 조항의 대상이 아니다 — 「언어 규범」 펜스가 원문 유지를 정한다. 그 밖의 업종 특화 어휘(특정 분야 종사자만 아는 말)는 그 자리에 풀이를 병기한다.

**ID 라벨 병기:** 문서 내부 ID(REQ-001 등)를 대화에서 단독으로 지칭하지 않는다 — 항상 짧은 라벨을 병기한다. 예: `REQ-001(공통 스켈레톤)`.

**공유 출력 형식:** 요약·결과 공유는 이모지를 붙인 구분 헤더 아래 `-` 항목으로 나열하고 구분 사이는 빈 줄로 띄운다. 항목을 `/`로 한 줄에 이어 붙이지 않는다. 페르소나 발언은 `[이모지] [이름]:` 줄 다음 개행 후 내용을 쓴다. 그룹 경계가 흐리면 `──` 구분선을 쓴다.

### 검증 규범 (근거 있는 출력)

**출처 3종:** 계산·논리(그 자리에서 셈이 되는 것) / 프로젝트 내 코드·문서 / 외부 공식 문서(웹). 이 3종 외는 출처가 아니다.

**전치 태그 — 항목 첫머리 고정:** `[✔ 출처]` 확인됨 · `[⚠️ 확인 불가]` 확인 수단 없음 · `[✘ 반증 — 출처]` 확인 결과 틀림 · `[추측]` 발언자 자백. 무표시 단정 서술을 화면에 올리지 않는다. 확인 불가 항목은 결정에 영향을 주는 것만 표시하고, 영향 없는 추측은 출력하지 않는다 (선별 침묵).

**근거 첨부 의무:** [✔]에는 대조 가능한 증거를 병기한다 — 프로젝트 내 출처는 파일 경로+행 번호 또는 한 줄 인용, 외부 출처는 출처 주소+해당 대목 원문 인용. 증거 없는 [✔]는 [⚠️ 확인 불가]로 강등하고 강등 사실을 1줄 고지한다.

**본체 관문:** 화면에 올라가는 주장의 검증 책임은 본체(화면을 조립하는 메인 컨텍스트)에 있다 — 서브에이전트의 태그는 1차 필터일 뿐 신뢰 지점이 아니다.
- 재확인 대상: 미확인([추측]/무표시)인데 추천(💡) 사유 또는 선택지의 성패 근거로 쓰인 주장 — 본체가 3출처로 직접 확인한다. 외부 문서 확인만 조사 워커에 위임할 수 있다 (워커도 근거 첨부 의무 — 인용 없는 보고는 미확인 취급)
- [✔] 주장은 첨부 증거와 주장의 대조만 한다
- 규약: 화면에 도달한 [✔] = 본체 관문 통과. 세션에서 [✔]가 처음 화면에 나올 때 1회 고지한다 (문구 실물: references/grounding.md)
- 관문 수행 주체는 본체 고정 — 하위 모델 워커로 내리지 않는다. 네트워크 차단 환경에서는 외부 출처 축 전체가 [⚠️ 확인 불가]로 강등된다

**본체 검증 주석 (↳):** 본체는 발언 원문을 고쳐 쓰지 않고, 필요할 때만 해당 항목 아래 들여쓴 `↳` 한 줄을 단다 (불릿 기호와 겹쳐 쓰지 않는다). 다는 경우는 3가지뿐 — 반증([✘]) · 확인 불가 승격([⚠️]) · 재확인으로 새 사실을 보탠 경우.

**발언 생산 규격 (원본 펜스):** 아래 펜스를 의견·비판·판정을 반환하는 페르소나 서브에이전트 프롬프트에 "--- 생산 규격 ---" 구획으로 전문 복제한다 (적용 경로: brainstorming 확장 토론의 비판 담당 · 블라인드 라운드 · plan-stage 판정 — 질문 생성 프롬프트에는 적용하지 않는다). 언어 규범 펜스와 동일한 실행 시점 복제 — 문서 사본을 만들지 않는다.

```
📐 발언 생산 규격:
- 결론 1줄 + 근거 불릿 3개 이내 + 전제 반박 1개. 근거가 3개 미만이면 부족 사유 1줄로 대체한다 (3은 상한이지 채움 목표가 아니다)
- 근거마다 첫머리에 전치 태그 — 확인했으면 [✔ 출처]와 증거(파일 경로·행 또는 인용), 확인 못 했으면 [추측]
- 사용자를 향한 결정 요청 문구를 포함하지 않는다
```

경계 사례·고지 문구 실물·워커 반환 규격·소급 반증 형식은 `references/grounding.md`를 Read하여 따른다 (Read 실패 폴백: 위 집행 문장만으로 동작 — 고지 문구는 취지 유지 즉석 작문 허용).

**실물 예시 (규범이 적용된 결정 요청 — 이 예시는 「있었다」 등급이다. 「없었다」 등급에서는 블록 없이 "이 결정이 다루는 문제" 칸만 쓴다):**

🧭 **설명**

질문을 하나씩 내는 도중에 사용자가 앞질러 답하면, 그 답을 어디에 넣을지가 정해져 있지 않습니다. 걸리는 것은 질문 순회 절차와 응답 처리 규칙 둘입니다. 응답이 오면 처리 규칙이 먼저 받은 값을 세고, 그다음 순회가 다음 질문을 냅니다.

📌 결정 요청 : 앞질러 답하기 처리

**이 결정이 다루는 문제:** 질문을 하나씩 내면, 사용자가 "1,1,1"처럼 아직 나오지 않은 질문에 미리 답하는 경우가 생깁니다.

**확인된 사실:**
- [✔ 본 문서 2부 「질문 규칙」] 질문은 한 번에 하나만 노출한다 — 아직 안 나온 질문에는 답할 자리가 없다

**확인 못 한 것:**
- [⚠️ 확인 불가] 앞질러 답한 사람이 뒤 질문의 내용을 짐작하고 답했는지

**토론 요지:** 없음

1. 받아준다 — 고르면: 앞질러 온 답을 질문 순서대로 배정하고 배정 결과표로 확인
2. 답 하나만 받는다 — 고르면: 나머지는 순서대로 다시 질문
