## 결정 사항

### 결정 1 — 스코프 축소 (제안대로 전부 축소)

**선택:** Simplifier 제안 7건을 모두 "이번에 하지 않는 것"으로 옮긴다.

**축소 목록과 이유**

1. **superpowers 수정안의 타당성을 누가 따지는가** → 다음 기능
   - 뼈대 원문이 "진입 **전** 단계"인데 이건 진출 **후**의 일 (위치가 반대편)
   - 비목표에 "원인 지목·수정안 작성"이 이미 있고 그 판정 대상도 같은 자리
   - 제약 2(새로 만드는 것은 구간 하나뿐)를 정면으로 깬다
   - superpowers 4단계에 "증거 없는 완료 선언 금지"가 이미 딸려 온다
   - **다만 이 질문이 나온 뿌리("즉답이 정말 면밀히 검토된 결과인지 알 수 없다")는 진짜 불만이므로 다음 기능 후보로 이름을 남긴다**
2. **되돌아가는 문 두 개를 자동으로 갈라주는 장치** → 미룸 (문 자체는 유지)
   - 사람이 "이건 사양 문제로 보입니다, 브레인스토밍으로 갈까요" 한 줄이면 결과가 같다
   - 자동 분기는 판정이 틀렸을 때의 위험을 새로 짊어진다
   - 첫 판은 안내 한 줄 + 사람의 수동 전환
   - 정정: Simplifier가 "사용자 뼈대 원문에 없다"고 했으나 사용자가 앞선 발화에서 직접 언급했다. 문 자체는 유지하고 자동화만 미룬다
3. **고친 뒤 커밋과 코드 리뷰** → 미룸 (끝점 밖)
4. **첫 판부터 어휘 감지 훅 배선 네 곳** → 미룸
   - 슬래시 명령 또는 발동 규칙 한 줄만으로 첫 판이 열린다
   - 사용자가 쓴 말은 "**간단한** 브레인스토밍"
5. **검증 규범을 공통 파일 차원에서 확장** → 미룸 (결정 3에서 국지 규칙으로 대체)
6. **전문가 세트 파일이 없을 때의 갈래** → 미룸 (첫 사용처에는 세트가 있음)
7. **조사 중 발견된 별개 문제 2건** → 스코프 밖
   - superpowers 버전 표기 어긋남 (문서 6.1.1 / 실제 6.2.0)
   - superpowers 스킬 폴더에 규범 아닌 파일 5개가 섞여 배포됨

### 결정 2 — 발동 방식: 발동 규칙 문서에 한 줄 추가

**선택:** `bootstrap.md`의 발동 규칙에 "결함·오류 신고인데 증상이 구체적이지 않은 경우"를 추가하고,
같은 문서의 "단순 수정, 조사는 워크플로우를 발동하지 않는다"(12행)를
"원인이 분명하면 그냥 고친다"는 취지로 정교하게 다듬는다.

**근거**
- [확인됨] 발동 규칙은 이미 `bootstrap.md` 문서에 있고 세션 시작 훅(`hooks/session-start:17`)이 본문을 통째로 주입한다. 새 스크립트가 필요 없다
- [확인됨] 지금 목록(`bootstrap.md:8`)에 결함 계열 어휘가 하나도 없다
- 처음 겪은 문제가 "아무것도 안 켜졌다"이므로, 그것을 못 고치는 문(슬래시 명령 단독)은 첫 판의 문으로 부적절하다
- 헛발동은 실제로 써 보며 문장을 조이면 되는 문제라 되돌리기 쉽다

**기각한 대안**
- 슬래시 명령 하나만 — 부르는 걸 잊으면 지금과 똑같다
- 둘 다 — 첫 판에서 만들 것이 둘로 늘고, 슬래시 명령 확인에 Claude Code 재시작이 필요하다

**⚠️ 관측 후 확장 (사용자 지시)**
> "이렇게 했는데 잘 지켜지지 않으면 3번과 같이 작업해야 해."

즉 발동 규칙 한 줄만으로 실제 발동이 안정적이지 않으면 **슬래시 명령을 병행(3번)하는 것으로 확장한다.**
이 확장은 관측 결과에 따라 발동하는 후속 작업이다.

### 결정 3 — 실행 기록을 이 구간 안에서만 근거로 인정

**선택:** 이 기능의 스킬 문서에 "실행 기록도 근거로 본다"를 한 줄 적는다.
표시는 기존 방식 그대로 쓰되 출처 자리에 무엇을 봤는지 적는다 (예: `[✔ 서버 로그 14:03 항목]`).
공통 규범 파일(`decision-flow.md`)은 건드리지 않는다.

**근거**
- [확인됨] `decision-flow.md:280`이 근거를 셋으로 못 박고 있다 — 계산·논리 / 프로젝트 내 코드·문서 / 외부 공식 문서
- [확인됨] 로그·스택 추적·테스트 실패 출력·재현 결과는 셋 중 어디에도 안 들어간다 (코드가 아니라 코드를 돌려서 관찰한 것)
- [확인됨] superpowers 1단계(52~62행)가 가장 먼저 요구하는 것이 바로 이것들이다
- 인정하지 않으면 로그를 눈으로 보고도 "확인 못 함"으로 적는 상태가 된다

**기각한 대안**
- 인정하지 않는다 — 화면이 실제와 어긋난다
- 공통 규범에 네 번째를 정식 추가 — 이 기능 하나로 모든 스킬이 공유하는 문서를 바꾸게 된다. 같은 문제가 다른 스킬에서도 반복되는 것이 확인되면 그때 올린다

## 조사로 해소된 항목

### 하위 에이전트에서 dev-workflow 훅이 도는가

Claude Code 공식 문서 확인 결과:

- **[확인됨]** 하위 에이전트는 새롭고 격리된 컨텍스트 창에서 시작하며, 대화 기록도 이미 불러온 스킬도 보지 못한다 (`sub-agents.md`)
  → **세션 시작 훅이 주입한 dev-workflow 지시는 하위 에이전트에 전달되지 않는다**
- **[확인됨]** 하위 에이전트 전용 훅이 따로 있다 — `SubagentStart`, `SubagentStop` (`hooks-guide.md`)
- **[확인 못 함]** `SessionStart`·`UserPromptSubmit`이 하위 에이전트 안에서도 도는지는 공식 문서에 명시가 없다

**결론:** 개발 단계 하위 작업자가 발견한 결함에는 이 구간이 자연히 안 걸린다.
이는 결함이 아니라 **경계**로 받아들인다 (제약 7과 일치).

국면 1의 시드 검증에서 근거 오독으로 강등됐던 항목이 이로써 정정·확정됐다.

## 만들면서 정할 것 (구현 중 관찰로 결정)

미리 숫자나 형식을 박지 않는다. 근거 없는 값이 규칙이 되는 것을 막는다.

1. **첫 화면의 모습** — 질문부터 낼지, 추론한 재현 경로를 먼저 한 줄 보이고 틀린 곳만 짚게 할지. 두 방식이 쓰는 재료가 같아 한 번 돌려 보면 바로 보인다
2. **질문 개수 상한** — 실제로 몇 개째에서 지치는지 보고 정한다
3. **비판의 규모** — 몇 명이 몇 라운드로 돌릴지, 서로의 발언을 가릴지. 완성 판정 8번이 이미 하한을 정해 두었다 (전문가 발언 최소 두 명분, 그중 최소 하나는 앞선 추정을 반박)
4. **"모름" 처리** — "그대로 superpowers에 넘긴다"를 기본값으로 시작. 완성 판정 2번은 어느 쪽이든 통과한다
5. **"원인이 분명하다"의 판정선** — 완성 판정 1번의 두 예시로 시작해 실제 신고를 넣어 보며 다듬는다

## 페르소나 피드백 결과

국면 2는 스코프 정리(Simplifier)와 조사가 주도했고, 별도 토론 라운드는 돌리지 않았다.

**Simplifier 판정 중 본체가 정정한 것 1건**

- Simplifier: "되돌아가는 문 두 개는 사용자 뼈대 원문 어디에도 없다"
- 정정: 사용자가 앞선 발화에서 직접 언급했다 — "디버깅 과정 중 크리티컬해서 아키텍처를 바꿔야 하는 상황이 온다면 이건 하나의 feature로 작업해야 하기 때문에 명세가 필요하다"
- 결과: 문 자체는 제약으로 유지하고, **자동 분기 장치만** 미루는 것으로 좁혔다

**합의**

- 첫 판은 "문 하나 + 질문으로 좁히기 + 넘기기" 최소 구성으로 간다
- 미루는 것은 사라지는 것이 아니라 이유와 함께 기록된다
- 숫자·형식은 관측 후에 정한다
