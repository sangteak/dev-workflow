## 탐색된 요구사항 전체 목록

논의 중 언급된 모든 것. 확정/미확정 구분 없이 기록한다.

### 문제 인식

- 기존 기능의 결함을 찾고 고치는 작업에서 superpowers 디버깅이 호출되고 고민 없이 바로 코드가 나온다
- 진짜 불만은 "견디기 힘들다"가 아니라 **즉답이 정말 면밀히 검토된 결과인지 알 수 없다**는 것. 실제로 그런 즉답 중 일부는 다시 고민해야 했다
- 원하는 것 두 가지 — ① 비판적 사고 기능을 쓰는 것 ② 근본 질문으로 예상 못한 상황을 미리 파악하는 것
- 원인이 명확한 결함은 문제가 없다. 진짜 값이 필요한 곳은 원인이 안 보이는 결함과, 기존 기능에 새 기능을 붙이거나 사양을 바꾸는 상황이다
- 실제 아팠던 사례: 운영 도구 스크립트 작업(윈도우 minikube·hyper-v)에서 모델이 추론으로 답해 여러 번 수정해야 했다. 워크플로우가 켜지지 않아 일반 대화로 진행됐을 수 있다
- 일반 코드베이스의 결함은 이슈 티켓으로 잘 처리되어 문제가 없었다

### 원하는 동작

- 브레인스토밍이 핵심 질문으로 요구사항을 좁히듯, 디버깅도 **핵심 질문으로 문제의 위치를 좁힌다**
- 사용자가 코드베이스를 모르면 "모름"으로 답할 수 있고, 알면 훨씬 빠르고 정확하게 도달한다
- 관통하는 정신: dev-workflow가 원래 담고 있던 "더 빠르고 더 견고하게"를 그대로 잇는다
- 예시: "매칭이 안돼 고쳐줘"가 들어오면 모든 가능성을 열어놓고 가정을 세우기보다, "매칭이 **어떻게** 안 되는 것인지"를 질문으로 구체화한다

### 사용자가 직접 정리한 뼈대 (원문)

> 실제 디버깅 기능은 superpowers가 그대로 담당한다. 왜냐하면 확인된 결과 탄탄하게 구성되어 있기 때문이다.
> 다만 superpowers에 결함 및 디버깅을 위한 내용이 전달될때 구체적이지 않을 수 있으므로 이 경우 파악 범위를 좁히기 위해 간단한 브레인스토밍을 진행한다.
> 즉, superpowers 디버깅 진입 전 단계를 만들어준다. 이건 일회성이므로 어딘가에 기록하지 않는다.

## 조사로 확인된 사실

### superpowers 6.2.0 systematic-debugging

- 활성 버전은 6.2.0 (`~/.claude/plugins/installed_plugins.json:27`). dev-workflow 문서에는 "검증 버전 6.1.1"로 적혀 있어 어긋남 — 별도 정정 대상
- 철칙 (`SKILL.md:17`): `NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST`
- 4단계: 1단계 근본 원인 조사(48~118행) → 2단계 패턴 분석(120~141행) → 3단계 가설과 검증(143~166행) → 4단계 구현(168~212행)
- 1단계가 먼저 알고 싶어 하는 것 셋: 에러 메시지·스택 추적 원문(52~56행), 재현 절차와 재현성(58~62행), 최근 변경(64~68행)
- **1단계와 2단계에 사용자에게 묻는 절차가 없다.** 모델이 혼자 조사한다
- 사람이 등장하는 자리 셋: 210행 "3번 실패 후 사람과 상의"(차단력 있음), 163~166행 "모르면 도움 요청"(대상 불명), 233~242행 "사람이 보낸 신호 인식"(먼저 묻는 장치 아님)
- 4단계는 실패하는 테스트를 먼저 만들 것을 요구(172~177행) → 증상의 영구 기록이 테스트가 된다
- 4단계에 들어가면 `test-driven-development`(실패 테스트 없이 제품 코드 금지)와 `verification-before-completion`(증거 없는 완료 선언 금지)이 딸려 온다
- 보조 기법 3종: 역추적(root-cause-tracing.md), 다중 방어(defense-in-depth.md), 조건 기반 대기(condition-based-waiting.md)
- 형제 스킬 중 systematic-debugging을 부르는 곳이 하나도 없다. 유일한 배선은 `using-superpowers:31` `"Fix this bug" → superpowers:systematic-debugging first`
- `using-superpowers:7` 특정 작업을 받은 하위 에이전트는 이 스킬을 무시한다
- `using-superpowers:62` 사용자 지시(CLAUDE.md 등)가 스킬보다 우선한다
- `SKILL.md:239`의 "Ultra-think this"의 붙임표는 확장 사고 강제 발동을 깨뜨리는 의도된 장치 (`RELEASE-NOTES.md:165`) — 옮겨 적을 때 제거 금지
- 6.2.0 본문은 압축판 (`RELEASE-NOTES.md:19` — Bottom Line·Key Principles·Real-World Impact 절 삭제)
- 스킬 폴더에 규범이 아닌 파일 5개(CREATION-LOG, test-academic, test-pressure-1~3)가 섞여 배포된다. 통째로 읽으면 "가정적 질문 금지" 같은 시험 프롬프트 문장이 규범으로 오인될 수 있다

## 페르소나 피드백 결과

### 라운드 1 (블라인드) — 좁히기 구간의 경계

두 전문가가 서로를 보지 못한 채 같은 결론에 도달했다.

**합의**
- 좁히기는 증상 명세까지만 만들고 원인 가설에는 손대지 않는다
- 결과는 대화가 아니라 파일 또는 호출 문장으로 넘긴다 (대화 내용은 압축되면 사라진다)
- 발동은 훅으로 어휘를 감지하되 절차를 강제하지 않고 "좁힐지 판정하라"만 얹는다
- **넘기는 것은 "이 범위만 보라"가 아니라 "여기부터 보라"여야 하고, 빗나갔을 때 원점으로 돌아가는 복귀선이 문장으로 박혀 있어야 한다** — 두 전문가가 서로 다른 이유로 같은 곳에 도달

**전제 반박 (양쪽 모두 제기)**
- 🛠️ Claude Code Expert: 사용자 관측 자체가 틀리면(매칭은 됐는데 화면에 안 뜬 것) 좁히기가 진짜 원인 영역을 미리 지워버린다
- 🎯 Workflow Designer: 사용자의 답이 틀리면 오진이 더 빨라지고, "내가 답한 대로만 보고 왔다"는 더 나쁜 불신으로 돌아온다

### 라운드 2 — 증상 카드 자리 (비판: 🎯 Workflow Designer [Contrarian])

**결론: 기존 이슈 카드 확장은 성립하지 않는다**

- 카드는 채워 넣는 서식이 아니라 **칸의 공백으로 상태를 읽는 기계**다. 원인 칸이 비면 "대기"로 판정되어 세션 목록에 이름조차 뜨지 않고(`context-handling/SKILL.md:157`), 억지로 채우면 "활성 카드는 항상 1장만"·"활성 카드가 있는 동안 신규 태스크 배정 보류"에 걸려 개발 전체가 선다(`SKILL.md:239, 253`)
- **삭제 방아쇠가 이 흐름에 없다.** 카드 삭제는 경량 사이클의 마지막 단계에서만 일어나는데(`SKILL.md:246`), 그 직전 단계인 "수정"을 superpowers에 넘겼다. superpowers에는 dev-workflow의 파일 규약도 삭제 지시도 없다
- 게이트 오탐을 피하려고 이름을 떼면 감시망 네 개 밖으로 동시에 나간다 (`detect-remnants`가 보는 이름은 HANDOFF.md·plan.md·phase1_exploration.md뿐)
- 이 저장소는 이미 정반대 규칙을 명문화했다 — `SKILL.md:211` "태스크 리뷰·fix 루프가 다루는 결함은 카드를 만들지 않는다 (Superpowers SDD가 전담)". **다른 엔진이 루프를 소유하면 카드를 만들지 않는다**가 기존 판단이다

### 사용자 반박 (본체보다 강했던 논거)

- 파일 기록의 목적은 "명세를 남겨 재활용"인데 결함은 일회성이라 재활용될 일이 없다
- 아키텍처를 바꿔야 하면 그건 기능 하나로 가고 거기서 명세가 정상적으로 생긴다

→ 본체가 추천을 3번(조건부 생성)에서 2번(파일 없음)으로 변경. 조건 셋이 모두 기존 장치(HANDOFF·이슈 카드·사용자 요청)와 중복임이 확인됨

## 시드 (사용자 확인 완료)

**목표**

superpowers가 실제 디버깅을 그대로 전담하되, 전달되는 결함 내용이 구체적이지 않을 때 파악 범위를 좁히기 위한 간단한 브레인스토밍을 superpowers 디버깅 진입 전에 한 구간 둔다. 이 구간은 질문으로 증상을 좁히고, 미처 생각 못 한 가능성을 표면으로 끌어낸다. 결과는 일회성이므로 어디에도 기록하지 않는다.

**제약**

1. superpowers 디버깅 네 단계는 손대지 않는다. 조사부터 고치기까지 그쪽이 전담한다
2. 새로 만드는 것은 superpowers 디버깅 진입 전 구간 하나뿐이다
3. 좁히기의 끝점은 증상 명세와 조사 우선순위까지다. 원인은 지목하지 않는다
4. 조사 우선순위는 명령이 아니라 권고다. 복귀 문장을 함께 넘긴다
5. 좁힌 결과를 파일로 기록하지 않는다. 오래 남는 기록은 실패 테스트와 커밋이 맡는다
6. 원인이 이미 분명한 결함은 좁히기 없이 그냥 고친다
7. 개발 단계가 진행 중일 때는 이 구간이 발동하지 않는다. 그 자리는 이슈 카드가 맡는다
8. 되돌아가는 문을 두 개 둔다 (사양 결정 / 기능 승계)
9. 비판에 참여할 전문가는 프로젝트 고정 세트를 쓴다
10. 발동 어휘는 한 번에 다 정하지 않고 상황을 보며 늘린다
11. 설계 문서는 dev-workflow 카테고리 아래에 놓는다

**비목표**

- superpowers 디버깅 네 단계를 고치거나 대체하는 일
- 원인을 지목하거나 수정안을 내놓는 일
- 좁히기 결과를 오래 남는 파일로 남기는 일
- 개발 단계 안에서 발견된 결함을 처리하는 일
- 디버깅 전용 전문가 세트를 새로 만드는 일
- 아키텍처를 바꿔야 할 만큼 큰 결함을 이 구간에서 처리하는 일

**완성 판정 기준**

1. `"매칭이 안돼 고쳐줘"`를 넣으면 좁히기가 열리고, `"이 함수에서 널 검사가 빠져서 터진다"`처럼 원인이 적힌 신고를 넣으면 좁히기 없이 바로 수정으로 간다 — 두 경우가 화면에서 구분되어 보인다
2. 질문이 한 번에 하나씩만 나오고, "모른다"고 답해도 막히지 않고 다음으로 넘어간다
3. 좁히기가 끝나면 증상 명세와 조사 우선순위가 화면에 나오고, 그 안에 원인 지목이나 수정 방법이 들어 있지 않다
4. 조사 우선순위 옆에 복귀 문장이 함께 붙어 있다
5. superpowers를 부르는 문장 안에 증상 명세와 조사 우선순위가 그대로 실려 전달되는 것이 화면에서 확인된다
6. 좁히기가 끝난 뒤 저장소에 이번 좁히기 때문에 새로 생긴 파일이 하나도 없다
7. 고치는 방법이 여러 갈래로 갈릴 때 실제로 사양 결정 화면이 뜨고, 설계 자체가 문제일 때 실제로 브레인스토밍 단계로 넘어간다
8. 이모지가 붙은 전문가 발언이 최소 두 명분 화면에 나오고, 그중 최소 하나는 앞선 추정을 반박한다
9. 사용자가 말한 증상 진술 자체를 되묻는 질문이 최소 한 개 나온다

**가정**

- superpowers 디버깅 문서 구조가 당분간 지금 모습을 유지한다. 줄 번호에 기대지 않고 "1단계 진입 전"이라는 위치로만 붙인다
- 사용자가 코드베이스를 어느 정도 알 때 질문이 값을 낸다. 전혀 모르면 지금과 같아지지만 손해는 아니다
- 프로젝트 고정 전문가 세트가 디버깅 상황의 비판에도 쓸 만하다
- 좁힌 결과를 기록하지 않아도 세션이 끊겼을 때 큰 손실이 없다
- [확인됨] 좁히기가 모으는 정보는 superpowers 1단계가 먼저 알고 싶어 하는 세 가지와 겹친다
- [확인 못 함] 그래서 1단계 조사가 실제로 짧아지는지는 확인되지 않았다. superpowers 문서 46행은 "각 단계를 반드시 끝내고 다음으로 가라"고만 적혀 있다. 만든 뒤 관찰로 확인할 항목

**열린 질문 (국면 2로 이월)**

1. 이 구간이 어떻게 켜지는가 — 어휘 감지·슬래시 명령·둘 다. 처음 어휘는 무엇인가. `bootstrap.md:12`와 어떻게 공존하는가
2. 첫 화면의 모습 — 질문부터 낼지, 추론한 경로를 먼저 보이고 틀린 곳만 짚게 할지
3. 실행 로그·스택 추적·테스트 실패 출력을 근거로 인정할지 (검증 규범 출처 확장 여부)

6. 비판을 어떤 모양으로 돌릴지 — 몇 명·몇 라운드·블라인드 여부
7. "모름"으로 넘긴 질문을 이 구간이 직접 조사할지, 그대로 superpowers에 넘길지
8. 전문가 세트 파일이 없을 때 비판을 생략할지, 기본 전문가를 쓸지
9. superpowers가 내놓은 수정안이 타당한지 누가 언제 따지는가
