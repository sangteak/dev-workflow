# intake-routing 설계 문서

> 한 줄 요약: 일이 들어오는 문을 브레인스토밍 하나로 모으고, 요청의 성격에 따라 나가는 문(구현·디버깅)과 남기는 것을 다르게 한다.

## 1. 배경과 동기

사용자가 겪은 문제는 하나였다.

> 예를 들어 내가 무슨 문제가 생겼어~ 했더니 dev-workflow가 호출되지 않고 바로 superpowers:debugger가 호출됐어. 이게 싫었던거야.

결함을 말하면 dev-workflow가 발동하지 않고 `superpowers:systematic-debugging`이 바로 잡는다. 그 스킬은 질문을 먼저 하지 않고 조사부터 시작한다.

조사로 드러난 것.

- [✔ `bootstrap.md:8`] 발동 어휘에 결함 계열이 하나도 없다. 결함 발화는 애초에 dev-workflow를 부르지 못한다
- [✔ `using-superpowers:31`] 반대편에는 `"Fix this bug" → superpowers:systematic-debugging first`라는 명시적 배선이 있다
- [✔ 디버깅 스킬 52~68행] 그 스킬의 1단계는 에러 원문·재현 절차·최근 변경 셋을 원하는데, **1단계와 2단계 어디에도 사람에게 묻는 절차가 없다.** 셋 다 모델이 알아서 찾아야 한다
- [✔ 같은 문서 233~242행] "틀을 잘못 잡았다"는 판정은 아예 바깥의 사람에게 넘긴다

주문을 외워 브레인스토밍을 켜도 해결되지 않았다. [✔ 확인] 켜도 도착지가 틀리다 — 첫 화면이 카테고리 확정이고, 끝나면 무조건 계획으로 가며, 문서 다섯 개가 생긴다. 결함에는 맞지 않는 옷이다.

그래서 필요한 것은 두 가지다. **들어오는 문을 하나로 모으는 것**과, **나가는 문을 갈래에 따라 나누는 것.**

## 2. 목표와 비목표

### 목표

- **GOAL-001**: 신규 기능·사양 변경·리팩터링·결함 네 갈래가 모두 브레인스토밍을 입구로 지난다. 사용자가 보는 첫 화면의 문법이 같다
- **GOAL-002**: 갈래에 따라 뒤에 오는 행동이 갈린다 — 구현은 `superpowers:subagent-driven-development`, 결함은 `superpowers:systematic-debugging`
- **GOAL-003**: 갈래에 따라 남기는 것이 다르다. 결함처럼 한 번 쓰고 마는 일은 마무리에서 흔적을 지운다
- **GOAL-004**: 새 행동이 늘어도 **블록 하나 추가로 끝난다.** 단계 표와 발동 규칙을 다시 건드리지 않는다

### 비목표

- **단계 이름을 갈래별로 늘리지 않는다** — 새 갈래 하나당 손댈 곳이 12~16군데가 되고, 사용자가 쓴 규칙 파일에까지 이름이 새겨져 되돌릴 수 없다
- **superpowers 내부 절차를 바꾸지 않는다** — 우리가 하는 일은 그 스킬에 더 나은 입력을 건네는 것까지다
- **브레인스토밍 앞에 별도 문진 화면을 두지 않는다** — 문이 둘이 되고 발동 경쟁자가 하나 는다
- **아카이브 누적 관리 규칙을 만들지 않는다** — `_archive/`는 이미 세션 목록과 머지 스캔에서 빠진다. 관측하지도 못할 규칙은 방치된다
- **관측 루프를 만들지 않는다** — 사용자 판단: "우리는 디버거에 조금 더 구체적인 내용을 전달하기 위함인건데 이게 실제로 유효한지 등은 그 다음 문제다". [✔ 확인] 이 저장소의 기존 관측 루프 3건이 전부 미실행 상태로 방치돼 있다

## 3. 확정된 요구사항

### 입구

- **REQ-001**: 브레인스토밍 자체가 네 갈래의 입구가 된다. 앞에 별도 관문을 두지 않는다 — 우선순위: HIGH
- **REQ-002**: 발동은 **상시 주입과 훅을 함께** 쓴다. 상시 주입이 뜻으로 넓게 그물을 치고, 훅이 정해진 낱말에 힘을 실어준다 — 우선순위: HIGH
- **REQ-003**: 무발동 취지 문장 다섯 곳을 "이미 답이 정해진 요청은 발동하지 않는다"는 뜻으로 정비한다 (`bootstrap.md:12`, `workflow-orchestrator/SKILL.md:27`·`34`·`167`, `README.md:132`) — 우선순위: MEDIUM

### 갈래

- **REQ-004**: 갈래를 문서 앞머리에 `action:` 한 줄로 적는다. 값은 `new-feature` · `spec-change` · `refactor` · `defect` 넷. **갈래는 단계 이름을 새로 만들지 않는다** — 우선순위: HIGH
- **REQ-005**: 성격은 모델이 추정해 번호 목록으로 보여주고, **사용자 승인으로 확정한다.** 추정만으로 확정하지 않는다 — 우선순위: HIGH
- **REQ-006**: 갈래 값이 사는 자리는 설계 문서 앞머리·`HANDOFF.md` 앞머리·`seed.yaml`. **세 곳 모두에 칸을 만든다** — 우선순위: HIGH
- **REQ-007**: 값이 없을 때의 기본 갈래를 정한다. 값 유실이 조용한 오작동으로 이어지지 않게 한다 — 우선순위: HIGH

### 깊이

- **REQ-008**: 네 갈래 모두 다섯 단계를 **전부 거친다.** 갈래가 정하는 것은 각 단계의 종료 조건뿐이다 — 우선순위: HIGH
- **REQ-009**: 종료 조건이 이미 채워진 상태가 곧 스킵이다. "충분한 요청이면 건너뛴다"를 별도 규칙으로 만들지 않는다 — 우선순위: MEDIUM
- **REQ-010**: **건너뛸 수 없는 바닥 여섯** — 카테고리 확정 · 시드 확인 · 성격 승인 · REVIEW · 커밋 승인 · 푸시 승인. 어떤 갈래에서도, 종료 조건이 다 찼어도, 사용자가 서둘러 달라고 해도 생략하지 않는다 — 우선순위: HIGH
- **REQ-011**: 결함 갈래의 종료 조건 다섯 칸 — 에러 원문 · 재현 절차와 재현성 · 최근 변경 · 대상 · 수락 기준. **앞의 셋은 디버깅 1단계가 요구하는 것과 이름을 맞춘다** — 우선순위: HIGH
- **REQ-012**: 재현성 칸에 "재현 안 됨"이 들어가면 개발로 넘기지 않고 자료 수집으로 되돌아간다 — 우선순위: HIGH
- **REQ-013**: 브레인스토밍 국면 전환 세 곳을 "진행 후 이의 확인"으로 바꾼다. 인터뷰 최소 3회 하한에 갈래별 조건 분기를 넣는다 — 우선순위: MEDIUM

### 구조

- **REQ-014**: 행동 블록을 `skills/workflow-orchestrator/references/actions.md`에 둔다. **한 행동에 관한 모든 것이 한 블록 안에** 있다 — 설명 · 종료 조건 · 넘길 곳 · 남길 것 · 지울 것 — 우선순위: HIGH
- **REQ-015**: `actions.md`를 **언제 누가 읽는지** 지시문으로 명시한다 — 우선순위: HIGH
- **REQ-016**: 단계 축이 실제로 깨지는 두 곳을 고친다 — 개발 판정이 "계획 파일 존재"로 못 박힌 곳(`workflow-orchestrator/SKILL.md:80~83` + 복제본 `bootstrap.md:16~24`), 세션 재개 목록에서 **에러도 경고도 없이 사라지는** 곳(`context-handling/SKILL.md:148~154`) — 우선순위: HIGH
- **REQ-017**: 저장소 방식 감지 트리거를 단계 이름 열거에서 **행위 기준**으로 바꾼다 — "코드 파일을 처음 고치기 직전, 또는 개발·리뷰 진입 중 먼저 오는 시점" — 우선순위: MEDIUM

### 산출물과 마무리

- **REQ-018**: 기능명은 **시드 확인 직후 모델이 짓고 고지 한 줄로 알린다.** 답을 요구하지 않는다. 갈래별 예외만 블록에 둔다 — 우선순위: MEDIUM
- **REQ-019**: 결함 마무리는 기능 폴더를 통째로 지운다. **단, 지우기 직전 사용자 확인을 받는다** — 우선순위: HIGH
- **REQ-020**: 리팩터링 마무리는 변경 이력 한 줄로 끝낸다. 문서 취합의 기본 동작(여섯 절 채우기)과 어긋나지 않게 갈래 분기를 넣는다 — 우선순위: MEDIUM
- **REQ-021**: 방향 전환은 크기와 상관없이 **하나의 흐름** — 정리하고 `_archive/`로 옮긴 뒤 승계 목록을 남기고 새로 시작한다 — 우선순위: MEDIUM
- **REQ-022**: `/dev-workflow:finish`가 현재 갈래를 알아낼 수 있어야 한다 — 우선순위: HIGH
- **REQ-023**: 도메인 문서로 합쳐진 기능을 고칠 때는 새 기능 폴더를 만들고 끝나면 다시 합친다 (기존 규칙 유지) — 우선순위: LOW

## 4. 설계 개요

### 두 축

이 설계의 뼈대는 **축을 하나 더 놓되, 기존 축을 건드리지 않는 것**이다.

| | 단계 축 (기존) | 갈래 축 (신규) |
|---|---|---|
| 값 | BRAINSTORM · PLAN · DEVELOP · REVIEW · COMPLETION | new-feature · spec-change · refactor · defect |
| 정하는 것 | **언제** | **무엇을 확정해야 끝인가 · 어디로 넘기는가 · 무엇을 남기는가** |
| 사는 곳 | 세션 상태 · 파일 존재 여부 | 문서 앞머리 `action:` 한 줄 |
| 늘어날 때 | 늘리지 않는다 | 블록 하나 추가 |

**모든 갈래가 다섯 단계를 전부 지난다.** 갈래는 단계를 건너뛰지 않고 각 단계의 깊이만 바꾼다.

이 저장소는 이미 같은 방식으로 두 번째 축을 하나 쓰고 있다 — 저장소 방식(git 사용 여부). 감지를 쓰이는 순간까지 미루고, 세션당 한 번 기억하고, 표에 열을 늘리는 대신 행 하나를 두 줄로 쪼갰다.

### 흐름

```
사용자 발화
   │
   ├─ 상시 주입이 뜻으로 판단 ─┐
   └─ 훅이 낱말로 감지 ────────┤
                              ▼
                    workflow-orchestrator
                              │
                              ▼
                      BRAINSTORM (입구)
                              │
                   국면 0 카테고리 확정 [바닥]
                              │
                   성격 추정 → 사용자 승인 [바닥]
                              │            └─→ action: 확정 · 즉시 파일에 기록
                              ▼
                   시드 확인 [바닥] → 기능명 고지
                              │
                   국면 1~4 (깊이는 블록의 종료 조건이 정함)
                              │
                              ▼
                            PLAN
                              │
        ┌─────────────────────┴─────────────────────┐
        ▼                                           ▼
     DEVELOP                                     DEVELOP
  (new-feature · spec-change · refactor)        (defect)
  subagent-driven-development                systematic-debugging
        └─────────────────────┬─────────────────────┘
                              ▼
                        REVIEW [바닥]
                              │
                              ▼
                        COMPLETION
                              │
         ┌────────────────────┼────────────────────┐
         ▼                    ▼                    ▼
   문서 취합·보존         변경 이력 한 줄      폴더 삭제
   (new-feature·spec-change)  (refactor)      (defect)
                                                   │
                                          삭제 직전 확인 [게이트]
```

### 행동 블록

`actions.md`의 블록 하나가 한 갈래를 통째로 정의한다.

```
## [갈래 이름]

- 설명 — 어떤 일인가
- 종료 조건 — 각 단계에서 무엇이 채워져야 다음으로 가는가
- 넘길 곳 — 개발 단계에서 어느 스킬로 보내는가
- 남길 것 — 마무리에서 무엇을 보존하는가
- 지울 것 — 마무리에서 무엇을 없애는가 (있으면 확인 게이트 동반)
- 기능명 규칙 — 기본 규칙에서 벗어날 때만
```

**새 행동을 추가할 때 이 파일에 블록 하나만 더한다.** 단계 표·발동 규칙·화면 문법은 건드리지 않는다.

다만 **이번 판에서는 한 번 손댄다.** 갈래 축이 단계 축과 직교하므로 축을 놓는 작업 자체는 여러 파일을 지난다. 그 뒤로 블록 하나만 더하면 되는 구조가 남는다.

## 5. 의존성 맵

| 컴포넌트 | 의존 대상 | 영향받는 컴포넌트 |
|----------|-----------|------------------|
| `actions.md` (신규) | 없음 — 순수 데이터 | workflow-orchestrator · brainstorming · document-consolidation · context-handling |
| workflow-orchestrator | `actions.md` · `decision-flow.md` | 단계 판정 · 성격 화면 · `/finish` 라우팅 |
| brainstorming | `actions.md` (종료 조건) · `personas.md` | 국면 전환 · 인터뷰 하한 · 기능명 · `seed.yaml` |
| context-handling | `action:` 값 | 세션 재개 목록 · HANDOFF 앞머리 · 진행 중 유지 규범 |
| document-consolidation | `actions.md` (남길 것 · 지울 것) | 마무리 분기 · 삭제 확인 게이트 |
| rules-injection | 단계 이름 | **기존 이름을 그대로 넘기면 무사.** 새 이름을 넘기면 조용히 규칙이 안 붙는다 |
| plan-stage | `action:` 값 | 갈래별 실현 가능성 평가 깊이 |
| 발동 훅 (신규) | **없음 — 파일을 읽지 않는다** (확정 6) | 상시 주입과 함께 이중 그물. 진행 중/신규 경계는 주입 문면이 두 갈래로 적어 모델이 가른다 |
| bootstrap.md | 없음 | **상시 주입 예산에 직접 반영** |
| superpowers | 없음 | 우리가 더 나은 입력을 건넬 뿐, 내부는 안 건드린다 |

**의존이 없는 곳** — 도메인 머지 · MCP 서버 · 설계 문서 색인 · 요약 · 개발 원칙 · 기존 테스트는 단계 이름을 아예 쓰지 않는다.

## 6. 기술 결정 및 대안 검토

| 결정 사항 | 선택 | 근거 | 검토한 대안 | 기각 사유 |
|-----------|------|------|-------------|-----------|
| 입구 위치 | 브레인스토밍 자체가 입구 | 주문을 외워 켜도 도착지가 틀렸다 — 첫 화면이 카테고리, 끝나면 무조건 계획, 문서 다섯 개 | ① 얇은 문진을 앞에 둔다 ② 새 통합 입구 스킬 | ① 문이 둘이 되고 발동 경쟁자가 는다 ② 되돌리기 어렵고 이름을 직접 부른 사람에게도 통행세 |

## 7. 제약조건과 가정

### 제약

- **[✔ `plugin-architecture.md:48`·`:50`] 상시 주입에 바이트 목표를 세우지 않는다** — 저장소 규범이 이미 「수치 프록시 금지」다(수치 목표는 지표가 목표를 밀어내니 세우지 않고, 깨지면 '순증 전량 분류'로 대체 판정한다). 상시 린트로 승격하지도 않는다. 이 기능이 더하는 194~244바이트는 순증 분류로 다룬다
  - ~~"2,560바이트 예산 26.6% 초과"~~ — **철회.** 계획 단계 실측 결과 2,560은 반올림 표기("약 2.5KB")를 거꾸로 환산해 만든 값이라 **어느 시점에도 실측된 적이 없고**, 3,242는 윈도우 줄바꿈이 섞인 값이다(커밋된 실체 3,208바이트). 예산이 정해진 커밋 시점의 실제 크기는 2,333바이트였다
- **[✔ `development-principles/SKILL.md:42` + 사용자 전역 설정] "버그는 묻지 말고 그냥 고쳐라"가 두 곳에 살아 있고, 한 곳은 이 저장소가 못 고친다.** 결함 갈래의 질문 루프와 정면으로 부딪히며, 우선순위 규칙상 사용자 설정이 이긴다
- **[✔ `using-superpowers:7`] 하위 에이전트는 격리된 컨텍스트로 시작해 세션 시작 훅 주입을 보지 못한다.** 행동 블록 규범을 하위 에이전트에 전할 방법을 따로 만들어야 한다
- **[✔ `tests/`] 스킬 문서를 검사하는 자동 테스트가 하나도 없다.** 테스트 17건은 전부 훅을 겨눈다
- **[✔ `installed_plugins.json`] 실제로 도는 것은 이 워크트리가 아니라 캐시 사본이다.** 고친 것을 확인하려면 버전을 올리고 다시 받고 재시작해야 한다

- 파일을 쓰지 않고 세션을 넘어 무언가를 누적하는 장치는 저장소에도 플랫폼에도 없다

### 가정

- 사용자가 성격 승인 화면에서 갈래를 제대로 고른다 — [⚠️ 미검증] 틀리는 빈도는 써 봐야 안다
- 결함이 마무리에 닿을 무렵의 사용자는 그것이 결함이었는지 사양 변경이었는지 안다 — 삭제 확인 게이트가 이 가정 위에 선다
- 브레인스토밍이 넘겨준 다섯 칸이 디버깅 1단계의 요구를 실제로 만족시킨다 — 이름은 맞췄으나 [⚠️ 미검증]

### 전제에 대한 반박 — 알고 진행한다

검증에서 전문가 셋이 서로를 못 본 채 같은 곳에 도달했다. 채택하지 않았으나 기록으로 남긴다.

> 전제가 틀렸을 때 실제로 남는 손실은 하나뿐이다 — "친숙한 같은 화면"이라는 값. 전제가 틀렸을 때 잃는 것은 작고, 전제를 믿고 지불하는 값은 크다.

**이 설계가 서는 자리** — 같은 전문가들이 짚은 유효 조건이다.

> 사용자가 자기 요청이 무슨 종류인지 **스스로 판단하기 어려울 때**다. "이상한데" 같은 발화는 결함인지 사양 오해인지 본인도 모르는 상태이고, 그때는 하나의 문에서 함께 정하는 편이 낫다.

성격이 처음부터 분명한 요청에는 이 설계가 값을 못 한다. 그 경우 종료 조건이 이미 채워져 있어 자동으로 얕게 지나간다(REQ-009).

다른 칸은 전부 자리표시자인데 `action:`만 `new-feature`가 박혀 있었다. 모델이 채울 때 **"이미 답처럼 보여" 그대로 통과**하므로 승인받은 값이 조용히 덮인다. 네 자리 전부 지시문으로 바꾸고 국면 4에 승계 지시를 신설했다.

**④ 이 판과 무관한 버그 하나를 고쳤다**

[✔ `git ls-tree` 최초 커밋] `hooks/session-start`·`hooks/inject-rules`가 **처음 커밋부터 `100644`**(실행 불가)였다. `hooks.json`이 인터프리터 없이 경로를 명령으로 부르고 둘 다 셔뱅이 있으므로, **리눅스·맥에서 세션 시작 훅 둘이 통째로 죽어 있었다** — 오케스트레이터 자동 주입과 규칙 주입이 그 둘이다. 윈도우(`core.filemode=false`)에서는 증상이 안 보이고 테스트는 `bash`로 직접 부르므로 원리적으로 못 잡는다.

### GOAL-004 실측 — §8의 상한이 과소평가였다

§8이 "블록 하나 + 훅 어휘 한 줄 + 화면 이름 한 줄" = **3곳**이라 적었으나, 브랜치 리뷰 실측은 **8곳**이다.

무조건: `actions.md` 블록 · `templates.md` 열거 주석 · `templates/seed.yaml` 주석 · 성격 승인 화면 선택지 번호 · `README.md` 갈래 표 · `hooks/intake-nudge` 어휘 · `SKILL.md` 어휘 원본 · `bootstrap.md` 착수 신호 예시.

「화면 이름 한 줄」은 소비 계약 ②(설명 첫 줄)로 실제로 제거됐으나, **선택지 번호와 README 표가 그 자리를 대신 차지했다.** 2판에서 이 문장을 실측값으로 고친다.

### 리뷰가 잡은 것 — 수정 라운드 8회

**Critical 4 · Important 14.** 반복된 패턴 하나가 뚜렷하다 — **본문이 아니라 "그것을 설명하던 문장"**에서 열한 번 걸렸다. 파일 머리 요약 주석 · 절 서두 설명 · 표 셀 · 다른 파일 헤더.

문서 기반 플러그인의 고유 함정이다. 코드라면 컴파일러가 잡을 어긋남이 조용히 남는다. 태스크마다 붙인 잔존 스윕이 정확히 이것을 잡았다.

판단 기준 하나가 실전에서 정립됐다 — **"내 변경 없이도 틀렸는가?"면 범위 밖 보고, "내 변경 때문에 틀려졌는가?"면 파일 스코프 밖이라도 내 책임.**

### 검증 수단의 한계 (실측)

확정 10에 따라 새 테스트를 만들지 않고 `grep` 기반 검증을 썼는데, 리뷰가 약점을 실증했다 — **문자열 개수를 세는 검증은 아무 문장이나 넣어도 통과한다.** 실제로 한 태스크에서 검증을 통과시키려 문장을 추가한 일이 있었다(그 문장 자체는 타당했으나 판단 근거가 "검증이 실패해서"였다).

남은 검증을 **자리별 고유 문맥 확인**으로 바꿨다. 2판에서 같은 함정을 피할 것.
