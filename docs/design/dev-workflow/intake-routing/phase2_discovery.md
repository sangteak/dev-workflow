## 결정 1 — 단계 축: 갈래를 별도 칸으로 병기한다 (B안)

### 선택

다섯 단계 이름(BRAINSTORM · PLAN · DEVELOP · REVIEW · COMPLETION)을 **그대로 두고**,
갈래를 문서 앞머리에 `action:` 한 줄로 적는다.

**핵심 규칙: 갈래는 단계 이름을 새로 만들지 않는다. 모든 갈래는 다섯 이름 중에서만 고른다.**

값: `new-feature` · `spec-change` · `refactor` · `defect`
사는 자리: 설계 문서 앞머리, `HANDOFF.md` 앞머리

### 전수 조사로 밝혀진 것 — 실제로 깨지는 곳은 두 곳뿐

단계 이름을 읽어 쓰는 곳을 빠짐없이 찾은 결과, 대부분은 라벨이거나 사람이 읽는 안내문이었다.

**깨지는 곳 둘**

- `workflow-orchestrator/SKILL.md:80~83` — DEVELOP 판정 조건이 "계획 파일 존재"로 못 박혀 있어, 계획을 안 만드는 갈래는 판정 불능. 같은 판정이 `bootstrap.md:16~24`에 복제돼 있고 **그쪽만 상시 규범**이다
- `context-handling/SKILL.md:148~154` — 여섯 번째 규칙 "위 어디에도 해당 없으면 목록에서 제외". 흔적을 안 남기는 갈래는 **에러도 경고도 없이 세션 재개 목록에서 사라진다**

**안 깨지는 곳**

- `HANDOFF.md`의 단계 이름은 분기에 안 쓰이고 화면에 찍는 라벨뿐
- 페르소나 확정은 브레인스토밍이 입구인 한 그대로
- 규칙 주입은 **기존 단계 이름을 그대로 넘기면 무사**. 새 이름을 넘기면 조용히 아무 규칙도 안 붙는다
- 마무리 경고등은 단계 이름을 안 본다 (다만 계획 파일이 없으면 술어가 항상 거짓)
- 도메인 머지·MCP 서버·설계 문서 색인·요약·개발 원칙·테스트는 단계 이름을 아예 안 쓴다
- 단계 표 네 곳 중 `bootstrap.md`만 상시 규범이고 나머지 셋은 읽는 문서다

### 기각한 대안

**A안 — 단계 이름을 갈래별로 늘린다 (DEBUG·REFACTOR 신설)**

- 새 갈래 하나당 손댈 곳 **12~16군데**
- 되돌리기 어려움 — 단계 이름이 사용자 화면·`HANDOFF` 파일·**사용자가 쓴 규칙 파일**에 새겨진다. 마지막 것은 우리가 못 고친다
- `CLAUDE.md` 판단 기준으로 **MAJOR 후보**
- 유일한 장점: 배선이 이미 단계 이름으로 되어 있어 새로 배울 개념이 0

**C안 — 갈래가 단계를 오버라이드한다**

- 세션 재개에서 무너진다. 새 세션은 갈래를 모른 채 시작하는데, "계획 파일 없음"이 "아직 안 만들었다"인지 "이 갈래는 원래 안 만든다"인지 구분 불가
- 해소하려면 갈래를 파일에 적어야 하고, 그 순간 B안이 된다. **단독으로 서지 못한다**

### 함께 정해진 것

- 저장소 방식 감지 트리거를 단계 이름 열거에서 **행위 기준으로 한 번 교체** — "코드 파일을 처음 고치기 직전, 또는 DEVELOP·REVIEW 진입 중 먼저 오는 시점"
- 세션 재개 판정에 갈래 라벨 병기 (한 줄 추가)
- 마무리 경고등 술어 일반화 — "지금 갈래 블록이 정한 '끝났다고 볼 조건'이 충족"
- **"진행 중 HANDOFF 유지" 규범 정정** — 지금은 `context-handling/SKILL.md:291`이 "국면 완료 시 반드시 삭제"인데, 갈래 값을 들고 있으려면 진행 중에는 유지해야 한다. 규범 변경 스윕 대상
- 단계 표 네 곳에 각주 한 줄씩 — "갈래에 따라 각 단계의 깊이가 다르다. 어느 칸을 채워야 하는지는 `actions.md`의 갈래 블록이 정한다"

### 선례가 B안을 지지한다

- [✔ `SKILL.md:47~50, 183~190`] **이 저장소는 이미 두 번째 축을 쓰고 있다** — 저장소 방식(git 사용 여부). 감지를 쓰이는 순간까지 미루고 세션당 한 번 기억하며, 표에는 열을 안 늘리고 개발 행을 두 줄로 쪼갰다
- [✔ `plan-stage/SKILL.md:268~280`] **가장 가까운 본보기** — 재계획 진입은 단계 이름을 안 늘리고 변형 입구만 만들었다
- [✔ `SKILL.md:242, 256, 260`] 이슈 카드 심각도는 세 값이지만 실제 경로는 둘이고, 세밀한 갈림은 **판별 문장 한 줄**이 고른다
- [✔ Jira 공식 문서] "워크플로 스킴은 워크플로와 이슈 타입 사이의 매핑을 정의한다". 기본 스킴이 모든 종류를 하나에 붙여두고 **예외만 명시 배정**하게 한다
- [✔ Linear 공식 문서] 반대 선택도 성립한다 — 종류별로 다른 워크플로를 주지 않는다
- [✔ GitHub `spec-kit` 이슈 #1191] 갈래 축이 없어 사용자가 `/speckit.bugfix` 같은 새 명령을 요구하는 압력의 실물 기록
- [✔ `claude-code-spec-workflow`] 갈래마다 단계 이름을 새로 만든 사례 — 기능은 "요구사항 → 설계 → 태스크 → 구현", 결함은 "신고 → 분석 → 수정 → 검증". **이름이 두 벌이 됐다.** A안이 가는 길

### 두 축 시스템의 흔한 실패 넷과 회피법

- **곱셈 폭발** — 네 갈래 × 다섯 단계 = 스무 칸. 회피: 굵은 경로만 라벨이 고르고 세밀한 갈림은 판별 문장이 고른다
- **중복 분류** — 새 축이 기존 신호와 같은 말을 두 번 한다. [✔ 파이썬 코어 팀 논의] GitHub 이슈 타입을 기존 라벨과 겹쳐서 접었다. **우리도 이슈 카드가 이미 "결함"을 표현한다** — 경계선 절의 구분을 지켜야 한다
- **축 값 유실** — 세션이 끊기면 갈래가 사라진다. 회피: 이미 읽고 있는 자리에 넣고, 값이 없을 때의 기본 갈래를 정한다
- **게이트 잠식** — "경량 갈래"라는 이름으로 안전장치가 조용히 빠진다. 회피: [✔ `merge-to-domain/SKILL.md:372`] "어떤 플래그 조합에서도 생략할 수 없다"는 바닥 명시 선례를 따른다

## 결정 2 — 갈래는 단계를 건너뛰지 않는다. 깊이만 줄인다

### 선택

**네 갈래 모두 다섯 단계를 전부 거친다.** 갈래가 정하는 것은 "각 단계에서 무엇을 확정해야 하는가"(종료 조건 칸)뿐이다.

### 근거

- [✔ superpowers `subagent-driven-development` 판단도 22~34행] 계획이 없으면 "Manual execution or brainstorm first"로 되돌린다. 계획 단계를 건너뛰면 구현을 무엇으로 돌릴지 새로 만들어야 한다
- [✔ `workflow-orchestrator/SKILL.md:114~163`] 리뷰 단계에 규칙 검증과 수락 기준 검증이 매달려 있다. 건너뛰면 함께 사라진다
- 리팩터링은 이미 돌아가는 코드를 건드린다. 절반만 끝난 순서는 돌아가던 것을 망가뜨리므로 **태스크 목록이 곧 되돌리기 지도**다
- 확장 원칙("새 행동은 블록 하나 추가로 끝난다")이 이 안에서만 온전히 성립한다 — 단계를 건너뛰면 **건너뛴 단계에 매달린 것들을 갈래마다 다시 이어 붙여야** 하고, 그게 곧 블록 밖을 건드리는 일이다
- [✔ 실측] 경량화 적용 시 브레인스토밍 왕복이 9회 → 6회라 다 거쳐도 무겁지 않다

### 건너뛸 수 없는 바닥 (여섯)

`action:` 값이 무엇이든, 종료 조건이 이미 전부 채워져 있든, 사용자가 서둘러 달라고 했든 건너뛸 수 없다.

1. 국면 0 카테고리 확정 — `decision-flow.md:255`가 로컬 템플릿 게이트로 고정
2. 시드 확인 (또는 블록이 지정한 대체 확인) — `brainstorming/SKILL.md:258` 명문 차단
3. 성격 확정에 대한 사용자 승인 — 추정만으로 갈래를 확정하지 않는다
4. REVIEW 단계 — 규칙 검증과 수락 기준 검증이 매달려 있다
5. 커밋 승인
6. 푸시 승인 (커밋과 별도)

형식 선례: `merge-to-domain/SKILL.md:372` "어떤 플래그 조합에서도 생략할 수 없다"

## 결정 3 — 결함 갈래에서도 질문 루프를 유지한다

### 초안에 있던 모순

행동 블록 초안의 종료 조건 다섯 칸은 전부 "브레인스토밍에서 채운다"로 적혀 있는데,
같은 문서의 다른 대목은 "국면 1~4를 디버깅 스킬로 대체한다"고 되어 있었다. 둘이 동시에 참일 수 없다.

### 선택

**전자.** 결함도 브레인스토밍이 질문으로 다섯 칸을 채운다.
후자를 택하면 질문이 사라지고, 그것은 사용자가 처음 겪은 문제("질문 없이 바로 코드")로 되돌아가는 것이다.

### 결함 갈래의 종료 조건 다섯 칸

앞의 셋은 `superpowers:systematic-debugging` 1단계가 요구하는 것과 **이름을 맞췄다.**
이름을 맞춰 두면 넘길 때 다시 물을 것이 없다.

1. **에러 원문** — 스택 트레이스 전문, 파일 경로·줄 번호·에러 코드 포함 (원본: 디버깅 문서 52~56행)
2. **재현 절차와 재현성** — 정확한 실행 단계 목록과 "매번 나는가"에 대한 답 (원본: 58~62행)
   - 이 칸에 "재현 안 됨"이 들어가면 개발 단계로 넘기지 않고 자료 수집으로 되돌아간다 (원본 62행 "If not reproducible → gather more data, don't guess")
3. **최근 변경** — 이 증상을 만들 수 있는 변경 목록. 없으면 "없음"이라고 쓴다 (원본: 64~68행)
4. **대상** — 어느 문서의 어느 절에 해당하는 결함인가
5. **수락 기준** — 2번 칸의 재현 절차를 그대로 다시 밟았을 때 증상이 안 나오는가

"모른다"고 답하면 조사로 넘어간다.

## 결정 4 — 기능명은 시드 확인 직후 모델이 짓고 이의만 받는다

### 선택

Step B 시드 확인 직후, 모델이 이름을 짓고 **고지 한 줄**로 알린다. 답을 요구하지 않는다.
갈래별 예외만 행동 블록에 둔다 — 사양 변경과 리팩터링은 고칠 대상 이름을 물려받고, 결함은 증상에서 뽑는다.

### 근거

- **왕복 순증 0** — 이미 사용자 응답을 받는 자리에 얹는다
- 목표가 확정되는 첫 순간이면서 파일이 아직 하나도 없는 순간이 여기다. 그보다 앞(국면 0)은 아는 게 첫 발화뿐이고, 그보다 뒤는 이미 폴더가 만들어진 뒤라 되돌리기가 비싸다
- [✔ `development-principles/SKILL.md:139`] "이 확인의 답이 사실상 항상 같은가"를 기준으로 게이트 대신 자동 결정 안전망을 쓰라는 규범이 이미 있다
- 저장소가 이미 이 비대칭으로 굴러간다 — 카테고리는 묻지만(`brainstorming/SKILL.md:40~58`) 이슈 카드 문제명은 묻지 않는다(`workflow-orchestrator/SKILL.md:214~235`). 카테고리는 목록에서 고르는 닫힌 선택이라 묻기가 싸고, 이름은 자유 문자열이라 물으면 **사용자가 작명 노동을 진다**
- 결함처럼 지워질 폴더에도 이름은 필요하다 — `HANDOFF`는 기능 폴더 안에만 살 수 있고(`context-handling/SKILL.md:47`), 경로가 없으면 세션을 넘길 수 없다

### 기각한 대안

- **국면 0에서 사용자에게 묻는다** — 왕복 1회 순증. 그 시점에는 목표가 없어 정보가 부족하다
- **국면 1 파일 쓰는 순간까지 미룬다** — 임시 저장 자리가 새 예외를 만든다 (`_draft/` 같은 것이 생기면 세션 탐색에서 걸러낼 이름이 둘이 된다)
- **갈래별로 작명 규칙을 전부 블록에 둔다** — 네 블록 중 셋이 같은 규칙을 반복하게 되어 단계 표 복제 네 곳과 같은 부담이 생긴다
- **사양 변경·리팩터링이 고칠 대상 이름을 그대로 쓴다** — 이름 충돌을 규칙으로 만든다. 도메인 문서와 기능 폴더가 카테고리 바로 아래 같은 자리에 산다

- 블록 항목 수 — 여섯인가 일곱인가 (페르소나 세트를 블록에 둘지)

### 구현 중 관찰로 정할 것

- 발동 어휘 최초 세트 — 후보 15개가 나왔다. `안 돼`·`안돼`는 일상 대화에 흔해 오탐 1순위이고, `error`·`이상해`·`튕겨` 같은 완곡 표현은 일부러 뺐다
- 리팩터링이 계획 단계를 항상 거치는가, 파일 수 기준 조건부인가
- 결함에서 "고칠 파일 4개 이상이면 갈래를 벗어난다"의 숫자 4 (선례 없는 임의값)
- 이의 창의 길이 — "다음 국면의 첫 사용자 응답까지"는 임의로 정한 값

## 국면 3으로 넘기는 위험 둘

### 위험 1 — 훅이 죽는 조건

발동 훅의 두 번째 겹을 "docs/design이 있고 **진행 중 잔존이 없을 때**"로 잡았다.
그 결과 **저장소에 진행 중 기능이 하나라도 있으면 무관한 새 결함 발화에도 훅이 안 울린다.**

여러 기능을 동시에 굴리는 사용자에게는 훅이 사실상 죽는다.
설계자는 "조용한 쪽으로 틀리기를 택했다"고 밝혔고, 두 번째 겹에서 이 조건을 빼는 다른 선택지도 함께 제시했다.

### 위험 2 — 상시 주입 예산은 어느 안이든 못 지킨다

정비 문안을 두 가지로 써서 실측했다.

- A안 (뜻이 또렷) — **+244바이트**
- B안 (압축) — **+194바이트**

어느 쪽이든 예산 2,560바이트를 **34% 넘게 초과한 상태**가 그대로다 (착수 전 26.6%에서 더 벌어진다).
자동 검사 장치도 없다. 예산 초과 자체를 어떻게 할지는 국면 3의 판단 대상이다.
