> 워크플로우 전반의 사용자 경험 일관성을 보장하기 위한 페르소나 피드백 구조, 상태 메타데이터 표준, 사용자 입력 형식 표준을 정의한다.

## 시스템 개요

dev-workflow는 브레인스토밍부터 리뷰까지 여러 단계를 거치며, 각 단계에서 페르소나가 참여하고 설계 문서가 생성된다. 이 과정에서 세 가지 일관성 문제가 발생한다. 첫째, 페르소나의 피드백이 체계적 구조 없이 흩어지면 다관점 검증의 품질이 들쭉날쭉해진다. 둘째, 설계 문서의 상태 메타데이터가 통일되지 않으면 인덱싱과 참조에서 누락이 발생한다. 셋째, 사용자 입력을 받는 지점마다 형식이 다르면 환경과 세션에 따라 경험이 달라진다. 이 domain은 페르소나 피드백의 구조화된 루프, 상태값 표준화, 입력 형식 통일이라는 세 축으로 워크플로우 전반의 UX 일관성을 확보한다.

## 페르소나 피드백 루프

brainstorming 스킬은 원래 국면 2(발견)에서 "충돌/보완" 규칙만 존재했으며, 정형화된 피드백 루프가 없었다. workflow-orchestrator가 "persona-based feedback loops"를 선언하지만 실제 구현은 plan-stage에만 있었고, brainstorming의 발산적 성격에 맞는 별도 메커니즘이 필요했다.

### 루프 구조

피드백 루프는 매 주제/질문마다 발동되며, 최대 3회로 제한된다. 초과 시 사용자 승인을 받아야 추가 토론이 가능하다. 각 라운드는 `[라운드 N/3]` 카운터로 표기하여 진행 상황을 명시한다.

비판적 관점은 라운드 로빈으로 할당하며, 라운드 시작 시 비판적 역할을 맡는 페르소나를 명시한다. 강제 비율은 두지 않으며, 비판 시에는 반드시 대안 또는 출구를 함께 제시해야 한다.

의견 본문은 페르소나 이모지와 이름 접두사를 붙인 자유 형식으로 작성한다. 정형 태그(찬성/반대 등)는 사용하지 않는다. 라운드 종료 시 `**합의:**` 또는 `**미합의:**` 마커와 결론 요약을 붙인다. 이는 brainstorming의 발산적 성격을 보존하면서도 결론을 구조화하기 위한 선택이다.

국면별로 강제 비율은 두지 않되 방향성 가이드를 제공한다. 국면 1에서는 비판보다 호기심을, 국면 3에서는 리스크를 놓치지 않도록 안내한다. phase 파일에는 토론 과정을 제외하고 합의/미합의 결론만 주제별로 그룹핑하여 기록한다.

plan-stage의 피드백 루프와는 의도적으로 별도 유지한다. 스킬 간 의존성을 방지하고 각자 독립적으로 진화할 수 있도록 하기 위함이다.

### 언어 규범

페르소나 발언이 만들어지는 전 경로에 같은 언어 규범을 적용한다. 원본은 `skills/workflow-orchestrator/decision-flow.md` 3부의 「언어 규범」 펜스 하나이며, 이 문서는 그 사실과 적용 구조만 기록한다 — 펜스 전문을 여기 복제하면 사본이 원본과 따로 낡는다.

적용 방식은 **원본 1곳 + 실행 시점 복제**다. 각 스킬은 서브에이전트 프롬프트를 조립할 때 펜스를 "--- 언어 규범 ---" 구획으로 그대로 붙여넣는다. 정적 복제(문서 사본을 만들어 두는 방식)와 참조만 두는 방식은 둘 다 실패한다 — 사본은 낡고, 서브에이전트는 참조를 읽지 않는다. 본체 발언은 `decision-flow.md`가 상시 규범이므로 원본이 직접 적용된다.

복제 지점은 brainstorming의 프롬프트 7종과 블라인드 프롬프트, plan-stage의 Architect·Researcher 프롬프트다. 적용 경로 목록을 문서에 명시해 "빠지는 경로 0"을 검증 가능하게 둔다.

### 발언 실질성

발언이 없는 것이 정상 상태이며, 쓰는 쪽이 입증 책임을 진다. 이 기본값 반전이 빈칸 채우기 습관의 뿌리를 끊는다 — 금지형("맞장구를 치지 마라")은 모델이 약하게 따른다.

발언하려면 새 기여 요소가 최소 하나 있어야 한다. 새 근거, 반례, 성립 조건 수정, 우선순위 변경 넷 중 하나이며, 없으면 발언을 생략한다.

모든 주장에는 도메인 근거를 병기한다. 동의 대상이 다른 페르소나든 사용자든 시드든 규칙은 한 벌로 같다. 블라인드 라운드에서 생략할 때는 `[의견 없음 — 사유 1줄]`을 정형으로 반환하고 취합 시 제외한다.

### 블라인드 첫 라운드

판정·평가 성격의 라운드는 상시 블라인드로 돌린다 — plan-stage 실현 가능성 판정, 국면 3 리스크 평가가 여기 해당한다. 발산 토론은 국면당 첫 루프만 블라인드이고, 2라운드부터는 대화형에 비판 로빈이 돌아간다.

블라인드 라운드는 페르소나 전원을 병렬 서브에이전트로 부르며 서로의 발언을 노출하지 않는다. 비판 담당을 따로 두지 않는다 — 비판할 동료 발언이 아직 없기 때문이고, 대신 전원이 "전제가 틀렸다면 무엇이 무너지는지"를 하나 이상 말할 의무를 진다.

독립성은 발췌 규격으로 지킨다. 프롬프트에 싣는 것은 사용자 발화 원문, 시드의 해당 절 원문, 기확정 결정 목록("재론 금지" 제약 명시) 셋이며, 이전 라운드 발언 전문은 싣지 않는다. 취합은 원문을 그대로 나열하고 본체가 재요약하지 않는다. 나열 순서는 라운드·주제마다 회전시킨다.

블라인드 일치도는 독립 검증이 아니라 약한 신호다 — 같은 모델이 같은 발췌를 읽으므로 오류가 함께 나는 경향은 남는다. 언어 규범이 안 지켜진 발언을 발견하면 `tasks/lessons.md`에 기록한다.

### 페르소나 적용 범위

페르소나는 BRAINSTORM과 PLAN에서만 쓴다. DEVELOP과 REVIEW는 의도적으로 페르소나를 두지 않으며 예외는 하나다 — 이슈 카드 경량 사이클의 확인 문구에 PLAN 세트 페르소나의 관점을 한 줄씩 병기한다. 서브에이전트나 토론 없이 메인 컨텍스트가 `.claude/personas.md`의 PLAN 세트를 읽어 작성하며, 그 파일이 없으면 관점 줄을 생략한다 (기본 페르소나로 채우면 도메인 추정치가 오도한다).

기본 페르소나 정의의 원본은 `skills/persona-resolution/SKILL.md`의 「기본 페르소나 정의 (Fallback)」 하나다. README의 표는 예시이며 프로젝트에 맞게 바뀐다.

### 발언 생산 규격

의견·비판·판정을 반환하는 페르소나 발언은 결론 한 줄, 근거 불릿 세 개 이내, 전제 반박 하나로 쓴다. 근거 셋은 상한이지 채움 목표가 아니며, 셋에 못 미치면 부족 사유를 한 줄로 대신 쓴다.

근거마다 전치 태그를 앞에 붙인다. 이 규격은 의견·비판·판정 프롬프트 셋에만 걸고 질문 생성 프롬프트에는 걸지 않는다 — 질문 산출과 "결론 한 줄" 정형은 양립하지 않는다.

발언을 벽 텍스트로 만들던 원인은 블라인드 라운드가 아니라 대화형 라운드의 비판 담당 원문 중계였다. 블라인드는 정형이 이미 강제돼 있었다.

### 근거 표기와 검증

검증 출처는 세 종류다 — 계산·논리, 프로젝트 내 코드·문서, 외부 공식 문서.

표시는 항목 첫머리에 전치 태그로 붙인다. `[✔ 출처]`는 대조를 통과한 사실, `[⚠️ 확인 불가]`는 결정에 영향을 주지만 확인하지 못한 것, `[✘ 반증 — 출처]`는 반증된 주장, `[추측]`은 확인 없이 하는 말이다. 세션에서 `[✔]`가 처음 나올 때 그 뜻을 한 줄로 고지한다.

**화면에 도달한 `[✔]`는 본체 관문을 통과했다는 뜻이다.** 미확인이면서 추천 사유나 선택지 성패의 근거로 쓰인 주장은 본체가 재확인하고, 이미 `[✔]`인 주장은 첨부된 증거와 대조만 한다. 이 관문은 본체가 직접 수행하며 워커로 내리지 않는다.

근거에는 증거를 첨부한다. 프로젝트 내 출처는 파일 경로와 행 번호 또는 한 줄 인용이고, 외부 출처는 워커가 판정과 출처 주소와 원문 인용을 함께 반환한다. 인용 없는 보고는 미확인으로 강등하고 강등한 사실을 화면에 드러낸다.

확인하지 못한 가정은 전부 말하지도 전부 숨기지도 않는다. **결정에 영향을 주는 것만** `⚠️`로 올려 표시하고 영향 없는 추측은 내지 않는다.

자동 형식 검사기는 두지 않는다. 준수는 모델의 지시 추종에 의존하므로, 규격은 지시문 한 문단으로 요약 가능해야 하고 등급·예외 판정에 주관 술어를 쓰지 않는다.

## 상태 메타데이터 표준

설계 문서 프론트매터의 `status` 필드에 `complete`와 `completed`가 혼용되면서, `design-doc-index`와 `design-summary` 스킬이 `status: complete`만 필터링하여 `completed`로 표기된 문서가 인덱싱에서 누락되는 문제가 발생했다. 근본 원인은 plan.md가 최종 상태를 `completed`로 명시했고, Claude가 `document-consolidation` 스킬의 `complete` 지시보다 plan의 값을 우선 적용한 것이다.

정규 상태값은 `ready-for-plan`과 `complete` 2개로 확정한다. 중간 상태(`in-progress`, `in-development`, `archived`)는 도입하지 않는다. phase 파일(phase1, phase2, phase3, plan.md)이 진행 추적 역할을 대체하므로 상태 라이프사이클은 2단계로 충분하다.

```
ready-for-plan (브레인스토밍 완료) → complete (개발+리뷰+문서통합 완료)
```

이 문제는 쓰기 쪽과 읽기 쪽 양쪽에서 방어한다.

**쓰기 쪽** — `document-consolidation` 스킬의 프론트매터 업데이트 규칙에 우선순위 규칙을 추가한다. plan.md 등 다른 소스에 명시된 값에 관계없이, 프론트매터 status는 반드시 정규값 `complete`를 사용한다.

**읽기 쪽** — `design-doc-index`와 `design-summary` 스킬에 인덱싱 본 로직 전 상태 정규화 전처리 단계를 분리한다. 프론트매터를 순회하여 `completed`를 `complete`로 자동 수정한 뒤 기존 필터링 로직을 그대로 실행한다. 허용 변형은 `completed` 1개만이며, 한국어(`완료`)는 제외한다. 시스템 메타데이터에 한국어 값이 들어갈 가능성이 없기 때문이다.

Markdown 스킬은 코드처럼 함수를 공유할 수 없으므로, 전처리 절차를 `design-doc-index`와 `design-summary` 양쪽에 동일한 표현으로 명시하여 유지보수 시 불일치를 방지한다.

## 입력 형식 표준

dev-workflow 플러그인에서 사용자 입력을 받는 36개 지점이 4가지 서로 다른 패턴(Yes/No 텍스트, 번호/문자 선택, 자유 텍스트, AskUserQuestion 도구)으로 혼재되어 있었다. 스킬 문서에 "무엇을 물어볼지"만 정의되어 있고, "어떤 도구/형식으로 물어볼지"는 미지정이었다. Claude가 비결정적으로 AskUserQuestion 도구 사용 여부를 결정하여 동일 사용자가 데스크톱과 노트북에서 다른 경험을 하는 문제가 발생했다.

모든 스킬에서 사용자 입력 형식을 텍스트 기반 번호 목록으로 통일하고, 스킬 문서에 입력 형식을 명시하여 Claude의 재량 여지를 제거한다. 규칙은 Claude의 출력 형식(질문 제시 방식)에만 적용되며, 사용자는 번호 또는 자연어로 자유롭게 응답할 수 있다.

### 입력 유형별 형식

**닫힌 선택 (선택지가 있는 질문)**
```
[질문 텍스트]

1. 선택지A
2. 선택지B
3. 선택지C
0. 직접 입력          ← 자유 입력 탈출구 필요 시만 추가
```

**Yes/No 질문**
```
[질문 텍스트]

1. Yes
2. No
```

**열린 입력 (선택지 없는 자유 텍스트)**
```
[질문 텍스트]
> 예: "[예시 입력]"
```

### 적용 규칙

- AskUserQuestion 도구를 사용하지 않는다. workflow-orchestrator의 CRITICAL 섹션에 명시적 금지로 배치하여 우선순위를 최대로 높인다. 금지의 적용 범위는 본 워크플로우가 주관하는 단계(BRAINSTORM/PLAN/COMPLETION)에 한정한다 — Superpowers 전담 단계(DEVELOP/REVIEW)는 이 금지의 적용 범위 밖이다.
- 모든 닫힌 선택은 텍스트 기반 번호 목록 형식으로 제시한다.
- Yes/No 질문도 번호 목록으로 통일한다 (`1. Yes  2. No`).
- 열린 입력은 번호 없이 예시 안내 형식으로 제시한다.
- 닫힌 선택에서 직접 입력이 필요한 경우, 0번을 "직접 입력" 예약 번호로 사용한다. 위치가 매번 달라지는 마지막 선택지 방식 대신 고정 번호를 사용하여 일관성을 확보한다.
- 문자 선택(A/B/C/D), 슬래시 구분(Yes / No), 괄호 안 선택지 나열을 금지한다.
- 사용자가 번호, "응", "Yes", "ㅇㅇ", "첫번째" 등으로 답해도 의미가 명확하면 수용한다. 의미가 모호한 경우에만 재확인한다.

### 적용 구조

규칙은 workflow-orchestrator에 Input Format Rules 섹션으로 추가하고, 9개 스킬의 기존 프롬프트 텍스트를 새 형식으로 일괄 수정한다. 규칙 분량이 10~15줄이므로 별도 스킬을 생성하지 않고 orchestrator를 확장하는 것이 적절하다.

```
workflow-orchestrator (SKILL.md)
├── CRITICAL 섹션: AskUserQuestion 도구 사용 금지
├── Input Format Rules 섹션: 입력 형식 표준 정의
└── Output Format Rules 섹션: (기존)

각 스킬 (SKILL.md)
└── 기존 프롬프트 텍스트 → 새 형식으로 교체
```

## 결정 요청 흐름

dev-workflow는 BRAINSTORM/PLAN 단계에서 페르소나 토론 후 사용자에게 결정을 요청하는 빈번한 패턴을 갖는다. 결정 항목이 한 번에 여러 개 나열되면 사용자 인지 부담과 라운드트립 중 맥락 손실이 발생한다. 본질 문제는 출력 형식의 단계적 흐름 부재와 결정 분할/통합 메타 규칙 부재 두 가지다. 이를 해결하기 위해 결정 흐름의 메타 원칙을 단일 SSOT로 정의한다.

규범은 `skills/workflow-orchestrator/decision-flow.md` 단일 파일에 집중되며, 4개 핵심 스킬(workflow-orchestrator, brainstorming, plan-stage, document-consolidation)이 SSOT를 가리킨다. orchestrator/brainstorming/development-principles에 분산 삽입하는 방식은 추상화 레벨 부정합(런타임 행위 원칙 vs 메타-가이드)과 컨텍스트 비용 비대칭(DEVELOP/REVIEW 세션에도 매번 결정 흐름 텍스트 영구 로딩)을 발생시키므로 채택하지 않는다. development-principles는 변경 없이 런타임 행위 원칙의 추상화 순수성을 유지한다.

v1.14.0부터 decision-flow.md는 결정과 질문을 아우르는 **상호작용 SSOT**로 확장되어 3부(1부 결정 규칙 · 2부 질문 규칙 · 3부 공통 형식·언어)로 재편됐다. 형식·언어의 원본은 3부가 유일하며, 1·2부는 그 스켈레톤과 언어 규범을 결정·질문에 각각 적용한 것이다. 상호작용 규범이 결정에만 존재하고 질문·안내에는 없던 비대칭이 실사용 UX 이슈 6건(결정 연극·초대-대기 불일치·박스 깨짐·용어 장벽·질문 일괄 제시·ID 불투명 참조)의 공통 뿌리였다. 파일 분리(question-flow.md)는 SSOT 단일성 훼손과 2회 Read 비용으로 기각됐다.

**v1.10.0 도달성 강화:** v1.9.0 배포 리뷰에서 "1줄 수동 참조 + 리포 상대경로"는 배포 환경(사용자 프로젝트 + 플러그인 캐시)에서 SSOT가 도달 불가하다는 결함이 확정되었다. v1.10.0부터 참조는 능동 Read 지시 + 경로 해소 절차(플러그인 루트 → 스킬 디렉토리 형제 경로 → `find "$HOME/.claude/plugins"` 동적 탐색)로 교체하고, 매 세션 주입되는 orchestrator SKILL.md에 '결정 요청 폴백 형식'(하나씩 + 오픈 박스 + 헤더)을, brainstorming에 토론 출력 최소 규칙(에이전트 태그·합의 마커)을 인라인하여 Read 실패 시에도 핵심 형식이 퇴행하지 않게 한다. 세션 시작 훅은 계산해 둔 플러그인 루트 값을 주입 텍스트에 한 줄 포함하여, 1선 경로 해소(플러그인 루트 직접 참조)가 세션 시작부터 성립한다. 훅에서 decision-flow.md 전문을 주입하는 방식은 컨텍스트 비용 비대칭 논거를 유지하여 보류하고, Read 준수율 문제가 관측되면 재검토한다.

메타 원칙(v1.10.0 재설계)은 2층 구조다. **1층 — 모델 출력 기본값:** 결정('산출물에 기록될 선택지 2개 이상 중의 선택'으로 조작적 정의, 진행/승인 게이트는 Input Format Rules 담당)은 의존성 루트부터 한 번에 하나씩 묻는다. 상호 순환 의존으로 분리 결정이 불가능한 경우에만 종합 질문으로 묶고, 주제 유사성 기반 클러스터 그룹핑은 금지한다. **2층 — 응답 주권:** 사용자 응답이 형식을 이긴다. 위임·즉시 번복·역질문·모드 전환 같은 명시적 의도를 수용하며 이미 답한 항목을 재질문하지 않는다. 단 응답 가능 범위는 v1.14.0에서 "선택지까지 노출된 항목에만 답할 수 있다"로 개정됐다 — 하나씩 모드에서 쉼표·줄바꿈 다중 값 응답이 오면 첫 값만 현재 항목에 반영하고 나머지는 안내 후 순서대로 다시 묻는다. 선답·일괄 응답을 모드 전환으로 자동 해석하지 않는다 (모드 전환은 "다 보여줘"/"알아서" 같은 명시적 요청으로만). 그 위에 진행 모드 3종(하나씩[기본]/한꺼번에/알아서)을 두되, 모드 선택은 별도 메타 질문 없이 사전 브리핑 푸터에 접어 넣는다. 모드는 국면 한정이며 세션 복구 시 기본값으로 리셋된다. 의존성 분석은 모델 자율 추론으로 처리하며, 100% 정확도 대신 사후 파기 대기열로 보완한다. 명시적 산출물(의존성 그래프 파일 등)은 생성하지 않는다.

**질문 트랙 (v1.14.0):** 답이 산출물에 결정으로 기록되지 않는 탐색적 질문에도 규범을 신설했다. 질문은 한 번에 하나만 노출하고(종전 "한 번에 최대 2개" 규칙 대체) `❓ 질문 [N]/[M]` 진행 표시를 붙이며, M(전체 수)은 페르소나 전원 소집·병합이 끝난 뒤 확정한다. 질문 카운터는 결정 카운터(📋 확정 N/M)와 별개로 세고 합산하지 않는다. "모름"/"넘어가" 응답은 해당 질문을 조사 대기열에 적재하고 다음 질문으로 진행하며, 순회가 끝나면 적재분을 일괄 조사한다. 질문의 답은 잠정이며 국면 전환 시점에 확정된다. 이 트랙은 페르소나 피드백 루프와 층위가 다르다 — 피드백 루프는 페르소나 토론의 진행 메커니즘이고, 질문 트랙은 사용자 입력 요청의 노출 방식만 다룬다.

**자가 응답 금지 (v1.14.0):** 번호 선택지를 출력한 메시지는 그 선택을 기다리며 끝나야 한다 — 모델이 대신 선택해 진행하는 "결정 연극"을 금지한다. 선택지 생략은 고정 표현 화이트리스트("그냥 기본값으로" / "알아서 해줘" / "당연히 [X]로" / "네가 정해줘" / "아무거나")에 해당할 때만 허용하며, 목록에 없는 표현은 의도가 명확해 보여도 생략 근거가 아니다. 생략 후 사용자가 이의를 제기하면 대기열을 거치지 않고 즉시 해당 선택지를 소급 제시한다. 판단형 기준 대신 화이트리스트를 쓴 것은 다중 모델 환경에서 과대/과소 적용 편차를 없애기 위함이다.

**공통 형식·언어:** 사용자 대면 문면의 **독자 기준선은 주니어와 시니어 사이의 개발자**다 (v1.24.1). 비개발자에게 설명하듯 쓰면 글이 늘어져 읽히지 않고, 시니어끼리 말하듯 쓰면 무슨 말인지 알 수 없다. 구조 기본값은 짧은 배경(왜 묻는지/무엇이 문제인지) + 선택지마다 "고르면: [결과 1줄]" + 전문 용어 등장 시 짧은 풀이 + 💡 추천과 사유는 별도 줄. 비유는 도움이 될 때만 쓴다(의무 아님). 문서 내부 ID(REQ-001 등)는 대화에서 단독 지칭하지 않고 항상 짧은 라벨을 병기한다 (예: `REQ-001(공통 스켈레톤)`). 요약·결과 공유는 이모지를 붙인 구분 헤더 아래 `-` 항목으로 나열하고 구분 사이는 빈 줄로 띄우며, 항목을 `/`로 한 줄에 이어 붙이지 않는다. 페르소나 발언은 `[이모지] [이름]:` 줄 다음 개행 후 내용을 쓴다. 절 기호(§) 같은 법조문식 표기는 사용자 대면 문면에서 쓰지 않고 문서 이름과 절 이름을 말로 풀어 쓴다. 목록·가이드라인을 슬래시로 한 줄에 잇지 않는 규칙은 산출물만이 아니라 중계·요약 문면에도 적용된다 (v1.21.0).

독자 기준선에서 어휘 규칙 넷이 따라 나온다 (v1.24.1~v1.24.9). 첫째, 그 개발자가 이미 아는 표준 용어는 그대로 쓰고 쉽게 바꾸려고 비유어를 지어내지 않는다. 둘째, 그 개발자가 모를 수 있는 말 — 이 저장소·도메인·플러그인 안에서만 통하는 용어 — 만 나온 자리에서 짧게 풀이하며 **풀이는 병기이지 대체가 아니다** (v1.15.0의 "일상어로 대체" 규칙을 교체). 셋째, 코드에 그대로 적히는 이름(함수·타입·필드·설정 키·API·외부 라이브러리 기능명)은 **번역하지 않는다** — 사용자가 그 이름으로 코드를 검색해야 하므로 번역하면 문장이 코드와 이어지지 않는다. 넷째, **저장소에 없는 낱말로 개념에 이름을 붙이지 않는다** — 반복해서 무언가를 가리키는 명사가 저장소에서 0건이고 개발 표준 용어도 아니면 지어낸 이름이며, 풀이를 붙여도 쓰지 않는다 (풀이가 필요하다는 것이 그 이름이 일을 안 한다는 증거다).

**한 문장을 화면 폭에 맞춰 중간에서 끊지 않는다** (v1.24.1). 줄바꿈은 문단과 불릿의 경계에서만 하며, 줄을 어디서 접을지는 읽는 쪽 화면이 정한다. 터미널이 긴 줄을 접을 때 들여쓰기를 이어 주지 않으므로 **들여쓰기로 계층을 만들지 않는다** — 접힘에도 남는 것은 구분선·짧은 머리줄·빈 줄 셋뿐이다 (v1.24.9).

출력 형식은 B+D 하이브리드를 따르되, v1.10.0부터 헤더(B)는 '매 응답'이 아닌 **이벤트 기반**으로 표시한다(결정 요청/카운터 변경/흐름 복귀 시에만 — '매 응답' 규칙은 정보 제공 예외와 자기모순이었고 노이즈가 컸다). 헤더 값(N/M/K)은 대화 기억이 아니라 사전 브리핑 목록의 재집계로 산출한다. 결정 박스(D)는 v1.10.0의 우측 개방 오픈형을 거쳐 v1.14.0에서 **괘선 없는 고정 스켈레톤**으로 대체 확정됐다 — 우측 닫힘 박스는 한글/이모지 전각 폭으로 정렬 유지가 구조적으로 불가능했고, 오픈형 박스 역시 터미널 렌더링에서 깨졌다. 정렬이 필요한 괘선(┌│└)과 대화 UI의 마크다운 표는 전면 금지하며(`──` 대시 구분선·디렉토리 트리·산출물 내부의 표는 허용), 결정 요청은 `📌 결정 요청 : [제목]` + 네 칸(이 결정이 다루는 문제 · 확인된 사실 · 확인 못 한 것 · 토론 요지) + 번호 선택지(각각 "— 고르면: [결과 1줄]" 병기) + `💡 추천: [번호]`(사유는 다음 줄) 고정 문면을 그대로 따른다. 네 칸은 화면 하나만 읽고 판단할 수 있게 하는 장치다 — 긴 토론 뒤에 박스만 도착하면 무슨 문제였는지, 무슨 근거가 오갔는지 알 수 없다는 실사용 문제가 근거다.

칸 구성은 2등급으로 갈린다. 토론이나 조사가 선행된 결정은 네 칸을 상시 두고 빈 칸은 "없음"이라고 명시한다 (칸의 부재와 확인의 부재를 구분하기 위해 생략을 금지한다). 선행이 없는 표준 결정은 문제 칸만 필수이고 나머지는 해당 이력이 있는 칸만 둔다. 로컬 템플릿과 승인 게이트는 기존 형식을 유지한다. 등급 판정은 기계적 술어 하나("이 결정 직전에 토론이나 조사가 있었는가")로만 하며 주관 술어를 쓰지 않는다.

**설명 블록 (v1.24.0):** 등급이 "있었다"인 결정은 박스 **바로 앞**에 설명 블록을 둔다. 통과 검사는 박스와 그 앞 블록을 한 덩어리로 본다. 사전 브리핑이 있으면 브리핑 → 블록 → 박스 순이다. 블록은 **이름표 없는 짧은 문단**으로 쓴다 (v1.25.0에서 교체 — 이름표 넷은 "오히려 읽는데 방해가 된다"는 사용자 지적으로 철회). 왜·무엇을·어떻게·언제는 담을 내용의 점검표로 규정 안에만 남기고 화면 모양에서 뺐으며, 넷을 다 채우려 하지 않고 그 결정에 필요한 것만 쓴다. 분량 상한은 두지 않는다 — 분량을 세는 어떤 문장도 뜻 판정이 되어 주관 술어 금지와 부딪힌다. 앞선 결정과의 연결은 블록에 다시 적지 않는다 — 그건 박스 첫 칸이 담당하며 블록의 「왜」는 문단, 박스 첫 칸은 그 한 줄 요약이라 층이 다르다. 고르는 데 영향을 주지 않는 내용은 쓰지 않는다 (선별 침묵을 확인 불가 항목에서 블록 전체로 넓힌 것이며 재적용이 아니라 범위 확대다). 등급과 별개로 사용자가 더 풀어 달라고 하면 언제든 낸다.

이 블록은 「공통 형식·언어」의 "짧은 배경"과 층이 다르다 — 배경은 모든 사용자 대면 문면의 기본값이고, 블록은 토론·조사가 선행된 결정에만 붙는 별도 장치다.

**판정형과 메뉴형 (v1.25.0):** 결정 요청에는 세 모양이 있다. **메뉴형**은 선택지를 늘어놓고 고르게 하며 기본값이다. **판정형**은 모델이 내린 판정과 그 근거를 먼저 보이고 「진행」과 「의견 있음」 둘로 받으며, 답을 이미 아는 자리에서 쓴다. **지도형 판정형**은 판정형이되 후보를 모두 보이고 짚은 자리를 `▶`로 표시한다 — 고르게 하지는 않으며, 후보 집합이 닫혀 있고 그 집합을 모르면 판정이 맞는지 대조할 수 없는 자리에 쓴다.

갈림 기준은 **「근거를 댈 수 있나」**다. 저장소나 대화에서 확인 태그를 붙일 수 있는 근거를 만들 수 있으면 판정형, 못 만들면 메뉴형이다. 이 기준을 실행할 때마다 매기지 않고 **자리마다 값을 설계 시점에 박는다** — 작업 방향 확인은 지도형 판정형, 재협의 선택지와 §2 대조는 판정형, Ambiguous 단계 감지와 다시 볼 것 노출과 일반 결정 박스는 메뉴형이다. 표에 없는 자리는 메뉴형으로 읽는다.

**조립 전 조건:** 판정형으로 박힌 자리인데 확인 태그 붙은 근거가 한 줄도 없으면 메뉴형으로 조립한다. 이 판정은 박스를 조립하기 **전에** 한다 — 판정형이냐 메뉴형이냐가 박스 모양 자체를 바꾸므로, 조립을 끝낸 뒤 발견하면 되돌아가 다시 조립하는 일이 되고 그건 검사가 아니라 재작성이다.

**되묻기:** 「의견 있음」을 받으면 근거를 다시 보이고 자유 응답만 받는다 — 선택지 이름 목록을 붙이지 않는다. **판정이 두 번 틀리면 그 자리에서 메뉴형으로 넘어간다** — 두 번 틀렸다는 것은 근거가 틀렸다는 뜻이므로 횟수 상한이 아니라 이 조건이 멈춤을 만든다. 이 되묻기는 「이미 답한 항목을 재질문하지 않는다」가 금지한 재질문이 아니다 — 같은 결정의 판정을 갱신하는 것이라 새 결정 번호를 매기지 않는다. 메뉴형에서 사용자가 선택 대신 되물으면 설명을 덧붙여 같은 박스를 다시 내지 않고 **문제 칸을 다시 쓰고 박스를 재조립한다.**

**내보내기 전 검사:** 박스를 조립한 뒤 화면에 올리기 전에 다섯을 센다. 판정 항목에 주관 술어(충분한·명확한·적절한)를 쓰지 않으며, 검사마다 적용 자리가 다르다.

선택지 이름에 쓰인 낱말 중 이 박스와 바로 앞 블록 본문에 한 번도 안 나오고 풀이도 안 붙은 말이 하나라도 있으면 실패다. 글자가 나오는지로 세므로 뜻 판정이 아니며, 대화 기억을 판정 근거로 삼지 않는다. 풀이란 그 낱말의 뜻을 그 자리에서 푸는 문장을 말하고, 선택지의 "고르면:" 줄은 결과를 적는 자리이므로 풀이로 치지 않는다.

선택지의 "고르면:" 줄에 「이 결정이 다루는 문제」 칸이나 「확인된 사실」 칸에 나온 명사가 하나도 안 들어 있으면 실패다 (v1.25.0에서 작성 지침에서 통과 검사로 승격 — 강등 근거였던 "로컬 템플릿이 걸린다"는 그 자리를 고치면서 사라졌다). 대조 상대는 그 두 칸이며 "사용자가 겪는 차이인가"를 뜻으로 판정하지 않는다. 적용 자리는 메뉴형 자리 전부다.

**선택지 이름에도** 그 두 칸의 명사가 하나 이상 들어가야 한다 — "새 기능 만들기"가 아니라 "매칭 진입 경로 새로 만들기"다. 적용 자리는 작업 방향 확인과 단계 감지 둘이며, 나머지 일곱 자리는 다음 릴리스 대상이다.

**원인 검사:** 「확인된 사실」 칸의 항목 중 **지우면 선택지 하나가 무의미해지는 항목**이 「이 결정이 다루는 문제」 칸에 안 들어 있으면 실패다. 지워 보는 것으로 세며 "중요한가"로 판정하지 않는다 — 지워도 선택지가 그대로 성립하면 그 항목은 배경이지 원인이 아니다. 판정형에서는 대조 상대가 판정 문장이고, 지워도 판정이 그대로 서는 근거 줄은 뺀다.

**곁가지 검사:** 박스와 같은 메시지에 있는 문단 중 이 박스의 선택지 어느 것으로도 답할 수 없는 물음이나 통보가 있으면 실패다. 그 문단을 빼고 다음 차례에 별도 결정으로 낸다 — 「자가 응답 금지」의 "선택지를 출력한 뒤 같은 메시지에서 다른 게이트로 잇지 않는다"를 세는 단계로 만든 것이다.

검사가 실패하면 채운다. 채울 수 없으면 조사하고, 조사하고도 못 채우면 「확인 못 한 것」 칸에 적고 진행한다 — 한 번만 허용한다. "설명을 못 해서 묻지 않는다"는 경로는 만들지 않는다.

**적용 밖 (검증 기준 — 누락 0):** ① 로컬 템플릿 결정 — **설명 블록 요구만 면제한다** (v1.25.0에서 전면 면제를 반으로 쪼갬. 결과 줄 규칙과 대상 규칙은 로컬 템플릿에도 건다 — 사용자가 실제로 못 고른 화면이 바로 그 로컬 템플릿이었다) ② 선택지 없는 탐색적 질문 (대조할 선택지가 없다. 번호 선택지가 붙은 질문은 낱말 검사와 결과 줄 검사의 대상이다) ③ 진행 모드 두 가지, 한꺼번에와 알아서 (항목별로 박스를 내지 않는다) ④ 선택지 생략 화이트리스트가 발동한 지점 (박스 자체가 없다).

**질문 트랙의 조립 전 갈림 (v1.24.2):** 질문을 내보내기 전에 둘을 센다. 답이 산출물에 기록되면 탐색적 질문이 아니라 결정이므로 결정 박스로 조립하고, 답의 후보를 두세 개로 셀 수 있으면 번호 선택지를 붙인다. 페르소나 서브에이전트가 생성한 질문에도 그대로 건다 — 생성 프롬프트는 질문을 만들라고만 지시하므로 만들어진 것이 결정인지 가리는 일은 내보내는 쪽 몫이다.

**규범 재서술 지점 목록 (v1.25.0):** 이 규범을 다시 적어 둔 자리를 원본(`decision-flow.md`) 머리말에 목록으로 둔다. 규범의 뜻을 바꾸는 작업은 같은 차례에 그 목록을 함께 고친다. 목록은 **바닥이지 천장이 아니다** — 전수 스윕은 매번 그대로 돌리고, 목록에 없는 자리를 찾으면 그 릴리스에서 목록에 더한다. 두 릴리스 연속으로 사본 누락이 같은 방향으로 났고, 목록을 가진 원본은 샌 적이 없다는 것이 근거다.

**관측 항목:** 낱말 검사가 일상 기능어에도 발화한다 — 구현 중 실제로 걸렸다. 선택지를 "첫 답만 받는다"로 썼더니 "첫"이 그 화면에 안 나와 자기 검사에 걸렸고, 낱말을 바꿔 피했다. 여러 낱말짜리 선택지 이름이 나오면 같은 벽에 다시 부딪힌다. 그리고 「적용 밖」 ①이 덮는 결정 지점이 최소 여덟 곳인데 그중 plan-stage의 재협의 선택지는 판정 라운드 직후에 나오는 결정이다 — 관측할 것은 "블록이 붙었나"가 아니라 "블록이 붙어야 할 결정 중 몇 개가 로컬 템플릿이라 비켜 갔나"다.

동작은 F+E 하이브리드를 따른다. 사전 브리핑(F)의 발동은 시점이 아니라 이벤트다 — 미결 결정이 2개 이상 식별되면 그 시점에 출력하여, 사용자가 전체 그림을 닻으로 삼게 한다. 출력 위치는 v1.14.0에서 고정됐다 — 브리핑은 첫 결정 박스와 같은 메시지에서 박스 직전에 출력하고, 페르소나 토론 라운드가 선행되면 라운드 종료 후로 미룬다. 입력을 여는 문면은 실제로 응답을 기다리는 시점에만 쓴다 (초대 문구를 내놓고 검토를 계속하는 초대-대기 불일치 금지). 진행 중 새 결정이 발견되면 의존성을 한 줄로 기술하고 갱신된 순서를 통보하되 별도 응답을 기다리지 않는다(경량 이의 게이트). 앞선 결정으로 무의미해진 항목은 고지 후 제거한다(조용한 제거 금지). 우선순위 라벨(상류/확신도/되돌리기 비용/위험도)을 직접 박는 방식은 마크다운 환경에서 모델의 사후 합리화 위험을 키우므로 채택하지 않는다.

**임계값 8 가드의 폐기 (v1.10.0):** v1.9.0의 "8개 도달 시 분할 제안 → 거절 시 압축 헤더" 메커니즘은 배포 리뷰에서 총체적 결함(분할 제안 자체가 메타 질문 역설, 압축 헤더의 기호 의미 역전, '풀 박스 3개 표시'와 D 템플릿의 구조 모순)이 확정되어 수리 대신 삭제한다. Miller's Law 인지 한계 보호라는 원 취지는 "미결 8개 이상 시 브리핑 푸터에 일괄/위임 모드 권장 한 줄"로 대체한다 — 메타 질문 없이 인지 부하 탈출구를 제공한다. 헤더는 단일 형식만 유지한다.

충돌 처리는 발견 주체로 구분한다. 모델/페르소나가 자체 감지한 충돌은 대기열에 추가(추가 시점 1회 고지)하고 현재 국면의 모든 결정 완료 후 일괄 노출하여 [모두 재논의/일부만/모두 기각] 옵션을 제공하며, phase 파일 작성 직전이 최종 안전망이다. 노출 화면은 구분선으로 항목을 가르고 항목마다 「이미 정한 것」과 「다시 보자는 이유」 두 소제목을 둔다 (v1.24.9). 사유에 분량 상한을 두지 않는다 — 왜 다시 봐야 하는가가 고르는 근거라 한 줄로 줄이면 고를 수 없다. 항목마다 번호를 붙이고 마지막 구분선으로 선택지와 가른다. 화면에는 저장소 내부 용어를 쓰지 않고 「다시 볼 것」으로 쓴다. 사용자가 명시적으로 번복을 요청하면 대기열을 거치지 않고 즉시 처리한다. 결정 박스 없이 통과된 페르소나 합의에도 식별 가능한 이름을 부여해 번복 시 참조를 가능하게 한다.

**상태 보존 (v1.10.0):** 결정 흐름 상태는 대화 컨텍스트에만 존재해 compact/세션 이관 시 유실된다는 결함에 대해, HANDOFF.md에 조건부 '결정 흐름 상태' 섹션(상태 마커 [x]/[>]/[ ]/[-]/[=], 재논의 대기열 전문)을 추가한다. 기록 시점은 save·compact 직전·국면 완료 시로 한정한다 — 결정마다 파일에 기록하는 상시 원장 방식은 대화 템포에 파일쓰기 툴콜이 개입하는 노이즈로 기각했다. 질문 순회가 활성이면 결정 마커와 혼용하지 않는 별도 줄(`❓ 질문 진행: [N]/[M] · 국면: [국면명]` + 미답변 질문 목록)로 기록한다 (v1.14.0 — 기존 마커는 결정 전용 의미라 재사용 시 의미가 혼란해진다). 등급 판정 근거(직전 토론·조사 유무), 발언 재실행 이력, 검증 태그 최초 고지 여부도 함께 기록한다 (v1.21.0) — 유실되면 보수적으로 재판정한다.

기존 페르소나 피드백 루프와의 관계는 보완적이다. 라운드 카운터·합의/미합의 마커·비판 라운드 로빈은 루프 *진행 중* 메커니즘이며, 결정 요청 흐름은 토론 *후* 사용자 결정 단계에 적용된다. 에이전트 태그(`[Socratic]`, `[Contrarian]`, Standalone Mode 태그 없음)와 결정 요청 분리 규칙(합의 도출 시 박스 생략, "이 두 가지에 대해" 같은 대명사 참조 금지)은 SSOT 내부에 통합되어 있다. 서브에이전트 원문에 결정 요청 문구가 포함돼 있으면 그 부분만 걸러 내되, **발언 자체는 고쳐 쓰지 않고 원문 그대로 나열한다** (v1.21.0). 본체가 압축·재요약하는 방식은 뭉개짐 사고의 원인 지점으로 확인돼 재논의에서 기각됐다. 규격을 어긴 발언은 재실행을 한 번 요청하고 그 사실을 화면에 표시하며, 재위반이면 발언을 제외하고 제외 사실을 고지한다. 본체의 개입은 `↳` 단독 마커로만 쓰고 반증·확인 불가 승격·새 사실 추가에 한정한다.

적용 경계는 '로컬 템플릿 우선' 규칙으로 결정론화한다. 스킬 본문에 구체 출력 템플릿이 있는 결정 지점(시드 확인·Simplifier·국면 0·plan-stage 재협의·document-consolidation 단계 확인)은 해당 템플릿을 그대로 출력하고 D 박스로 재조립하지 않는다. document-consolidation은 이미 순차 구조이므로 헤더·브리핑·대기열을 적용하지 않는 명시적 예외로 선언한다(v1.9.0의 "자연스럽게 풀 박스를 따른다" 서술은 같은 파일의 인라인 템플릿과 자기모순이어서 교체). plan-stage의 OPEN_QUESTIONS 템플릿은 "각 항목에 대해 결정을 내려주시면"이라는 일괄 결정 유도 문구가 메타 원칙과 정면 충돌하여 브리핑(F) 정합 구조로 교체했다.

국면 단위는 대응표로 고정한다 — brainstorming은 국면 0~4 각각이 하나의 국면, plan-stage는 Step 1~4 전체가 하나의 국면, 기타 적용 스킬은 스킬 실행 1회가 한 국면이다. 재논의 대기열의 최종 안전망 노출 시점도 이 국면 단위를 따른다.

## 게이트 실효성

게이트(사용자 확인 지점)는 "제 역할을 하는가"를 기준으로 관리한다 (v1.15.0). 원래 과제는 확인 절차 축소(배칭)였으나 조사에서 전제가 낡았음이 확인됐다 — 번호 응답 UI로 확인이 많아도 불편이 크지 않고, 묶어 보여주기는 "하나씩" 규범과 충돌한다. 대신 실제 결함 2유형(무게가 다른 행동이 한 확인에 결합된 등급 오류 · 확인은 있으나 실효가 없는 형식적 게이트)을 바로잡는 실효성 정비로 재정의됐다. 게이트 수 줄이기 자체는 목표가 아니다 — 기준은 오직 역할 수행 여부다 (실제 제거 판정 0건).

**게이트 신설·심사의 공통 기준 — 3단 결정 트리** (예/아니오만 — 세션·모델 불문 재현): ① 이 확인이 없으면 되돌릴 수 없는 결과가 발생하는가? → Yes = 유지 ② 답이 사실상 항상 같은가? → Yes = 자동화 후보 ③ 생략해도 사용자가 사후에 알 방법이 있는가? → No = 안전망 선행 (안전망을 설계할 수 없으면 자동화 보류)

**자동 결정 안전망 3요소:** 확인을 생략하는 게이트에는 ① 답을 요구하지 않는 사후 고지 1줄 (표준형: `[이모지] [무엇]을 자동 [처리]했습니다 — [요지]. (수정하려면 말씀하세요)`) ② 처리 내용의 기록 ③ 소급 수정 경로가 따라야 한다. 규범 전문은 development-principles의 「자동 결정 안전망 (공통 포맷)」·「게이트 신설 체크리스트」 2절이 SSOT이며, 각 스킬은 1줄 참조로 연결된다.

**토론 라운드의 차단성 판별문:** 라운드 증가는 차단성 우려에만 허용한다 — "이 우려가 반영되지 않으면 최종 승인을 진행할 수 없는가?" Yes면 차단성(라운드 증가), No면 권고성(회계 1줄 기록으로 종결). 페르소나 초기 의견이 전원 일치하면 합의 기록으로 라운드를 종료한다. 단 전원 일치라도 판정 근거가 미실측 수치·구조적 상한 가정에 기대면 합의 블록에 실측 값 또는 추정 근거 1줄을 기록해야 종료할 수 있다 (v1.16.0 — 동일 컨텍스트를 공유한 페르소나의 일치는 독립 검증이 아니며, 낙관 일치가 실측 없이 통과한 계획 결함이 실증됨).

**v1.15.0 심사 처분 요지 (34행):** 유지 23 · 자동화 5(중간 산출물 삭제·PLAN 연속 진행·HANDOFF 복구 재확인·페르소나 저장·자동모드 키워드 confirm — 전부 안전망 동반) · 조건부 자동화 1(잔존 HANDOFF: git은 자동+고지, no-git은 확인 유지) · 분리 1(커밋/푸시 — 커밋은 로컬 중위험, 푸시는 원격 공개 고위험이라 각자 확인) · 생략+사후 고지 2(merge-to-domain digest 학습 게이트 — 검증 재료 없는 확인) · 포괄 정비 1(Architect 라운드 등급표) · 직접 갱신 1(국면 4 시드) · 제거 0. 심사 전체 표는 git 이력의 gate-effectiveness feature 문서에 있다. 비가역 최종 승인(dry-run 승인 등)은 어떤 진행 모드에서도 생략할 수 없다.
