> 워크플로우의 실행 환경 적응(VCS 분기)부터 종료 시퀀스(문서 취합 → 커밋 → 푸시)까지, DEVELOP 단계의 전체 라이프사이클을 관리한다.

## 시스템 개요

dev-workflow는 Superpowers 위에서 동작하는 플러그인이다. DEVELOP 단계에 진입하면 Superpowers의 `subagent-driven-development`에 실행을 위임하는데, 이 과정에서 두 가지 구조적 문제가 존재했다.

첫째, 실행 환경의 다양성이다. Superpowers는 git worktree를 REQUIRED로 명시하지만, 언리얼 프로젝트처럼 Perforce를 사용하는 환경에서는 `.git` 자체가 존재하지 않는다. 기존에는 Claude Code가 worktree 실패를 암묵적으로 무시하고 메인 디렉토리에서 직접 작업했으나, 공식적인 대응 전략이 없었다.

둘째, 종료 시점의 제어 부재다. DEVELOP/REVIEW 완료 후 Superpowers가 곧바로 커밋을 제안하면서 문서 취합(document-consolidation)이 스킵되는 문제가 반복되었다. 사용자가 매번 "마무리하고 커밋하자"라고 수동 개입해야 하는 마찰이 있었다.

이 두 문제를 해결하기 위해 workflow-orchestrator의 역할을 확장했다. 기존의 세션 시작 프로토콜(시작 → 단계 감지)에 더해, VCS 감지에 의한 실행 모델 분기와 종료 프로토콜을 추가하여 워크플로우의 전체 라이프사이클을 관리하도록 했다. 핵심 원칙은 Superpowers 자체를 수정하지 않고, 컨텍스트 주입과 래퍼로만 제어한다는 것이다.

## VCS 감지와 실행 모델 분기

### 환경 감지

세션 환경 컨텍스트가 제공하는 "Is directory a git repo" 값으로 VCS를 감지한다 (v1.11.1부터). Yes면 `git-mode`, No면 `no-git-mode`를 설정하며, 감지는 DEVELOP 또는 REVIEW 진입 시점(둘 중 먼저)에 세션당 1회만 수행한다. 값이 제공되지 않은 경우에만 git 명령으로 확인하고, 모호한 경우에는 사용자에게 worktree 사용 여부를 질문한다.

초기(v1.11.0까지)에는 `.git` 디렉토리 존재 여부를 직접 검사했으나, linked worktree에서는 `.git`이 디렉토리가 아닌 파일이라 오탐하는 결함이 확인되어 v1.11.1에서 환경 컨텍스트 조회로 교체했다. p4 CLI 감지나 별도 설정 파일 방식은 복잡도 대비 가치가 부족하여 기각을 유지한다.

### git-mode

기존 Superpowers 방식을 그대로 사용한다. `using-git-worktrees`로 worktree를 설정한 뒤 `subagent-driven-development`를 실행하며, git commit과 SHA 비교 기반의 Code Quality Review가 동작한다.

### no-git-mode

worktree 설정 단계를 스킵하되, Superpowers의 2단계 리뷰 loop(Spec Review + Code Quality Review)는 그대로 유지한다. 이를 위해 다음 규칙을 적용한다:

- worktree 설정 단계를 스킵하고, 프로젝트 디렉토리에서 직접 작업한다
- git commit 대신 Implementer 리포트를 체크포인트로 사용한다
- Code Quality Reviewer에게 SHA 비교 대신 Implementer 리포트의 "Files changed" 목록을 전달하여, 리뷰어가 해당 파일을 직접 읽어 리뷰한다
- Spec Review는 원래 코드 직접 읽기 방식이므로 변경 없다
- 세션에 노출된 네이티브 태스크 추적 도구로 Task 진행을 추적한다 (예: TaskCreate/TaskUpdate 계열 또는 TodoWrite — 특정 도구명에 의존하지 않는다)
- DEVELOP 진입 시 감지된 모드를 한 줄로 안내한다

worktree 불가 시 `executing-plans`로 폴백하는 대안도 검토했으나, 리뷰 메커니즘이 없고 공식적으로 비권장이므로 기각했다. 체크포인트를 p4 shelve로 구현하는 방안도 VCS 의존성과 환경 설정 부담 때문에 기각하고, VCS에 완전 독립적인 파일 기반 마커를 선택했다.

### worktree의 실제 가치

worktree의 핵심 가치는 작업 공간 격리이다. Superpowers의 Task 실행은 이미 순차 모델(병렬 디스패치 금지)이므로 병렬성은 부가 가치에 불과하다. Perforce 환경에서는 바이너리 의존성, 에디터 연동 필요성 등으로 worktree의 가치가 제한적이며, 최종 검증은 사용자가 에디터에서 수행한다고 가정한다.

## 마무리 시퀀스와 종료 프로토콜

### 문제와 해결

Superpowers는 태스크 완료 후 곧바로 커밋을 제안하는 경향이 있다. 이로 인해 document-consolidation이 스킵되어 문서가 산발적으로 남는 문제가 발생했다. 이를 해결하기 위해 두 가지 조치를 취했다.

첫째, DEVELOP 진입 시 Superpowers에 "모든 태스크 완료 후 커밋을 제안하지 않는다. 완료 보고만 한다. 마무리 시퀀스는 오케스트레이터가 관리한다."라는 컨텍스트를 주입한다. 이는 no-git-mode 컨텍스트 주입에서 검증된 동일한 패턴이며, git-mode와 no-git-mode 공통으로 적용된다. 다만 텍스트 기반 지시이므로 100% 제어를 보장할 수 없는 한계는 수용한다.

둘째, 사용자가 자연어로 마무리를 선언하면 정해진 순서의 시퀀스가 자동 진행된다.

### 마무리 시퀀스 흐름

사용자의 마무리 선언을 감지하면 다음 순서로 실행한다:

0. **이슈 카드 잔존 검사 (v1.18.0)** — feature의 `issues/`에 미해소 이슈 카드가 남아 있으면 목록을 제시하고 처리 또는 의식적 보류 확인을 받는다. "보완이 끝나야 feature가 마무리된 것"의 강제 지점이다.
1. **문서 취합** — document-consolidation 스킬의 `consolidate-main`을 호출한다. 실패 시 중단하고 사용자에게 알린다. 이 단계 안에 **§2 대조**가 있다 (v1.24.6) — 개발 중 쌓인 변경 이력과 목표·비목표를 맞춰 보고, 이력의 어떤 행이 §2 문장을 거짓으로 만들면 갱신안을 내 확인을 받는다. 어긋남이 0건이면 출력이 없다. 목표·비목표를 정면으로 묻는 판별문은 크리티컬 이슈에만 걸리므로, 경미·중간 이슈가 조금씩 밀어낸 것을 여기서 한 번에 잡는다.
2. **README 영향 판단** — 변경 내용이 README에 영향을 주는지 Claude가 판단한 뒤 사용자에게 확인한다. 영향이 없으면 스킵하고, README.md가 프로젝트 루트에 존재하지 않으면 역시 스킵한다.
2.5. **규칙 주입** — `rules-injection`을 호출해 `applies-to: completion` 규칙(예: 커밋 메시지 형식)을 컨텍스트에 첨부한다.
3. **커밋 제안** — 사용자 확인 후 커밋을 실행한다.
4. **푸시 제안 (커밋 성공 후)** — 커밋 요지를 한 줄로 알리고 원격 푸시 여부를 별도로 확인한다. 커밋만 하고 마치는 선택을 허용한다.

커밋과 푸시를 한 확인에 묶던 방식은 v1.15.0 게이트 심사에서 등급 오류로 판정되어 2단으로 분리됐다 — 커밋은 로컬(중위험)이고 푸시는 원격 공개(고위험)라 각자 등급에 맞는 확인을 받는다. 각 단계는 성공/실패를 명시적으로 판단하며, 실패 시 해당 지점에서 중단하여 커밋을 차단한다.

### 마무리 진입의 네 축

초기에는 자연어 감지 하나였으나, 실사용에서 두 가지가 관측돼 v1.20.0에서 네 축으로 늘렸다. 마무리 질문은 DEVELOP 종료 시 한 번 발화되는 이벤트라 이슈 처리 등으로 흐름을 벗어나면 재무장 계기가 없어 조용히 스킵됐고, 사용자가 "마무리하자"라고 말해도 모델이 Completion Protocol로 라우팅하지 않고 자체 정리하는 라우팅 실패가 실관측됐다. 놓치는 주체는 사용자가 아니라 모델이었다.

**1축 — 훅.** `UserPromptSubmit` 훅 `completion-nudge`가 "미완료 잔존이 있고 마무리 어휘가 나왔을 때"에만 판정 위임형 지시를 주입한다. 발화 순간 컨텍스트 최후방에 들어가므로 라우팅 실패 세 갈래를 함께 우회한다. 매 턴 상시 주입은 훅 지연과 배너 무시를 부르므로 조건부 정밀 주입을 택했다. 주입문은 판정을 모델에 위임하는 형태다 — "세션 전체의 마무리 의도면 라우팅, 특정 코드 정리 요청이면 해당 없음" + 무시 탈출구.

**2축 — 경고등.** 열려 있음을 지속 가시화한다. 파일 술어(`status`가 complete가 아니고 plan.md에 잔여 태스크가 없음)가 참일 때 오케스트레이터의 일단락 출력 말미에 `🔔 마무리 대기` 한 줄을 붙이고, 기존 statusline이 있는 사용자에게는 setup에서 통합을 제안한다. 술어를 파일로 정한 것은 컴팩션이나 세션 교체 뒤에도 다시 파생할 수 있어서다 — 대화 기억을 저장소로 쓰면 원문제와 같은 결함이 된다.

**3축 — 명령.** `/dev-workflow:finish` 호출 자체가 완료 선언이며 트리거 감지를 생략한다. 이를 위해 Completion Protocol 절을 `references/completion-protocol.md`로 분리해 command가 직접 읽는다 — 직행을 파일 구조로 보장하는 방식이고, 오케스트레이터에 분기를 만들면 본문 전체가 다시 로드된다.

**4축 — 상시 규범.** `bootstrap.md`의 COMPLETION 매핑을 명령형과 금지문으로 두어 어휘 밖 발화의 안전망으로 삼는다. 수사를 격화하지 않고 명령형 교체만 한다.

**어휘 SSOT.** 감지 어휘의 원본은 오케스트레이터의 트리거 목록 하나다. 훅은 그 목록의 미러이며 크로스레퍼런스 주석을 달고, 둘이 어긋나지 않는지 확인하는 diff 검사가 회귀 테스트의 0번이다.

- 한국어: "마무리", "마무리해줘", "완료", "정리해줘", "끝내자"
- 영어: "wrap up", "finish", "finalize", "done"

**완료 판단의 주체는 언제나 사용자다.** CI나 PR 머지를 완료 앵커로 삼는 방식은 핵심 원칙 위반으로 기각했다 — 스킵 지점을 복제하고 좀비 상태를 만든다.

## 관련 파일

| 파일 | 용도 |
|------|------|
| `skills/workflow-orchestrator/SKILL.md` | 세션 시작 프로토콜, VCS 감지, DEVELOP 분기, 종료 프로토콜 — 라이프사이클 전체를 관리하는 중앙 오케스트레이터 |
| `skills/document-consolidation/SKILL.md` | 마무리 시퀀스의 Step 1에서 호출되는 문서 취합 스킬 (§2 대조 포함) |
| `skills/workflow-orchestrator/references/completion-protocol.md` | 마무리 시퀀스의 SSOT — command가 직접 읽는다 |
| `hooks/completion-nudge` | 마무리 어휘 + 미완료 잔존 시 판정 위임형 지시 주입 (1축) |
| `hooks/lib/detect-remnants` | 잔존 감지 공용 스크립트 — session-start · completion-nudge · statusline이 함께 쓴다 |
| `commands/finish.md` | `/dev-workflow:finish` — 호출 자체가 완료 선언 (3축) |
| `tests/hooks/` | 훅 회귀 테스트 — 0번이 어휘 SSOT diff 검사다 |

## 핵심 결정 사항

| 결정 사항 | 선택 | 근거 |
|-----------|------|------|
| VCS 감지 방법 | 세션 환경 컨텍스트 "Is directory a git repo" 값 (v1.11.0까지 `.git` 디렉토리 유무 → v1.11.1 교체) | `.git` 리터럴 검사는 linked worktree(`.git`이 파일)에서 오탐. 환경 컨텍스트 값은 추가 도구 호출 없이 확실 |
| worktree 불가 시 실행 모델 | subagent-driven-development 유지 (worktree만 스킵) | 2단계 리뷰 loop의 품질을 유지하기 위함 |
| no-git-mode 체크포인트 | 파일 기반 마커 (네이티브 태스크 추적 + Implementer 리포트) | VCS에 완전 독립적이고 구현이 단순 |
| Code Quality Review 대체 방식 | 파일 목록 + 코드 직접 읽기 | Implementer 리포트에 이미 "Files changed"가 존재 |
| Superpowers 수정 여부 | 수정하지 않음 (래퍼/컨텍스트 주입만) | 외부 플러그인이므로 업데이트 호환성 유지 |
| 마무리 시퀀스 제어 위치 | workflow-orchestrator | 세션 시작 프로토콜과 대칭적 구조, 중앙 관리 |
| 커밋 제안 억제 방식 | 컨텍스트 주입 | no-git-mode에서 검증된 패턴 재활용 |
| 마무리 트리거 | 자연어 감지 | 사용자의 자연스러운 흐름 유지 |
| README 업데이트 판단 | Claude 자동 판단 + 사용자 확인 | 불필요한 업데이트 방지 |
| 커밋/푸시 게이트 (v1.15.0) | 확인 2단 분리 — 커밋 확인 후 푸시 별도 확인 | 무게가 다른 행동(로컬 커밋 vs 원격 공개)이 한 확인에 결합된 등급 오류 교정. 커밋 자동화안은 사용자 전역 "커밋 전 확인" 규칙과 충돌해 기각 |
| 라우팅 보강 (v1.20.0) | 조건부 정밀 주입 훅 | 발화 순간 컨텍스트 최후방에 들어가 라우팅 실패 세 갈래를 함께 우회한다. 매 턴 상시 주입은 훅 지연과 배너 무시를 부른다 |
| 경고등 채널 (v1.20.0) | 규범 줄 + 기존 statusline 한정 | 회색 지대를 정밀 조준하면서 결정론 채널을 병행한다. 신규 statusline 설치 제안은 사용자가 명시 제외했다 |
| 회색 지대 경계 (v1.20.0) | 파일 술어 | 컴팩션·세션 교체에도 다시 파생할 수 있다. 대화 기억을 저장소로 쓰면 원문제와 같은 결함이 된다 |
